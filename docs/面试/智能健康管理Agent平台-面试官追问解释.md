# 智能健康管理 Agent 平台：面试官追问解释

这份文档用于准备面试追问。回答时建议遵循一个结构：先说结论，再说为什么这么设计，最后说权衡和改进空间。

## 1. 为什么这个项目适合用 Agent，而不是普通 ChatBot？

普通 ChatBot 更适合单轮问答，输入问题后直接生成答案。但健康咨询经常不是一个单步问题，而是一个需要多阶段处理的任务。

例如用户说：“我最近血压偏高、睡眠不好、体检血脂也高，帮我看看生活上怎么调整。”这个问题里包含信息抽取、风险识别、知识检索、建议生成和注意事项补充。如果直接让模型一次性回答，容易遗漏信息，也难以控制过程。

所以我把它设计成 Agent：

- 先识别用户意图和任务复杂度。
- 再根据问题选择执行模式。
- 需要知识时调用 RAG 检索。
- 需要计算时调用工具。
- 最后综合各步骤结果生成回答。

Agent 的价值在于把复杂任务拆成可控步骤，让模型不只是生成文本，而是参与任务规划、工具选择和结果整合。

## 2. 为什么同时支持 ReAct 和 Plan-and-Execute？

这两个模式适合的问题类型不一样。

`ReAct` 适合探索型任务。它的特点是边思考边行动，模型可以根据中间观察结果决定下一步。例如用户问一个不确定是否需要知识库的问题，Agent 可以先判断，再决定是否检索、是否调用工具。

`Plan-and-Execute` 适合目标明确但步骤较多的任务。它会先把复杂问题拆成计划，再逐步执行。例如“根据我的血压、血脂、睡眠情况，帮我制定一周生活调整建议”，这种问题如果先规划，会更有条理。

我没有只用一种模式，是因为单一模式会有局限：

- 只用 `ReAct`，复杂任务容易步骤发散，执行链路不可控。
- 只用 `Plan-and-Execute`，简单问题又显得太重，延迟和成本更高。

所以系统通过条件路由，根据任务复杂度选择合适模式。

## 3. 条件路由是怎么判断的？

可以从三个维度判断：

1. 用户意图：是普通问答、知识检索、计算任务，还是综合健康建议。
2. 任务复杂度：是否包含多个健康指标、多个目标或多个约束。
3. 工具需求：是否需要查知识库、调用计算工具、读取历史记忆。

简单问答可以直接走 RAG 或普通回答；复杂咨询进入 Agent 编排；多步骤任务优先走 `Plan-and-Execute`；需要动态观察工具结果的问题更适合 `ReAct`。

实际工程里，路由可以由规则、LLM 分类或两者结合实现。规则稳定、成本低，LLM 分类泛化能力强。我的设计倾向是先用规则兜底，再用 LLM 做更细的语义判断。

## 4. 为什么 RAG 要用混合检索？

因为健康知识场景同时存在专业术语和口语表达。

关键词检索的优势是精确。比如“低密度脂蛋白”“空腹血糖”“BMI”这类词，关键词检索能很好命中。

向量检索的优势是语义匹配。比如用户说“最近总是头晕，和血压有没有关系”，这类表达不一定包含知识库原文里的关键词，但语义上和血压、头晕、风险因素相关。

如果只用关键词检索，对口语问题不友好；如果只用向量检索，对专业词和数值类指标有时不够稳定。所以我采用关键词检索和向量检索双路召回，再做融合排序。

## 5. RRF 是什么？为什么用 RRF？

`RRF` 是 Reciprocal Rank Fusion，倒数排名融合。

它不直接依赖不同检索器的原始分数，而是根据每条结果在各个召回列表里的排名来融合。一个常见形式是：

```text
score(d) = sum(1 / (k + rank_i(d)))
```

其中 `rank_i(d)` 表示文档 `d` 在第 `i` 个检索器结果里的排名，`k` 是平滑参数。

选择 `RRF` 的原因是关键词检索和向量检索的分数体系不一样，BM25 分数和向量相似度不能直接比较。`RRF` 用排名融合，可以减少不同分数尺度带来的问题，工程上简单、稳定，也适合多路召回融合。

## 6. 为什么还需要 rerank？

召回阶段的目标是尽量把可能相关的内容找回来，所以它更关注召回率。但最终给模型的上下文不能太长，需要把最相关的内容排在前面。

rerank 的作用是做更精细的相关性判断。比如向量召回可能找到了语义相近但不够准确的内容，关键词召回可能找到了词匹配但语义不相关的内容。通过 rerank，可以把真正和用户问题更相关的片段排到前面。

如果面试官追问成本，可以补充：rerank 不一定对所有结果都做，一般只对 top N 候选做重排，控制延迟和计算成本。

## 7. 文档为什么要分块？怎么分块？

向量模型和 LLM 上下文都有长度限制，所以不能把整篇文档直接塞进去检索和生成。分块的目标是让每个 chunk 既足够小，方便精确召回，又保留足够语义，避免信息被切断。

常见做法是按照标题、段落、句子或固定 token 长度进行切分，并保留一定 overlap。overlap 的作用是减少边界信息丢失。例如一个健康建议的条件和结论可能跨段落，如果没有重叠，检索结果可能只召回一半信息。

我的设计里会优先保留语义完整性，再考虑长度控制。

## 8. 为什么要做多层记忆？

因为不同类型的记忆有不同生命周期。

当前会话里的上下文，例如用户刚刚提到的症状，属于短期记忆，要求读写快，所以适合放在 `Redis`。

历史会话摘要、用户画像、健康偏好等信息需要长期保存，所以适合放在 `PostgreSQL`。

跨会话语义召回需要根据当前问题找到过去相关内容，不只是按时间查，所以适合用向量数据库，比如 `Milvus`。

多层记忆的核心目的，是在成本、速度和个性化之间做平衡：短期记忆保证连续性，摘要压缩控制上下文长度，长期语义记忆支持跨会话个性化。

## 9. 为什么短期记忆用 Redis？

`Redis` 适合高频、低延迟的会话上下文读写。多轮对话中，每次请求都需要读取最近几轮消息，并在回答后写回新消息。这类数据访问频繁，但不一定都需要长期保存。

Redis 的优势是速度快、适合设置过期时间，也方便实现滑动窗口。比如只保留最近 N 轮对话，或者对过长会话触发摘要压缩。

如果 Redis 不可用，也可以降级到数据库或内存缓存，但性能和并发能力会弱一些。

## 10. 为什么长期记忆不用只存在 PostgreSQL？

`PostgreSQL` 适合结构化数据，例如用户 ID、会话 ID、时间、摘要、标签等。但长期记忆的召回往往是语义问题，不一定能靠精确字段查询解决。

例如用户现在问：“我之前是不是说过睡眠的问题？”如果历史记录里没有固定标签，只靠 SQL 查询就比较困难。向量数据库可以把历史摘要或关键片段向量化，根据语义相似度召回。

所以我采用 `PostgreSQL` 存结构化事实和持久化记录，`Milvus` 存语义向量，两者互补。

## 11. 为什么需要摘要压缩？

直接把所有历史对话放进 prompt 有三个问题：

- token 成本高。
- 上下文噪声多，影响模型注意力。
- 超过上下文长度后会丢失重要信息。

摘要压缩可以把长对话变成结构化摘要，比如保留用户基本情况、长期症状、明确偏好、已给过的建议和待跟进事项。这样既减少 token，又能保留对后续回答有用的信息。

关键点是摘要不能只压缩文本，还要尽量保留可复用事实。

## 12. 如何避免健康咨询中的幻觉？

我从几个层面控制：

1. 知识层面：用 RAG 引入外部健康知识，减少模型凭空回答。
2. 生成层面：要求回答基于检索内容，避免绝对化诊断。
3. 流程层面：复杂任务通过 Agent 拆解，降低一次性生成的遗漏风险。
4. 安全层面：对高风险症状提示就医，不做疾病确诊。
5. 兜底层面：检索结果不足时说明不确定性，而不是强行生成。

如果继续优化，我会加入来源引用、医学安全规则库和专门的回答评测集。

## 13. 如何处理工具调用失败？

工具调用失败不能直接影响最终体验，所以需要状态跟踪和降级策略。

例如 RAG 检索失败时，可以降级为通用健康建议，并明确提示知识库暂时不可用；计算工具失败时，可以让模型说明暂时无法计算，而不是编造结果；外部服务失败时，可以重试或切换备用服务。

Agent 状态里应记录每一步的输入、输出、错误和重试次数，这样既方便运行时降级，也方便后续排查问题。

## 14. 为什么需要任务状态跟踪？

Agent 和普通函数调用不同，它可能包含多轮推理、多次工具调用和多次结果整合。如果没有状态管理，很难知道当前执行到哪一步、哪个工具返回了什么、是否需要重试。

状态跟踪可以解决三个问题：

- 可控：限制最大步骤数、最大重试次数，避免循环。
- 可观测：记录中间过程，方便调试和分析。
- 可恢复：局部失败时可以降级或重试，而不是整条链路崩掉。

这也是 Agent 工程化里很重要的一点。

## 15. 为什么不能完全让 LLM 自己决定流程？

LLM 的优势是语义理解和生成，但它并不擅长保证流程稳定性。如果完全让模型自己决定，可能出现工具滥用、步骤发散、循环调用、遗漏关键安全提示等问题。

所以我的设计是：让 LLM 负责它擅长的语义判断、规划和总结；让代码负责边界、路由、状态、重试、异常处理和安全规则。

一句话总结就是：模型负责智能，工程框架负责稳定。

## 16. 这个项目最大的难点是什么？

我认为最大的难点不是某一个单点技术，而是如何把 Agent、RAG、记忆和工具调用组织成稳定的工程链路。

单独做一个 RAG 问答或者一个工具调用并不难，难的是用户真实问题进来后，系统要判断走什么流程、取哪些上下文、查哪些知识、调哪些工具、如何处理失败、最后如何生成可靠回答。

这个项目的核心价值就在于把这些模块串成了一个可控的 Agent 工作流。

## 17. 如果让你继续优化，你会怎么做？

我会优先做四类优化。

第一是安全性。健康场景要加入高风险症状识别、禁忌提醒、就医建议和免责声明，避免系统表现得像诊断工具。

第二是可追溯性。回答里加入知识来源引用，让用户和面试官能看到答案依据。

第三是知识图谱融合。健康咨询里很多问题不只是文本相似度匹配，而是实体和关系推理，比如“某个指标异常可能和哪些疾病、症状、生活习惯相关”“某类人群有哪些饮食禁忌”。知识图谱可以把疾病、症状、指标、药物、饮食建议、风险因素等结构化，和 RAG 形成互补：RAG 负责从文档中找依据，知识图谱负责提供实体关系和推理路径。

第四是评测体系。建立健康问答评测集，从检索命中率、回答准确性、上下文一致性、工具调用成功率和安全性几个维度评估系统效果。

这四件事能让项目从“能跑的 Agent 应用”进一步接近“可评估、可迭代、可上线”的 Agent 系统。

## 18. 能不能举两个例子说明完整工作流程？

可以。

第一个例子是简单知识问答。用户问：“高血压患者饮食要注意什么？”系统会先识别为健康知识问答，复杂度较低，于是走 RAG 链路。它会同时使用关键词检索和向量检索，从知识库召回限盐、低脂饮食、控制体重、规律运动等相关片段，然后用 `RRF` 融合排序，筛选最相关上下文交给 LLM。最后 LLM 基于检索内容生成回答，并提示这类建议不能替代医生诊断。

这个流程的重点是快、稳、有依据。因为问题比较明确，不需要复杂任务规划，直接检索增强生成就够了。

第二个例子是复杂综合咨询。用户问：“我最近血压偏高，睡眠不好，体检血脂也高，帮我分析一下日常应该怎么调整。”系统会判断这是多因素综合咨询，进入 Agent 工作流。Agent 会先拆解任务：提取用户问题中的健康指标和症状，读取历史记忆里的年龄、既往病史、饮食偏好等上下文，检索高血压、血脂异常和睡眠相关知识，必要时调用健康指标解释或计算工具，最后把结果汇总成饮食、运动、睡眠、监测和就医提醒几个部分。

这个流程的重点是可控。系统不会让模型一次性自由发挥，而是通过任务拆解、知识检索、工具调用和结果整合来降低遗漏和幻觉风险。

## 19. 一句话总结项目亮点

这个项目的亮点是：围绕健康咨询场景，把 Agent 任务规划、混合 RAG、多层记忆、工具调用和异常降级串成了一套完整的工程化链路，使系统能够更稳定地处理复杂、多轮、个性化的健康咨询问题。
