## 一、Agent 核心循环

### Q1：ReAct 是什么？你项目中怎么实现的？

**一句话**：ReAct = Reasoning + Acting，让 LLM 边思考边行动，交替进行。

**项目实现**（[react_agent.py](../../app/core/agent/react_agent.py)）：

```python
# 核心循环只有 3 行逻辑：
for step_idx in range(self.max_steps):
    raw = await self._llm.acomplete(messages, temperature=0.2)  # 1. LLM 输出文本
    parsed = _parse_react_step(raw)                              # 2. 正则解析成结构化数据
    obs = await self._tools.invoke(action, action_input)         # 3. 执行工具拿 Observation
```

**完整流程**：

```
Step 1: Thought: 需要搜索 → Action: web_search → Action Input: {"query":"..."}
        → 系统自动追加 Observation: "搜索结果: ..."
Step 2: Thought: 信息够了 → Final Answer: "答案是..."
```

**追问：为什么不用 LangChain 的 ReAct 封装？**
> 自研实现让我完全掌控每一步——用正则解析而不是调 AgentExecutor，max_steps 硬限制防死循环，每步都有 try/except 兜底。而且面试时我能讲清楚底层原理。

### Q2：ReAct 和 Chain-of-Thought (CoT) 有什么区别？

| | CoT | ReAct |
|------|------|------|
| 核心动作 | 只推理，不行动 | 推理 + 行动交替 |
| 外部信息 | 全靠 LLM 内部知识 | 可以调工具获取外部信息 |
| 适用场景 | 数学推理、逻辑题 | 需要查资料、调 API 的任务 |
| 例子 | "一步步算 123×456" | "搜索今天天气，然后告诉我穿什么" |

**关键区别**：CoT 是闭卷考试（全凭记忆），ReAct 是开卷考试（可以查资料）。

### Q3：为什么 Action Input 要求 JSON 格式？

两个原因：

1. **解析确定性**：JSON 有明确的起始标记 `{}`，正则 `\{[\s\S]*\}` 能精确提取，不会把后续文字误当参数
2. **结构化参数**：工具需要明确的键值对，JSON 天然支持嵌套、数组、数字类型

```python
# 项目中用两层正则解析：
# 第一层：严格 JSON（花括号包裹）
input_m = re.search(r"Action Input:\s*(\{[\s\S]*\})", text)
# 第二层：宽松兜底（非 JSON 块后的纯文本当作参数）
loose = re.search(r"Action Input:\s*([\s\S]+?)(?=\n\n|\Z)", text)
```

**追问：生产环境怎么改进？**
> 换成 OpenAI function calling 模式。LLM 直接返回 `tool_calls` 数组，参数已经是结构化 JSON，不再需要正则解析。但当前自研方案的好处是不绑定特定 API 格式，任何 LLM 都能用。

### Q6：Planner 如果 plan 阶段就失败了怎么办？

项目有三层降级（[planner.py:128](../../app/core/agent/planner.py#L128)）：

```python
# 第 1 层：plan 生成 JSON 解析失败 → 降级为单步推理

    return [SubTask(id="fallback_1", title="直接回答", action_type="reasoning")]

# 第 2 层：execute 某步失败 → replan 重规划（最多 2 次）
for attempt in range(self.max_replan_attempts + 1):
    res = await self.execute(...)
    if res.success: return res
    current_plan = await self.replan(...)  # LLM 基于已执行结果重新规划

# 第 3 层：replan 也失败 → 编排器降级到 ReAct
if not result.success and self._fallback_on_plan_failure:
    result = await self._run_react(...)  # 兜底
```

## 二、RAG 全链路

### Q7：RAG 的完整流程是什么样的？

```
文档上传 → 解析(PDF/Word/TXT) → 分块(512字/64字重叠)
         → 向量化(Sentence-Transformers 384维)
         → 存入 Milvus Lite + BM25 索引

用户提问 → 向量检索(COSINE 相似度) + BM25 关键词检索
        → RRF 融合(k=60) → 可选重排序(Cross-Encoder)
        → 拼接上下文 → LLM 生成带引用([1][2])的回答
```

---

### Q8：BM25 是什么？项目中怎么实现的？

**一句话**：经典的关键词检索算法，衡量一个词对一篇文档的"重要性"。

**BM25 公式**（[rag_service.py:141](../../app/core/rag_service.py#L141)）：

```
score(d, q) = Σ IDF(t) × (f×(k1+1)) / (f + k1×(1-b + b×dl/avgdl))
               ↑            ↑
           词的重要性    词在该文档中的贡献（含饱和度+长度归一化）
```

**三个参数的含义**：

| 参数 | 默认值 | 直觉解释 |
|------|--------|---------|
| k1=1.5 | 词频饱和度 | 一个词出现 1 次和出现 10 次的差距被压缩——出现太多次不再加分 |
| b=0.75 | 长度归一化 | b 越接近 1，越惩罚长文档——长文档天然词频高，需要"扣分" |
| avgdl | 动态计算 | 所有文档的平均长度，用于归一化 |

**自研 BM25 的关键代码**：

```python
# IDF：逆文档频率
self._idf[t] = math.log(1.0 + (N - df + 0.5) / (df + 0.5))
# 如果某个词只在 1 篇文档出现 → IDF 很大 → 这个词非常重要
# 如果出现在每篇文档 → IDF ≈ 0 → 这个词是噪音（如"的""了"）

# BM25 评分
s += idf * (f * (k1 + 1)) / (f + k1 * (1 - b + b * dl / avgdl))
```

**追问：为什么 BM25 和向量检索一起用？**
> 互补。向量检索能理解语义（"汽车"≈"轿车"），但专有名词（型号、代码）容易模糊。BM25 擅长精确匹配，但理解不了同义词。RRF 融合取长补短。

---

### Q9：RRF 是什么？为什么用它而不是简单加权？

**RRF（Reciprocal Rank Fusion）**：不看绝对分数，只看排名。

```python
# 核心公式（rag_service.py:338）
rrf_k = 60
for rank, r in enumerate(vec_results):
    scores[r.id] = 1.0 / (rrf_k + rank + 1)    # 向量排第1 → 1/62
for rank, r in enumerate(kw_results):
    scores[r.id] += 1.0 / (rrf_k + rank + 1)   # 关键词排第1 → 也加 1/62
```

**为什么不用简单加权？**

| 方法 | 问题 |
|------|------|
| 分数直接相加 | 向量分数范围是 0~1，BM25 分数可能是 0~50，直接相加会被 BM25 主导 |
| 归一化后相加 | 需要知道全局最大/最小值，且分布可能高度倾斜 |
| **RRF** | 只关心排名，天然无视分数尺度差异 |

**k=60 是什么意思？** 防止排名第一的结果"独裁"。k 越大，排名差距对最终分数影响越小，更公平。k=60 是论文经验值。

---

### Q10：向量检索和关键词检索各有什么优劣势？

| | 向量检索 | BM25 关键词 |
|------|---------|------------|
| 原理 | 语义相似度（COSINE） | 词频统计（IDF×TF） |
| 优势 | "汽车"能找到"轿车" | 精确匹配型号、代码 |
| 劣势 | 专有名词模糊 | 同义词完全找不到 |
| 依赖 | 需要嵌入模型 | 无需 GPU |
| 典型命中 | "怎么保养车辆"→汽车保养文章 | "iPhone 15 Pro Max"→精确产品页 |

**实际例子**：
- 用户搜"Python 爬虫" → BM25 命中标题里有"爬虫"的文档，向量命中讲 requests/BeautifulSoup 的文档
- RRF 融合后两者都有，用户能看到更全面的结果

### Q12：chunk_size 和 chunk_overlap 怎么选？

项目配置（[rag_service.py:477](../../app/core/rag_service.py#L477)）：
```python
self._chunker = DocumentChunker(chunk_size=512, chunk_overlap=64)
# overlap 占比：64/512 = 12.5%
```

| 参数 | 太小 | 太大 |
|------|------|------|
| chunk_size | 信息碎片化，缺乏上下文 | 检索精度下降，噪音多 |
| chunk_overlap | 边界信息丢失（一个句子被切成两半） | 冗余存储，浪费空间 |

512 字约等于 1-2 个段落，是一个"有完整语义的最小单元"。64 字重叠确保被切断的句子至少有 1 个 chunk 是完整的。

### Q13：重排序（Reranker）是干什么的？

**一句话**：粗筛后用更精准但更慢的模型重新排序。

```
粗筛（向量检索）: 召回 20 条 → 快（100ms），但精度一般
精排（Cross-Encoder）: 对 20 条重打分 → 慢（500ms），但精度高
最终返回: top 5
```

**Bi-Encoder vs Cross-Encoder**（[reranker.py](../../app/core/rag/reranker.py)）：

| | Bi-Encoder | Cross-Encoder |
|------|-----------|-------------|
| 做法 | query 和 doc 分别编码再算相似度 | query+doc 一起喂给模型打分 |
| 速度 | 快（doc 向量可预计算缓存） | 慢（每对都要重新算） |
| 精度 | 一般 | 高 |
| 项目中的用途 | 向量检索（粗筛） | 重排序（精排） |

### Q16：三级存储是怎么设计的？为什么这样分层？

**架构**（[persistent_memory.py](../../app/core/persistent_memory.py)）：

```
读取 get_relevant():
```

### Q19：计算器工具怎么保证安全？如果 Agent 想执行 `__import__('os').system('rm -rf /')` 怎么办？

**用 AST 白名单**（[calculator.py:15](../../app/core/tools/builtin/calculator.py#L15)）：

```python
_ALLOWED_OPS = {ast.Add, ast.Sub, ast.Mult, ast.Div, ast.Pow, ast.USub, ast.UAdd, ast.Mod}
# ↑ 只有这 8 种操作符是允许的

def _eval(self, node):
    if isinstance(node, ast.BinOp) and type(node.op) in _ALLOWED_OPS:
        return _ALLOWED_OPS[type(node.op)](left, right)  # 在白名单中→求值
    raise ValueError("不支持的表达式语法")  # 否则直接拒绝
```

`ast.parse(expr)` 把表达式解析成抽象语法树（AST），然后只对白名单操作符求值。`ast.Call`（函数调用）、`ast.Attribute`（属性访问）都不在白名单里，所以 `__import__('os').system(...)` 会被直接拒绝。

### Q20：数据库查询工具怎么防止 SQL 注入？

**双重校验**（[database.py:36](../../app/core/tools/builtin/database.py#L36)）：

```python
def _validate_sql(self, sql):
    # 1. 必须是 SELECT 开头
    if not sql.startswith("select"):
        raise ValueError("仅允许 SELECT 查询")

    # 2. 黑名单关键词
    forbidden = ("insert", "update", "delete", "drop", "alter", "truncate", "create")
    for bad in forbidden:
        if bad in sql:
            raise ValueError(f"查询包含禁止关键字: {bad}")
```

两层防护：白名单（只允许 SELECT）+ 黑名单（禁止危险操作）。即使 Agent 被诱导生成恶意 SQL，也会在 Python 层被拦截。

## 五、模型路由与韧性

### Q21：三态熔断器是什么？项目中怎么实现的？

**类比**：家里的保险丝。电器短路 → 跳闸断电 → 过一会试试能不能合上去。

**三态切换**（[circuit_breaker.py](../../app/infrastructure/llm/circuit_breaker.py)）：

```
CLOSED（正常）  ──失败 5 次──►  OPEN（熔断，拒绝请求）
                                     │
                                 60 秒后
                                     ▼
                              HALF_OPEN（试探，最多 3 次）
                              成功→CLOSED  失败→OPEN
```

**关键代码**：

```python
async def call(self, func, *args, **kwargs):
    async with self._lock:  # 并发安全
        # OPEN → 检查是否过了 60s
        if self._state == CircuitState.OPEN:
            if time.monotonic() - self._last_failure_time >= 60:
                self._state = CircuitState.HALF_OPEN  # 进入试探
            else:
                raise RuntimeError("熔断器拒绝调用")   # 快速失败

        # HALF_OPEN → 限制试探次数 ≤ 3
        if self._state == CircuitState.HALF_OPEN:
            if self._half_open_attempts >= 3:
                raise RuntimeError("试探次数已达上限")
```

**追问：为什么用 `time.monotonic()` 不用 `time.time()`？**
> `time.time()` 可能因为 NTP 时间同步而回退，导致熔断器误判"已经过了 60 秒"。`time.monotonic()` 保证单调递增。

### Q22：多模型路由怎么选择模型？

**优先级 + 同优先级加权随机**（[model_router.py:69](../../app/infrastructure/llm/model_router.py#L69)）：

```python
def _select_candidates(self, model_preference):
    # 1. 按 priority 分组（priority=0 优先于 priority=1）
    by_prio = {}
    for cfg in self._configs:
        by_prio.setdefault(cfg.priority, []).append(cfg)

    # 2. 同优先级内，按 weight 加权随机排序
    for prio in sorted(by_prio.keys()):
        scored = [(cfg, random.random() ** (1.0 / max(cfg.weight, 0.01)))
                  for cfg in group]
        scored.sort(key=lambda x: -x[1])  # weight 越大越靠前
```

**算法的直觉解释**：
- `random.random()` 生成 0~1 的随机数
- `** (1.0/weight)` → weight=3 时取 1/3 次方 → 0.7^(0.33)=0.89，很大概率排前面
- weight=0.5 时取 1/0.5=2 次方 → 0.7^2=0.49，大概率靠后

**追问：每个模型挂了怎么办？**
> 每个模型有独立熔断器。A 挂了被熔断 → 自动跳到 B → B 也挂了跳到 C。全挂才抛异常。

---

### Q23：为什么每个模型要有独立的熔断器？

```python
# model_router.py:56 — 每个模型一个 CircuitBreaker 实例
self._breakers[cfg.model_id] = CircuitBreaker(
    failure_threshold=failure_threshold,
    recovery_timeout=recovery_timeout,
    name=f"llm:{cfg.model_id}",  # 不同的名字
)
```

因为 A 挂了不等于 B 挂了。如果共享熔断器，一个模型出问题会导致所有模型都被熔断。独立熔断器让故障隔离——DeepSeek 挂了不影响 OpenAI，反之亦然。

## 六、意图识别与反思

### Q24：意图识别是怎么做的？

**三层意图树 + 关键词匹配**（[recognizer.py](../../app/core/intent/recognizer.py)）：

```
问答
  ├── 知识问答 ← "什么""为什么""如何"
  └── 闲聊     ← "你好""谢谢"
任务
  ├── 搜索     ← "搜索""查一下"
  ├── 计算     ← "计算""等于"
  └── 数据库   ← "sql""查询"
文档
  ├── 上传     ← "上传""pdf"
  └── 总结     ← "总结""摘要"
```

```python
# 置信度计算
conf = min(0.95, 0.45 + 0.12 * hits)
# 命中 0 个关键词 → 0.25~0.35（弱规则推断）
# 命中 1 个关键词 → 0.57
# 命中 4 个关键词 → 0.93（接近上限）
```

**追问：当前方案有什么问题？**
> 纯关键词匹配太粗糙。如果用户说"给我讲讲 ML 中的 agent"，ML 可能被理解为"机器学习"而非匹配任何意图。生产环境应该换成 LLM 分类（few-shot）或微调小模型。

### Q25：反思（Reflection）是怎么做的？为什么用独立 LLM 而不是同一个 LLM 自查？

**流程**（[reflection.py](../../app/core/agent/reflection.py)）：

```python
# 1. 给质检 LLM 看原始问题+Agent 的答案+执行轨迹
messages = [
    {"role": "system", "content": "你是严格的输出质量审查员..."},
    {"role": "user", "content": f"问题:{query}\n答案:{answer}\n证据:{evidence}"},
]
# 2. LLM 输出 JSON 审查报告
raw = await self._llm.acomplete(messages, temperature=0.1)
# 3. 返回结构化报告
return ReflectionReport(
    quality_score=score,           # 0-100
    likely_hallucination=bool,     # 疑似幻觉？
    is_complete=bool,              # 回答完整？
    suggestions=[...],            # 改进建议
)
```

**为什么用独立 LLM？** 同样的 LLM 做同样的任务，很难发现自己的错误（类似自己检查作业）。用独立的调用 + 更低的 temperature + 不同的 prompt 角色，相当于「换一个人来审查」。

**追问：当前反思有什么不足？**
> 反思结果只是"打分"，没有反馈给 Agent 重新生成。真正的 Reflexion 模式应该：quality < 阈值 → 把 suggestions 注入 Agent 的 system prompt → 重新生成。

### Q27：为什么要用 Protocol（协议）而不是 ABC（抽象基类）？

```python
# Protocol：只要对象有这个方法就行，不需要"继承"
class LLMCallable(Protocol):
    async def acomplete(self, messages, **kwargs) -> str: ...

# 任何有这个方法的对象都能传进去，不需要显式继承 LLMCallable
agent = ReActAgent(llm=my_llm_object, ...)
```

**Protocol vs ABC 的区别**：

| | Protocol（结构化子类型） | ABC（名义子类型） |
|------|------------------------|------------------|
| 关系 | 有这个方法就算 | 必须显式继承 |
| 耦合 | 松（不依赖具体类） | 紧（依赖继承关系） |
| 适用场景 | 跨模块、跨项目接口 | 同一模块内的继承体系 |

项目中编排器定义 Protocol，让基础设施层任何实现都能直接插入——这才是真正的"依赖反转"。

### Q29：为什么 MemoryLike、LLMCallable、ToolInvoker 都用 Protocol 而不是具体类？

因为 ReAct Agent 不需要知道「记忆存在 Redis 还是 PostgreSQL」「LLM 是 OpenAI 还是 DeepSeek」「工具是怎么实现的」。它只需要知道：

```python
class MemoryLike(Protocol):
    async def get_relevant(self, session_id, query, limit) -> List[str]: ...
    async def append_turn(self, session_id, role, content, metadata) -> None: ...
```

**好处**：
1. **可测试**：写单元测试时，传一个假的 MemoryLike 对象就行
2. **可替换**：把 Redis 换成 MongoDB，ReAct 代码一行不改
3. **边界清晰**：一眼就知道 Agent 依赖什么

## 八、开放性问题

### Q31：这个项目最大的技术亮点是什么？

**三个最突出的亮点**：

1. **ReAct 自研实现**：没用 LangChain 封装，从 prompt 设计到正则解析全手写，展示了对 Agent 底层的真正理解
2. **三级记忆降级**：Redis → PG → 内存，每层独立 work，核心代码不到 300 行
3. **三态熔断器**：128 行实现经典设计模式，`asyncio.Lock` + `time.monotonic()` 细节到位

---

### Q32：这个项目最大的短板是什么？

**三个最明显的短板**：

1. **单 Agent 架构**：没有多 Agent 协作，面试高频话题覆盖不到
2. **传统 Function Calling**：工具硬编码在代码里，没有 MCP 协议支持
3. **意图识别粗糙**：纯关键词匹配，生产环境完全不够用

**追问：怎么改进？**

> 1. 多 Agent：用 LangGraph 的 StateGraph 建 Boss-Worker 模式
> 2. MCP：把现有工具封装成 MCP Server，Agent 通过 JSON-RPC 动态发现
> 3. 意图识别：换成 LLM few-shot 分类或微调小模型
