# 项目目录结构与工作流（规范评估 + 逐文件说明）

> 本文档回答两个问题：**当前目录设置是否规范？** 以及 **每个文件/目录是干什么的、项目完整工作流是怎样的？**
> 配合阅读：[项目全景文档](项目全景文档.md)、[项目工作流程举例](项目工作流程举例.md)、[源项目结构与本地增量对比](源项目结构与本地增量对比.md)。

## 0. 规范度评估（结论先行）

**总体判断：结构规范，属于标准的 FastAPI + 前后端分离工程布局，可以直接拿到面试上讲；有 5 处"规范度瑕疵"建议面试前处理。**

### 做得规范的地方

| 方面 | 说明 |
|---|---|
| 分层清晰 | `api`（接口）→ `core`（业务）→ `infrastructure`（基础设施）→ `models`（数据模型）→ `etl`（数据管道），单向依赖、可替换实现 |
| 测试独立 | `tests/` 与源码分离，`conftest.py` 保证离线可跑 |
| 工程目录齐全 | `scripts/`（评估与工具）、`.github/workflows/`（CI）、`docs/`（文档）、`frontend/`（前端） |
| 配置管理规范 | 敏感配置走 `.env`（已被 `.gitignore` 忽略），只提交 `.env.example` 模板 |
| 容器化 | `Dockerfile` + `docker-compose.yml` 一键拉起全栈 |
| 前端自成一体 | `frontend/` 内部遵循 Vite 标准结构（src/api、src/components、src/pages、src/types） |

### 建议改进的 5 处

| # | 问题 | 位置 | 建议 |
|---|---|---|---|
| 1 | **运行时数据进了 git**：Milvus Lite 向量库（`milvus.db/`、`milvus_eval.db/`）和上传文档（`uploads/`）被提交跟踪，属于运行产物，不应入库 | 仓库根 | 加入 `.gitignore` 并从 git 跟踪中移除（`git rm -r --cached`）；保留文件本身即可运行 |
| 2 | **残留骨架命名**：`enterprise-ai-agent` 出现在 `pyproject.toml`、`app/config.py`、`docker-compose.yml` 容器名、`.env.example` | 多处 | 统一改为 `xinkang` / `心康助手` |
| 3 | **docs 文件平铺且命名重叠**：17 份文档直接堆在 `docs/` 下，"详解/解析/深度解析"语义重复 | `docs/` | 按 `面试/`、`机制解析/`、`教程/`、`报告/` 分子目录（`docs/面试/` 已经是好示范） |
| 4 | **大量改动未提交**：`tests/`、`scripts/`、`.github/`、README、新模块、17 份文档都是未跟踪状态，git 历史与代码现状不一致 | 仓库根 | 整理成 1～2 个有意义的 commit（如"工程化：测试/评估/CI/文档"） |
| 5 | **core 根部的服务文件与子包并存**：`agent_service.py`、`rag_service.py`、`persistent_memory.py`、`session_repository.py` 放在 `core/` 根，而 `agent/`、`rag/`、`memory/` 是子包 | `app/core/` | 可接受（体现"装配层"职责），也可归入 `core/services/`；二选一即可，不要两种混着来 |

> 另外：`frontend/node_modules` 当前处于半删除状态（清理目录时被进程占用中断），启动前端前需先执行 `npm install`。

## 3. 后端 `app/` 逐文件说明

```
app/
├── main.py                    # FastAPI 入口
├── config.py                  # pydantic-settings 配置
├── api/routes/                # HTTP 路由层
├── core/                      # 业务核心（Agent/RAG/记忆/工具/意图）
├── etl/                       # 文档解析/分块/入库流水线
├── infrastructure/            # 基础设施封装（LLM/向量库/缓存/DB/追踪）
└── models/                    # 数据模型
```

### 3.1 入口与配置

| 文件 | 作用 |
|---|---|
| `main.py` | 创建 FastAPI 应用：lifespan 中初始化数据库引擎并自动建表（开发环境）、注册 CORS、挂载 chat/document/health/sessions 四个路由 |
| `config.py` | `Settings` 类集中管理全部配置：服务名/环境、OpenAI、PG、Redis、Milvus Lite 路径与集合名、SerpAPI、HF 镜像、日志级别；`get_settings()` 带缓存 |

### 3.2 API 路由层 `api/routes/`

| 文件 | 作用 | 关键接口 |
|---|---|---|
| `chat.py` | 对话主路由（320 行） | `POST /chat`（直连 LLM）、`POST /chat/stream`（SSE 流式）、`POST /chat/agent`（AgentService 完整编排）、`POST /chat/rag`（混合 RAG 问答）、RAG 文档上传/状态/列表/删除、`POST /chat/rag/search-compare`（四种检索方式对比） |
| `document.py` | 文档上传/列表 | `POST /documents`、`GET /documents` |
| `health.py` | 健康检查 | `GET /health` |
| `sessions.py` | 会话管理 | `GET /sessions`、`GET /sessions/{id}`、`DELETE /sessions/{id}` |

### 3.3 业务核心 `core/`

**服务/装配层（core 根部）**

| 文件 | 作用 |
|---|---|
| `agent_service.py` | **总装配层**：先读取会话记忆（方案 A：记忆前置），再按 意图识别(带历史) → 模式路由(带历史) → 编排(ReAct/Plan 循环内调工具+反思) → 写记忆 串成可调用链路；懒加载单例；RAG 不可用时降级，Agent 仍可工作 |
| `rag_service.py` | **混合 RAG 服务**：Milvus Lite 存储 + jieba BM25 + 向量双路召回 + RRF 融合 + 可选 CrossEncoder 重排 + 带引用生成 + 文档摄入/删除 + 内存向量库兜底；含 `_rebuild_bm25()`（重启后重建索引） |
| `persistent_memory.py` | **三层记忆管理器**：Redis 短期（滑动窗口+摘要压缩）→ PG 会话持久化 → Milvus 长期语义；统一暴露 `get_relevant` / `append_turn` |
| `session_repository.py` | SQLAlchemy 2.0 异步会话 CRUD：会话创建/列表/详情/删除、消息追加与历史读取 |

**Agent 子包 `core/agent/`**

| 文件 | 作用 |
|---|---|
| `mode_router.py` | 模式路由：规则快路径（高置信度直接映射）→ LLM Router（模糊场景二次判断）→ fallback（react 兜底）；支持 react / plan_execute / function_call 三种模式 |
| `orchestrator.py` | 编排器：按意图/模式选择 ReAct 或 Plan-Execute，Plan 失败自动降级 ReAct；串联记忆、工具、追踪、反思 |
| `react_agent.py` | 自研 ReAct 循环：Thought → Action → Observation，正则解析模型输出，步数上限、记忆注入、trace 回调 |
| `planner.py` | 规划 Agent：任务分解为子任务（JSON），逐步执行，失败重规划 |
| `reflection.py` | 反思 Agent：对回答做质量评分、幻觉/完整性检查，产出改进建议 |
| `function_call_agent.py` | 基于 LangChain `bind_tools()` 的 Function Calling Agent：结构化工具调用，与自研 ReAct 对照 |
| `langgraph_agent.py` | 基于 LangGraph `StateGraph` 的 ReAct：agent → tools → evaluator 循环，质量不达标带反馈重试 |

**意图识别**

| 文件 | 作用 |
|---|---|
| `core/intent/recognizer.py` | 意图识别：关键词规则 + LLM 双通道；高置信度走规则快路径，低置信度走 LLM 分类；JSON 容错提取；输出意图/置信度/槽位/澄清建议 |

**记忆子包 `core/memory/`**

| 文件 | 作用 |
|---|---|
| `short_term.py` | 短期记忆：Redis 滑动窗口 + 超量 LLM 摘要压缩；实现 `MemoryLike` 协议供 ReAct 调用 |
| `long_term.py` | 长期记忆：Milvus 向量检索跨会话召回 |
| `manager.py` | 记忆管理器：组合短期 + 长期记忆 |

**RAG 子包 `core/rag/`**

| 文件 | 作用 |
|---|---|
| `retriever.py` | MultiRetriever：向量（Milvus）+ BM25 关键词（jieba）双路召回，RRF 融合 |
| `reranker.py` | CrossEncoder 精排 |
| `generator.py` | 基于检索上下文的答案生成（含引用标注） |

**工具子包 `core/tools/`**

| 文件 | 作用 |
|---|---|
| `base.py` | `BaseTool` / `ToolParameter` 基类，定义工具接口 |
| `registry.py` | 工具注册表：注册、列举、按名调用 |
| `router.py` | 工具路由 |
| `builtin/calculator.py` | 计算器工具 |
| `builtin/database.py` | 数据库查询工具 |
| `builtin/search.py` | Web 搜索：SerpAPI（有 Key）+ DuckDuckGo（降级）双通道 |
| `builtin/rag_search.py` | RAG 检索工具：让 Agent 在 ReAct 循环中自主查询知识库 |

### 3.4 ETL `etl/`

| 文件 | 作用 |
|---|---|
| `parser.py` | 文档解析（PDF 等非结构化 → 文本） |
| `chunker.py` | 分块：fixed / recursive / paragraph / langchain 四种策略 |
| `pipeline.py` | ETL 流水线：解析 → 分块 → 向量化 → 入库 |

### 3.5 基础设施 `infrastructure/`

| 文件 | 作用 |
|---|---|
| `llm/model_router.py` | 多模型路由：按优先级/权重选择模型，支持回退 |
| `llm/circuit_breaker.py` | 三态熔断器（关/开/半开），LLM 调用失败快速失败保护 |
| `llm/types.py` | LLM 相关类型定义 |
| `vectordb/milvus_client.py` | Milvus 客户端封装 |
| `cache/redis_cache.py` | Redis 缓存封装 |
| `database/models.py` | SQLAlchemy 表模型（会话、消息等） |
| `database/session.py` | 异步数据库引擎与会话管理 |
| `trace/tracer.py` | 链路追踪：trace_id、span、事件日志 |

### 3.6 数据模型 `models/`

| 文件 | 作用 |
|---|---|
| `enums.py` | 枚举（MessageRole、AgentMode 等） |
| `schemas.py` | Pydantic 请求/响应模型：Chat/Agent/RAG/文档/记忆/检索/引用/步骤追踪等 |

## 7. 工作流

### 7.1 环境准备（一次性）

```powershell
# 1) Python 环境（本机为 conda env myAgent，Python 3.12）
conda activate myAgent
pip install -r requirements.txt

# 2) 前端依赖（注意：node_modules 当前半删，必须先装）
cd frontend
npm install
cd ..

# 3) 配置
copy .env.example .env      # 填写 OPENAI_API_KEY（可选 SERPAPI_API_KEY）

# 注意：若系统存在用户级 DEBUG=release，需覆盖为合法布尔值
$env:DEBUG = "false"
```

### 7.2 开发运行（日常）

```powershell
# 后端（8000 端口）
python -m uvicorn app.main:app --reload --port 8000

# 前端（5173 端口，另开一个终端）
cd frontend && npm run dev
```

启动顺序与依赖：

```
用户 → 前端(5173) → 后端(8000) → AgentService → 编排器 → 工具/记忆/RAG
                                    │
                                    ├─ Milvus Lite（本地文件 milvus.db，免 Docker）
                                    ├─ Redis（短期记忆；未启动则降级）
                                    └─ PostgreSQL（会话持久化；未启动则降级内存）
```

### 7.3 功能使用流程

**知识库问答（RAG）**

1. 前端"文档"页上传 PDF（或 `POST /api/v1/chat/rag/ingest`）
2. 后端解析 → 分块 → 向量化 → 写入 Milvus Lite（`milvus.db`）
3. 用户在对话页提问 → `/chat/rag`：BM25 + 向量双路召回 → RRF 融合 →（可选）重排 → 生成带引用的答案
4. "检索对比"面板可同时看 vector / keyword / hybrid / hybrid+rerank 四种结果

**Agent 对话**

1. 用户提问 → 读取会话历史（记忆前置，方案 A：多轮上下文注入）
2. 意图识别（规则快路径或 LLM 通道，结合历史消解追问/指代）
3. 模式路由选 react / plan_execute（LLM Router 可结合历史；function_call 是 ReAct 内部的工具调用后端）
4. 编排器执行：ReAct 循环中自主调用 `rag_search` / `web_search` / `calculator` 等工具
5. 每步 Thought/Action/Observation 写入 trace，前端右侧实时展示
6. 回答后反思 Agent 做质量检查；对话写入三层记忆（Redis → PG → Milvus）

### 7.4 测试工作流

```powershell
# 全部测试（67 例，离线）
scripts\run_tests.ps1
# 或
python -m pytest
```

### 7.5 评估工作流

```powershell
# 1) 准备知识库（Web UI 上传或 ingest API），准备标注查询
# 2) 跑各组实验
python scripts/eval_full_kb.py        # 全知识库旗舰实验
python scripts/eval_real_doc.py       # 单篇真实指南
python scripts/eval_rag_standalone.py # 零依赖合成语料回归
python scripts/eval_rag.py            # 连接真实 RAGService 管线
# 3) 查看 scripts/eval_report*.md，汇总进 docs/评估报告-混合检索.md
```

> 注意：评估用 `milvus_eval.db` 隔离，不污染主库 `milvus.db`；运行需 `DEBUG=false`。

## 8. 整理建议清单（按优先级）

1. **修复前端**：`cd frontend && npm install`（node_modules 半删状态）

5. **docs 分目录**：面试 / 机制解析 / 教程 / 报告
