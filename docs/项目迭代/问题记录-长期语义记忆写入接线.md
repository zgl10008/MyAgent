# 问题记录：长期语义记忆（Milvus）写入未接线

> 记录日期：2026-08-11
> 涉及模块：`app/core/persistent_memory.py`、`app/core/memory/long_term.py`
> 状态：已修复并补充回归测试

---

## 一、问题

项目的三层记忆中，长期语义记忆基于 Milvus 向量库：读取侧（`recall`）已在
`get_relevant` 里接通（召回结果以 `[历史记忆]` 前缀叠加到短期记忆前面），
但**写入侧（`store`）从未被任何调用点调用**——每条新对话只写入了
Redis / PostgreSQL / 内存，Milvus 里永远是空的。

后果：语义召回永远召回不到内容，"很久以前但和当前问题语义相关"的记忆无法生效，
长期语义记忆名存实亡。

---

## 二、定位过程

全项目检索 `store(` 调用点：

- `LongTermMemory.store` 只被自身定义，无任何生产代码调用；
- `set_long_term` 只注册了读取侧 `_append_long_term`；
- `PersistentMemoryManager.append_turn`（每轮问答的写入入口）没有走语义库。

结论：读写两侧没有对齐——读通了、写没接。

---

## 三、修复内容

在 `app/core/persistent_memory.py` 的 `append_turn` 中新增长期语义记忆写入旁路：

1. `append_turn` 在写完内存 / PG / Redis 后，调用新增的
   `_append_long_term_turn(session_id, role, content, metadata)`；
2. `_append_long_term_turn` 规则：
   - 未注入长期记忆（`_long_term is None`）则直接返回，零开销；
   - 只存非空的 `user` / `assistant` 消息，跳过 `system` 与空内容，避免噪声；
   - 调用 `LongTermMemory.store` 写入向量库；
   - 任何异常只记 warning，不影响 PG / Redis / 内存主流程（延续项目的降级设计）。

这样每轮问答结束后，用户提问和助手回答都会作为语义记忆入库，
读取侧的 `_append_long_term` 就能真正召回历史相关记忆。

---

## 四、测试

新增 `tests/test_persistent_memory.py`（4 个用例）：

- user / assistant 消息均写入长期记忆，且携带元数据；
- system 消息与空内容被过滤；
- Milvus 写入失败不影响主流程（内存兜底仍可读）；
- 未注入长期记忆时保持原行为。

---

## 五、验证

- 完整测试套件：通过（78 passed）。

---

## 六、遗留与后续建议

1. 当前是"每轮全量写入"，可加重要度筛选（如健康关键词、长度阈值）减少噪声；
2. 写入是同步等待 embedding + 入库，可考虑异步化或批量写入降低单轮延迟；
3. Milvus 的 `store` 用 `asyncio.to_thread` 执行同步客户端调用，高频场景
   可改用 pymilvus 异步接口。
