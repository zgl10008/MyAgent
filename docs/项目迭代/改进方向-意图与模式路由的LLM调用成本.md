# 改进方向：意图识别与模式路由的 LLM 调用成本（面试可讲）

> 本文档记录一次面试向的技术质疑及其评估结论：
> **"意图识别（闲聊/知识问答/任务执行）本身就是路由的依据，拆成两步会多一次 LLM 调用，增加延迟和成本。"**
> 结论：**方向对了一半，但说法过于简化**——真实实现只在低置信度分支多一次调用，且意图不是路由的充分依据。
> 关联文档：[改进方向-多轮上下文意图路由](改进方向-多轮上下文意图路由.md)。

---

## 1. 质疑内容

> 意图识别（闲聊/知识问答/任务执行）本身就是路由的依据。拆成两步会多一次 LLM 调用，增加延迟和成本。

拆解为两个断言：

1. **意图识别结果足以决定路由**（断言 A）
2. **意图 + 路由两步总是产生两次 LLM 调用**（断言 B）

---

## 2. 代码事实核查（断言 B 只对一半）

当前实现（`app/core/agent_service.py` → `app/core/intent/recognizer.py` → `app/core/agent/mode_router.py`）：

| 场景 | 意图识别 | 模式路由 | LLM 调用次数 |
|---|---|---|---|
| 意图命中规则表且置信度高（如"帮我算 1+1"→ 数学计算 0.95） | LLM 分类 1 次 | 规则快路径命中，**不调 LLM** | 1 次 |
| 意图不在规则表 / 置信度 < 0.50 / 低于意图阈值（如"那它呢？"） | LLM 分类 1 次 | LLM Router 1 次 | **2 次** |
| LLM 不可用（离线/降级） | 关键词规则 | 规则快路径 | 0 次 |

关键代码行为：

- `ModeRouter._rule_resolve()`：意图在映射表且置信度达标 → 直接返回模式，**不触发 LLM**
- LLM Router 仅在规则未命中、置信度低于 0.50 地板、或低于意图阈值（数学计算/实时搜索需 ≥0.70）时触发
- 也就是说，"多一次 LLM 调用"只在**模糊/低置信度分支**成立——该分支本就值得多花一次推理

**结论：断言 B 不成立**——不是每次对话都付两次调用的代价，规则快路径已短路大部分常见请求。

---

## 3. 意图是不是路由的充分依据？（断言 A 也不成立）

路由规则表确实是 `意图 → 模式` 映射，但**模式选择还依赖三类意图之外的信息**：

| 信息 | 例子（当前代码） |
|---|---|
| 查询本身的特征 | 同为"知识问答"，含"最新/2026/实时" → 规则升级为 plan_execute（时间敏感性）；"高血压的诊断标准" → 保持 react |
| 任务复杂度 | 需要 搜索→筛选→整合 的多步任务 → plan_execute；单步概念问答 → react |
| 工具可用性 | 路由感知 `rag_search` 等工具是否注册（`ModeRouter._tool_names`），有知识库时同意图可走不同工具组合 |

若把模式选择并进意图分类，等于让一个分类器同时优化两个目标：
标签空间从 5 类意图变成 `5 × 2` 组合，提示词与评测都更难稳定。

拆分的工程收益（也是保留现状的理由）：

- **单一职责**：意图分类只管"用户想干什么"，路由只管"用哪种执行范式"
- **可独立评测**：意图准确率、路由决策准确率分开度量，出错好定位
- **可独立降级**：意图规则兜底、路由规则兜底互不牵连，离线也能跑

## 4. 改进方向（按优先级，暂未实施）

### 方向 1：意图识别改为"规则优先、LLM 兜底"（成本最大优化点）

现状：配置 LLM 后意图识别**永远先调 LLM**，清晰场景也付一次调用。

改法：

```python
# 伪代码：规则快路径先跑，只有模糊/低置信度才升级 LLM
intent, conf = keyword_classify(query)
if conf >= threshold and intent in RULE_CONFIDENCE_MAP:
    return intent            # 0 次 LLM 调用
return await llm_classify(query)   # 仅模糊场景
```

收益：大部分完整单轮问题 **0 次 LLM 调用**；LLM 只服务真正需要它的场景。
这与骨架最初"关键词规则 + 澄清引导"的设计一致，当前改成了 LLM 优先反而把快路径调慢了。

### 方向 2：低置信度场景"一次 LLM 输出意图 + 模式"（合并调用）

只合并模糊分支，不合并整体：

```json
{"intent": "知识问答", "mode": "react", "slots": {}, "rationale": "..."}
```

把原本的"意图 1 次 + 路由 1 次"压成 **1 次**。
清晰场景仍然走规则快路径，0~1 次调用。
代价：该分支的单一职责被合并，出错定位不如拆分直观——所以只在模糊分支合并是折中。

### 方向 3：收紧 LLM Router 触发条件

- 置信度下限从 0.50 提高到 0.60
- 对"闲聊/文档管理"这类低风险意图用规则定死，不给二次调用机会
- 对"数学计算/实时搜索"维持较高阈值（0.70）不变

收益：减少模糊分支触发率；代价：低置信但特殊的请求可能路由不准，需回归测试兜底。

### 优先级建议

```
方向 1（规则优先） > 方向 2（模糊分支合并） > 方向 3（收紧阈值）
```

方向 1 收益最大且改动最小（只动 `recognizer.py` 的调用顺序）；
方向 2、3 都应在评估脚本（`scripts/eval_rag.py` 等）之外补充路由准确率的小样本回归。

## 5. 面试话术

**被质疑"拆两步多一次 LLM 调用"时的回应**：

> 您说的成本问题确实存在，但只在低置信度分支成立——规则快路径已经短路了大部分请求，并不是每次都两次调用。不过这也提醒我两个优化点：一是意图识别可以改回"规则优先、LLM 兜底"，清晰场景零调用；二是路由只在模糊场景用一次 LLM 同时输出意图和模式，把两次压成一次。我目前的拆分是为了单一职责和可独立降级，评测上也更容易定位是哪一环出错。

**回答要点**：

1. 承认成本问题（不抬杠），但用代码事实限定范围：只有低置信度/不在规则表的分支是 2 次
2. 说明意图不是路由的充分依据：时间敏感、任务复杂度、工具可用性都影响模式选择
3. 给出量化优化路径：规则优先 → 模糊分支合并 → 收紧阈值
