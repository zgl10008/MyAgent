# 改进方向：意图识别与模式路由的多轮上下文（面试可讲）

> 本文档记录"意图识别 / 模式路由如何使用对话历史"的现状与演进方案。
> **方案 A 已实现**；方案 B/C/D 是记录在案的改进方向，面试时可主动讲"已实现 + 演进路径"。
>
> 2026-08-10 补充：方案 A 落地时曾遗漏 FunctionCall 后端的记忆注入（多轮上下文丢失），
> 已修复并补回归测试，详见 [问题记录-多轮对话上下文丢失](问题记录-多轮对话上下文丢失.md)。

---

## 1. 问题背景

最初的链路是纯单轮的：

```
意图识别（只看当前 query） → 模式路由（只看当前 query + 意图标签） → 编排器
```

多轮追问（"那它呢？""还有吗？""这个药呢？"）中的指代和省略无法消解，意图与模式容易判错。
而记忆原本只在编排器内部的 ReAct 循环里读取，意图识别和模式路由拿不到历史。

---

## 2. 方案 A（已实现）：记忆前置 + 上下文注入

### 改动内容

1. **`app/core/agent_service.py`**（请求入口）：
   在意图识别之前读取会话历史：
   ```python
   history = await self._memory.get_relevant(session_id, user_text, limit=6)
   ```
   失败则按单轮处理（`try/except` 降级），不影响主流程。
2. **`app/core/intent/recognizer.py`**：
   `recognize(query, context={"history": [...]})` 把历史拼进 LLM 分类提示词；
   提示词新增"多轮规则"：追问/指代必须结合历史推断真实意图。
3. **`app/core/agent/mode_router.py`**：
   `resolve(query, intent_result, history=...)` 把历史拼进 LLM Router 提示词；
   提示词新增决策原则 4：追问场景结合历史判断任务后再选模式。

### 改进后的链路

```
读记忆 → 意图识别(带历史) → 模式路由(带历史) → 编排(ReAct/Plan 内调工具+反思) → 写记忆
```

### 验证

- 新增 5 个单元测试：意图识别历史注入 2 例、模式路由历史注入 2 例、规则快路径不受影响 1 例
- 测试总数 62 → **67**，全部离线通过
- 历史读取失败、LLM 不可用等场景均有降级路径，不影响单轮请求

### 已知代价（引出方案 B）

方案 A 对**每一次请求**都读记忆并注入，即使问题本身完整单轮（如"什么是高血压？"）也如此——
多了一次记忆检索 + 更多 token。需要按需注入。

## 3. 方案 B（推荐下一步）：触发式上下文注入

核心思想：**只有"看起来像追问/指代"的请求才注入历史**，其余保持单轮零开销。

```
用户 query
  ├─ 含指代词/省略特征？ ──是──→ 读最近 N 轮历史 → 意图识别(带历史) → 模式路由(带历史)
  └─ 否（完整单轮问题） ────→ 意图识别(单轮) → 模式路由(单轮)   ← 零额外开销
```

### 触发判定（规则草案）

- 指代词表：`它、这个、那个、这药、那药、这些、那些、上面、刚才`
- 省略/延续特征：以 `那、然后、还有、再、继续、所以` 开头的疑问
- 短 query（如 ≤ 6 字且含指代词）→ 高概率追问，必须注入
- 命中后历史窗口取最近 3~5 轮（或 LLM 压缩摘要），避免 token 膨胀

### 收益

- 多数请求保持单轮：无额外记忆检索、无历史 token、延迟更低
- 追问场景获得正确上下文，多轮体验质变

### 实现位置（预估）

- `agent_service.py`：新增 `_needs_context(query)` 判定；命中才读记忆
- `recognizer.py` / `mode_router.py`：方案 A 的 `history` 参数已就绪，**零改动直接复用**

## 4. 方案 C（更完整）：请求级会话上下文对象

定义统一对象：

```python
@dataclass
class ConversationContext:
    session_id: str
    recent_messages: list[Message]      # 最近几轮
    summary: str | None                 # 长会话的 LLM 摘要
    profile: dict | None                # 用户画像/健康档案（可选）
```

在 API 入口统一装配一次，注入意图识别、模式路由、编排器，甚至 RAG 查询改写。

- 收益：各环节上下文一致、可缓存、便于加用户画像
- 代价：重构面大，涉及请求模型与多个模块签名

---

## 5. 方案 D（分层记忆）

不同环节消费不同粒度的记忆：

| 环节 | 记忆粒度 | 理由 |
|---|---|---|
| 意图识别 / 模式路由 | 最近 3~5 轮或压缩摘要 | 只需"知道在聊什么"即可消解指代 |
| ReAct 编排 | 全量相关记忆（`get_relevant`） | 需要完整事实支撑回答 |
| RAG 查询改写 | 当前轮 + 上一轮 | 补全省略的检索词 |

避免让路由层背上全量历史的 token/延迟成本。

## 6. 面试话术

**主动讲法（推荐）**：

> 我实现的编排链路里，意图识别和模式路由最初是单轮的。我识别到这个边界后做了方案 A：在请求入口先读取会话记忆，把历史注入意图识别和模式路由的提示词，多轮追问和指代就能消解了。同时我保留了降级路径——记忆读取失败或 LLM 不可用时，自动回退到单轮关键词。更进一步，我计划做触发式注入：只有检测到指代词或省略的请求才带历史，其余保持单轮零开销，避免每次都多一次检索和 token 消耗。

**被追问"多轮对话怎么处理"时的回答要点**：

1. 现状：方案 A 已落地（记忆前置 + 历史注入 LLM 通道），有 5 个相关单测
2. 降级：规则关键词通道仍可单轮兜底
3. 演进：方案 B 触发式注入（指代词判定）→ 方案 C 会话上下文对象 → 方案 D 分层记忆
