## 1. 源仓库整体结构

源仓库 `bcefghj/ai-agent-interview-guide` 是一个"AI Agent 面试全攻略"项目，包含面试资料和三种语言的可运行骨架：

```
ai-agent-interview-guide/
├── README.md              # 总览
├── LICENSE                # MIT
├── comics/                # 6 张 Agent 概念漫画（什么是 Agent、ReAct、RAG、多 Agent…）
├── docs/                  # 面试资料：八股文、企业招聘分析、STAR 话术、面试问答集等
├── project-go/            # Go 版 Agent 骨架（cmd/server + internal/{agent,rag,memory,tool,…}）
├── project-java/          # Java 版 Agent 骨架（Spring Boot + Milvus + Redis + PG）
└── project-python/        # Python 版 Agent 骨架（本项目的前身）
```

三个语言版本**功能等价**，都覆盖：Agent 编排（ReAct / Plan-and-Execute / Reflection）、意图识别、记忆、RAG、工具、LLM 路由与熔断、ETL、向量库与缓存。本地仓库只保留了 Python 版，删掉了 Go / Java 与原面试资料/漫画。

### 骨架各模块的实际状态

| 模块 | 骨架状态 | 说明 |
|---|---|---|
| `api/routes/chat.py` | **占位** | 直连 OpenAI 模型，未调用编排器/记忆/RAG；意图识别只产出标签 + 澄清提示 |
| `api/routes/document.py` | 基础 | 文档上传接口，未接 ETL/RAG 入库链路 |
| `core/agent/*` | **参考实现，未接线** | ReAct/Planner/Reflection/Orchestrator 均有完整代码，但没有任何路由调用它们 |
| `core/memory/*` | 参考实现，未接线 | short_term（Redis+压缩）、long_term（Milvus）独立可用，但对话链路不用记忆 |
| `core/rag/*` | 参考实现，未接线 | MultiRetriever 有向量+BM25+RRF，但没有服务层、没有上传→入库闭环、没有对话接口 |
| `core/intent/recognizer.py` | 简易实现 | 仅关键词规则，无 LLM 通道 |
| `core/tools/builtin/search.py` | 占位级 | DuckDuckGo HTML 抓取后直接截断返回原始片段 |
| `infrastructure/*` | 可用 | LLM 路由、熔断、Milvus 客户端、Redis、PG session、Trace 均为封装 |
| `etl/*` | 可用 | 解析/分块/流水线独立存在 |
| 前端 / 测试 / CI / 评估 | **完全没有** | 骨架无任何前端、无单元测试、无 CI、无评估脚本 |

一句话总结骨架：**"零件齐全但没有组装"**——各组件能独立运行，HTTP 层却只暴露了直连模型的最小对话接口。

## 6. 核心增量详解

### 6.1 API 层：从"直连模型"到"完整 Agent 平台"

骨架的 `/chat` 是"LLM 直连 + 一个意图标签"。本地把它扩展成 4 组能力：

- `/chat/agent`：走 AgentService，返回意图、模式、步骤追踪（Thought/Action/Observation）、反思报告
- `/chat/rag`：走混合 RAG，返回答案 + 引用片段
- `/chat/rag/search-compare`：同一查询分别跑 vector / keyword / hybrid / hybrid+rerank，前端可视化对比（也是评估的对外窗口）
- `/sessions`：会话创建、列表、详情、删除，配合 PG 持久化

入口 `main.py` 额外补了 CORS（对接前端）和启动自动建表（开发环境免手工 SQL）。

### 6.2 Agent 编排层：把"零件"组装成"整机"

骨架的编排器/ReAct/Planner/Reflection 是独立模块，没有任何调用方。本地新增：

1. **AgentService（总装配）**：路由层只依赖它；它负责构造模型路由器适配、工具注册表适配、注入记忆与 RAG，并在初始化失败时降级（RAG 不可用则 Agent 仍可对话）。
2. **模式路由**：意图识别结果 → 模式选择。高置信度直接映射（如"计算"→ react + calculator），模糊场景用 LLM 判断，失败兜底 react。
3. **两类新 Agent 实现**：FunctionCall Agent（结构化工具调用）和 LangGraph Agent（状态图 + 质量评估重试），与自研 ReAct 形成三种实现对照——面试时是很好的"框架理解深度"展示点。
4. **工具化 RAG**：`rag_search` 工具让 Agent 自己决定何时检索知识库，而不是把 RAG 固定绑在某个接口上。

### 6.3 混合 RAG：从"有检索器"到"可服务、可评估"

骨架的 `MultiRetriever` 只有检索能力。本地新增 `RAGService` 补齐完整闭环：

- **存储**：Milvus Lite 本地文件库（免 Docker，开箱即用），另有内存向量库兜底
- **检索**：jieba BM25 关键词 + 向量（sentence-transformers）双路召回 → RRF 融合 → 可选 CrossEncoder 精排

## 7. 修复的两个真实问题（面试亮点）

评估过程中发现并修复了两个真实缺陷：

**① 重启后 BM25 索引丢失**

- 现象：Milvus 只持久化向量，内存 BM25 索引重启即空，keyword / hybrid 检索**静默退化为纯向量检索**
- 修复：`RAGService` 新增 `_rebuild_bm25()`，启动加载时从 Milvus 查询全部 chunk 重建 BM25 与 source 映射
- 位置：`app/core/rag_service.py`（`_MilvusRAGStore._ensure_loaded` → `_rebuild_bm25`）

**② 中文整段分词导致关键词检索失效**

- 现象：骨架用正则 `[\w\u4e00-\u9fff]+` 切分，"高血压的诊断标准" 会被当成**一个词**，BM25 关键词检索几乎失效
- 修复：`rag_service.py` 与 `retriever.py` 统一改为 **jieba 分词 + 英文正则**，并加入依赖 `jieba>=0.42.1`
- 附带价值：评估脚本与运行时保持同一套分词实现，避免"评测好、线上差"

### 9.3 完整版（1～2 分钟，面试官让你介绍项目时）

> 我介绍的这个项目叫心康助手，是一个面向心血管慢病管理场景的 AI Agent 平台。它的定位是：既是一个可运行的健康咨询 Agent 应用，也是一套可评估、可测试、可讲解的 Agent 工程化项目。
>
> 首先说明它的来源：项目基于一个 MIT 开源的 Agent 骨架起步。那个骨架本身只是"可运行的最小接口"——对话接口直接连模型，里面虽然有 ReAct、Planner、反思、记忆、检索这些参考组件，但都是独立模块，没有任何接口调用它们。相当于提供了零件，但没有组装。我的工作就是把它从"零件"组装成"整机"，并做了大量扩展。
>
> 第一块是 Agent 编排链路。我实现了总装配层 AgentService：先读取会话记忆注入上下文，再把意图识别、模式路由、Agent 编排、工具调用、反思串成一条完整链路，最后写回记忆；并接成真实的 HTTP 接口，支持会话的创建、持久化和多轮上下文理解。意图识别从单纯的关键词规则升级成 LLM 加规则双通道；模式路由支持规则快路径、LLM 二次判断和兜底降级；编排在 Plan 失败时能自动降级到 ReAct。
>
> 第二块是混合 RAG。骨架只有检索器，我把它扩展成完整服务：文档上传、解析分块、向量化入库、jieba BM25 加向量双路召回、RRF 融合、可选 CrossEncoder 重排、带引用的答案生成，并封装成 rag_search 工具，让 Agent 在推理循环里自主决定什么时候查知识库、什么时候搜网络、什么时候交叉验证。
>
> 第三块是记忆与前端。记忆做了三层：Redis 短期滑动窗口加摘要压缩、PostgreSQL 会话持久化、Milvus 长期语义召回。前端用 React 加 TypeScript 实现了三栏应用，可以看到 Agent 每一步的 Thought、Action、Observation，以及 RAG 上下文和检索方式对比。
>
> 工程化方面，我有 67 个单元测试，全部离线可跑；4 组量化评估，其中混合检索相比纯向量，Recall@5 提升 28.3%、MRR 提升 10.2%，叠加重排后 MRR 再提升 9.8%，在真实服务管线上也验证了 Recall@5 提升 12.8%、MRR 提升 17.3%；CI 用 GitHub Actions 在 Python 3.11、3.12 上自动跑测试和 lint。
>
> 最后，评估过程中我发现并修复了两个真实问题：一个是服务重启后 BM25 索引会丢失，混合检索会静默退化成纯向量检索，我加了从向量库重建索引的逻辑；另一个是原来的正则会把中文整段当成一个词，导致关键词检索基本失效，我统一改成了 jieba 分词。这两个问题都有对应的回归测试。
>
> 整体上，这是一个从骨架到完整系统、从实现到可评估可测试的完整项目，每个模块的实现细节我都能讲清楚。
