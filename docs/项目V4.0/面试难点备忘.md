## 难点一：Function Calling 多工具调用的 tool_call_id 关联 bug ⭐

### 一、现象

单工具调用完全正常；当模型**一次返回多个工具调用**时（比如同时调 `calculator` 和 `rag_search`），执行到第 1 步就卡住，下一轮请求被 API 拒绝，报错：

```
must be followed by tool messages responding to each tool_call_id
```

### 二、为什么会出这个问题（详细原因 + 代码）

要讲清这个 bug，得先讲 Function Calling 的**消息协议规则**：

> 当模型决定调用工具时，它返回一条 `AIMessage`，里面带一个 `tool_calls` 列表（可能含多个工具调用）。代码执行完这些工具后，把结果拼回对话历史再发给模型。协议硬性要求：**一条带 `tool_calls` 的助手消息，后面必须紧跟与每个 tool_call 一一对应的 `ToolMessage`，靠 `tool_call_id` 字段配对。**

一个合法的消息历史长这样（假设模型一次调用 2 个工具 `call_001`、`call_002`）：

```
AIMessage(tool_calls=[call_001, call_002])        ← 声明"我要调这两个工具"
ToolMessage(content="结果1", tool_call_id="call_001")  ← 回答 call_001
ToolMessage(content="结果2", tool_call_id="call_002")  ← 回答 call_002
```

**我当时的错误代码**——把"追加助手消息"这一句放进了循环里：

```python
for tc in response.tool_calls:            # 循环每个工具调用
    obs = 执行(tc)
    history.append(AIMessage(tool_calls=response.tool_calls))  # ❌ 每循环一次就重复加一遍
    history.append(ToolMessage(content=obs, tool_call_id=tc["id"]))
```

循环跑两遍，拼出的历史变成了：

```
AIMessage(tool_calls=[call_001, call_002])        ← 第 1 遍加的
ToolMessage("结果1", tool_call_id="call_001")      ← 只回了 call_001
AIMessage(tool_calls=[call_001, call_002])        ← 第 2 遍又加了一遍（重复！）
ToolMessage("结果2", tool_call_id="call_002")      ← 只回了 call_002
```

**为什么这样会挂**：API 服务器在真正跑模型之前，会先校验消息格式。它看到第二条 `AIMessage(tool_calls=[call_001, call_002])` 声明了两个调用，但后面只跟了一条 `ToolMessage(call_002)`——`call_001` 的结果缺失了。于是 API 拒绝整个请求。

关键点：**第二个工具其实执行了、结果也算出来了**，只是消息结构排错了，模型根本没机会看到结果。所以这个 bug 不是"工具算错了"，也不是"模型答错了"，而是"拼消息的方式违反了接口的格式契约"。

### 三、正确应该是什么样的

```python
# 助手消息只加一次（在循环外）
history.append(AIMessage(
    content=response.content or "",
    tool_calls=response.tool_calls,
))
# 循环里只给每个 tool_call 各加一条 ToolMessage
for tc in response.tool_calls:
    obs = await invoke_tool(tc["name"], tc["args"])
    history.append(ToolMessage(content=obs, tool_call_id=tc["id"]))
```

拼出的历史：

```
AIMessage(tool_calls=[call_001, call_002])        ← 只加一次
ToolMessage("结果1", tool_call_id="call_001")
ToolMessage("结果2", tool_call_id="call_002")
```

配对完整，API 校验通过。

### 四、收获

1. **把接口协议当"契约"理解，而不是"格式"**：报错不在工具执行层，而在消息协议层。遇到这类问题，先搞清楚"这个接口对消息序列有什么硬性约定"，再回头看自己的拼装逻辑，比瞎试快得多。
2. **"单测全绿"不等于"没问题"**：单工具用例永远测不出这个 bug，因为它只在多工具并发调用时才触发。测试要覆盖边界情况（多工具、零工具、异常工具）。
3. **现象反推根因**：工具执行了但结果没被用，说明问题在"结果如何传递"，而不是"结果如何产生"——把链路切开定位，快很多。
4. **最小修复 + 回归测试**：改就几行，但补了一个"一次调多个工具"的用例防止回归。

**时长参考**：约半天（大头在定位）。
