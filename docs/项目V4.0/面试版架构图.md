## 一、总览：四层架构

```
┌─────────────────────────── 接入层 ───────────────────────────┐
│  FastAPI  (app/api/routes/chat.py)                          │
│  /chat/agent   /chat/rag   /rag/ingest   /chat|stream       │
└────────────────────────────┬─────────────────────────────────┘
                             ▼
┌─────────────────────── Agent 编排层 ─────────────────────────┐
│  AgentService  ── 总控：安全门 → 记忆 → 意图 → 路由 → 执行 → 回写 │
│     │            │              │              │             │
│  意图识别       模式路由        编排器          反思闭环        │
│  IntentRecognizer  ModeRouter  Orchestrator   Reflection      │
│  (LLM+关键词)    (规则→LLM→兜底) (react/plan_execute) (分级→修正)│
│                    └── 工具调用后端: Function Calling (可降级)  │
└────────────┬───────────────────────────────┬─────────────────┘
             │  ReAct 循环里自主调度工具          │
             ▼                               ▼
┌──────────────── 能力层 ────────────┐  ┌──────── 记忆层 ────────┐
│  工具 ToolRegistry                │  │ 短期 Redis(滑窗+摘要)   │
│  ├ calculator(计算)               │  │ 长期 Milvus(语义召回)   │
│  ├ web_search(百度)               │  │ 持久化 PostgreSQL        │
│  └ rag_search(私有知识库)          │  └────────────────────────┘
└────────────┬──────────────────────┘
             ▼
┌──────────────────────── 检索层 RAG ─────────────────────────┐
│ 两阶段: BM25(jieba)+向量 → RRF 融合召回 → cross-encoder 精排  │
│ 向量化: bge-m3 (1024维, CUDA)   精排: bge-reranker-v2-m3     │
│ 存储: Milvus (向量库)                                       │
└─────────────────────────────────────────────────────────────┘
```

**一句话概括**：一个「带医疗安全边界、能自主选工具、会反思修正」的多模式 Agent，底座是「双路召回 + 精排」的两阶段 RAG 和「短/长/持久」三层记忆。

## 二、Agent 执行主流程（时序）

```
用户提问
  │
  ▼
安全门 classify_risk()（关键词粗筛 + LLM 确认）
  ├─ 未命中关键词 → safe，放行
  ├─ emergency（正在发作）→ 急诊话术，短路返回
  ├─ clarify（时态不明）→ 澄清追问
  └─ safe（假设/既往/科普）→ 放行 + disclaimer
      ▼
读记忆 memory.get_relevant(session_id, query)
  ├─ 短期(Redis 近轮) + 长期(Milvus 语义) → 补全追问/指代
      ▼
意图识别 IntentRecognizer.recognize()
  ├─ LLM 分类: 知识问答/实时搜索/数学计算/文档管理/闲聊
  └─ 降级: 关键词规则树，低置信度→澄清
      ▼
模式路由 ModeRouter.resolve()
  ├─ 规则快路径: 简单→react，搜索/多步→plan_execute
  ├─ LLM Router 二次判断
  └─ 兜底: react
      ▼
编排执行 Orchestrator.run()
  ├─ react      : Thought→Action→Observation (≤10 步)
  └─ plan_execute: 拆子任务→逐个子任务 ReAct→失败重规划(≤2)→汇总
      ▼
反思闭环 (enable_reflection 开关)
  └─ 风险分级→低风险跳过/高风险评估→修正→完整重试(≤2)
      ▼
回写记忆 append_turn (user+assistant)
      ▼
返回: 最终答案 + 步骤 StepInfo + 工具调用 ToolCallLog
```

## 三、RAG 两阶段检索链路

```
查询 query
   │
   ▼
┌────────── 召回阶段(多路) ──────────┐
│ 向量路: bge-m3 编码 → Milvus TopK  │
│ 关键词路: jieba 分词 → BM25 打分   │
└──────────┬─────────────────────────┘
           ▼
      RRF 倒数排名融合 → candidate_k=50 候选
           ▼
┌────────── 精排阶段 ────────────────┐
│ cross-encoder bge-reranker-v2-m3  │
│ 对 (query, doc) 逐对打分 → 重排    │
└──────────┬─────────────────────────┘
           ▼
       top_k=20 结果 → 带引用生成
```

**建库侧**（离线）：多格式解析 → 分块 → bge-m3 向量化 → 入 Milvus。

## 四、三层记忆架构

```
短期记忆  Redis 滑动窗口(window=20, 4000token)
   └─ 超量触发 LLM 摘要压缩(保留尾部)
长期记忆  Milvus 语义向量(COSINE) → 跨会话语义关联
持久化    PostgreSQL → 会话消息落盘
   └─ PersistentMemoryManager: Redis 热 + PG 冷 + 内存降级
```

## 五、每层展开点（接住追问）

| 模块 | 可展开的技术点 |
|------|---------------|
| 模式路由 | 为什么不全部交给 LLM？——规则快路径省 token + 低延迟，LLM Router 兜底语义边界，失败再回 react，三级降级保证可用性 |
| ReAct vs Plan-Execute | 简单任务 ReAct 少规划开销；多步任务 plan 拆解 + 失败重规划，比裸 ReAct 更稳、更可解释 |
| Function Calling | 是「工具调用后端」不是第三种模式；后端不可用时降级文本兼容后端，模式不变 |
| RRF 融合 | 无需调权重，鲁棒；两阶段里召回负责「全」、精排负责「准」 |
| 精排数据 | MRR +29.9%、Precision@1 +50%、Recall@5 +64.6%，代价是 +2s 延迟，部署按需开关 |
| 记忆 | 短/长/持久三层各司其职；摘要压缩控上下文长度；长期记忆解决跨会话 |
| 医疗安全 | 关键词粗筛 + LLM 确认两阶段：只对「正在发作」短路急诊话术，假设/既往/科普放行，降低误拦 |

## 六、60 秒开场介绍稿（纯文字版）

> 我做的这个项目是一个**心血管慢病管理 AI Agent**，核心解决三个问题：**怎么把大模型接入真实任务、怎么让检索更准、怎么让多轮对话记住上下文**。
>
> 首先是**任务编排**。我设计了一个三级模式路由：规则快路径、LLM 路由、ReAct 兜底，根据意图和任务复杂度在 **ReAct 循环**和 **Plan-and-Execute** 两种范式之间切换，工具调用用 Function Calling 做后端、失败自动降级，外面再套一层**反思闭环**，高风险回答会评估修正后重试。
>
> 其次是**知识增强**。我做的是**两阶段检索**：第一路 BM25 关键词 + 第二路 bge-m3 语义向量，用 RRF 融合做召回，再用 cross-encoder 精排。评测下来 **MRR 提升 29.9%、Precision@1 提升 50%、Recall@5 提升 64.6%**，代价是多了约两秒延迟。
>
> 最后是**记忆**。短期用 Redis 滑窗加摘要压缩，长期用 Milvus 做语义召回，底层 PostgreSQL 持久化，三层协同解决跨会话的上下文关联。
>
> 另外整个系统有**医疗安全边界**——关键词粗筛 + LLM 确认两阶段，只有「正在发作」的高风险症状才会被短路拦截。
