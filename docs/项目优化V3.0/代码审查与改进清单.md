# 代码审查与改进清单

> 对整个项目（后端 Agent/RAG/记忆/基础设施 + 前端 + 测试/CI + 仓库卫生）做的一次全面 review。
> 记录日期：2026-08-18
> 结论分「高 / 中 / 低」三档，最后给出建议的动手顺序。

---

## 一、结论摘要

1. **最大的问题不是 bug，而是「双套实现 + 死代码」并存。** 项目里存在一整套平行的 RAG/基础设施实现，以及多个从未接线的模块。它们有导出、有测试、但不在请求路径上，正在悄悄漂移。面试官 grep 一下就会看到两套 BM25、两个 vector store 封装。
2. **有几个真 bug 和安全问题值得先修**，尤其对心血管/医疗 demo：删除会话时 Redis 记忆没删、LLM 裸 SQL 工具、PHI 写进日志、async 循环里同步阻塞。
3. **「反思风险分级」还没接线**：模块（`reflection_gating.py`）和单测（`test_reflection_gating.py`）都写了，但配置里没开关、orchestrator 默认永远走 R3 全量反思，R1/R2 的省成本路径从未执行。
4. **安全关键区是干净的**：上传校验、calculator 的 AST 白名单、web search（无 SSRF）、熔断器、DomainPolicy 急诊分流均确认无误，面试里是加分项，不用动。

## 三、中优先级（工程一致性 / 成本 / 覆盖）

### A. 死代码 & 双套实现（一次清理，收益最大）

- [langgraph_agent.py](../../app/core/agent/langgraph_agent.py) 完全没被 import（只有 docs 提到），还重复定义了 `AgentResult` 和 `REACT_SYSTEM_PROMPT` → 删或接线。
- 平行的 RAG/基础设施实现：
  - `rag/retriever.py`(`MultiRetriever`)、`rag/reranker.py`(`Reranker`)
  - `vectordb/milvus_client.py`(`MilvusManager`)、`cache/redis_cache.py`(`RedisCache`)
  - 都在 `__init__.py` 导出且有测试，但 `RAGService` 用的是自己内联的 `_MilvusRAGStore` + `_BM25`。**同一能力两套实现**。
- `tools/builtin/database.py`(`DatabaseQueryTool`)、`tools/router.py`(`ToolRouter`) 导出但从未注册。
- 未使用的方法/变量：`AgentOrchestrator._run_reflection`（[orchestrator.py:488](../../app/core/agent/orchestrator.py#L488)）、`ReflectionAgent.should_retry_or_warn`（[reflection.py:146](../../app/core/agent/reflection.py#L146)）、`orchestrator.py` 的 `used_fallback` 局部变量。
- 前端死页面：`MedicationPage.tsx`、`MonitorPage.tsx`、`Sidebar.tsx`（和 `App.tsx` 内联 sidebar 重复）、`RiskBadge.tsx` —— 都没被路由。
- 前端死 API 模块：`api/chat.ts`、`api/documents.ts`、`api/health.ts` 里的函数全部没人调用（页面直接裸 `fetch`）。

### B. 双入口行为分叉（面试易被追问）

- **两套 chat 入口**：`/chat`（模块级 `IntentRecognizer()` 无 LLM，永远关键词分类）vs `/chat/agent`（LLM 意图 + 路由 + 反思）。两套 policy/system-prompt/高风险检查要手动同步；`/chat` 的 `_stream_generator` 还绕过 `ModelRouter` 和熔断器，直接 new `AsyncOpenAI`。
- **两套文档入库**：`/documents/upload` 写进 PostgreSQL + `uploads/` 但**不进 Milvus**，所以这些文档对 agent 的 `rag_search` 工具**不可见**；只有 `/rag/ingest` 才喂搜索库。从 A 入口传的文档，B 入口搜不到。

### C. 「反思分级」还没生效

- `enable_reflection_gating` 不在 `agent_service.py` 的 config dict 里，orchestrator 默认 `False`（[orchestrator.py:142](../../app/core/agent/orchestrator.py#L142)），所以运行时 `risk_level` 恒为 `R3_HIGH`、`allow_retry` 恒 `True`（[orchestrator.py:318,331](../../app/core/agent/orchestrator.py#L318)）—— R1/R2 的省成本路径从未执行。模块 + 单测都在，就差接线（对应 `优化记录.md` 末尾的 TODO #1/#2）。

### D. 依赖清单漂移

- `requirements.txt` 有 `milvus-lite>=3.0.0`，但 `pyproject.toml` 的 `[project].dependencies` **漏了它**，`pip install -e .` 会装不出硬依赖；`psycopg2-binary` 两处都有但代码用 `asyncpg`（无用依赖）。建议单一来源（`[project]` + CI 里 `-e .`）。

### E. 测试覆盖缺口

- 20 个测试文件覆盖了叶子组件，但**请求主链路零覆盖**：`AgentOrchestrator.run`、`AgentService.chat`、所有路由、`main.py` 装配都没测。最高风险的 fallback-to-react、plan_execute 分发、反思重试循环全是裸奔的。

## 四、低优先级（打磨 / 潜在坑）

- **语义缓存 id 用 `hash()`**（进程随机化）→ 重启后同一 query 命中不同 id；`semantic_set` 无锁读改写、索引无限增长 [redis_cache.py:196](../../app/infrastructure/cache/redis_cache.py#L196)（该缓存本身是死代码，接线前先修）。
- **`list_sessions` N+1**：每个会话一次 `count(*)` [session_repository.py:63-88](../../app/core/session_repository.py#L63-L88)。
- **BM25/tokenizer 重复**：`rag_service.py` 和 `retriever.py` 两份几乎相同的 Okapi 实现，抽一个 `bm25.py`。
- **Milvus expr 转义错**：转义单引号但用双引号包裹 `== "{sid}"` [long_term.py:145](../../app/core/memory/long_term.py#L145)、`:208` —— 应转义 `"` 和 `\`。
- **`_rebuild_bm25` 硬编码 `limit=10000`**：集合超 1 万 chunk 时重建后关键词索引不完整 [rag_service.py:238](../../app/core/rag_service.py#L238)。
- **客户端生命周期**：`AsyncOpenAI` 没 `aclose()`、没 timeout、没 shutdown hook；`tracer._current_parent` 不清理会随 session 数增长。
- **`mode_router.py:54` 硬编码 `"2025","2026"`** 时间敏感词，过几年自动失效。
- **前端**：
  - `strict` 未开启（`frontend/tsconfig.app.json`）。
  - dropzone `accept` 含 `.doc/.docx`，但后端只收 `.pdf/.txt/.md/.markdown` [useDropzone.ts:50](../../frontend/src/pages/useDropzone.ts#L50)。
  - `ChatRequest` 类型缺 `conversation_id`/`domain`，`agent_mode` 缺 `'auto'` [types/index.ts:11-16,104](../../frontend/src/types/index.ts#L11-L16)。

## 五、仓库卫生（工程化，代码 review 不覆盖）

1. **`milvus.db/` 6 个二进制文件被 git 跟踪**，每次跑服务都在 churn（`LOCK`、`manifest.json`、`schema.json`、3 个 `wal/*.arrow`）→ `git rm -r --cached milvus.db/`。
2. **无 `.gitattributes`**，Windows 下 LF/CRLF 一直报警 → 加 `*.py text eol=lf` 等规则。
3. **根目录孤儿 `package-lock.json`**（`packages` 空，前端依赖在 `frontend/package-lock.json`）→ 删。
4. **大量未提交改动**：47 个文件 +1924/−5480 行堆在 `feature/cardiovascular-agent` → 按逻辑拆几个提交（领域策略 / FC 主路径 / 反思分级）。

## 六、建议的动手顺序

1. **一轮「删死代码 + 收敛双套」**：删 `langgraph_agent.py`、`DatabaseQueryTool`、`ToolRouter`、未用 RAG/vectordb/cache 封装、前端死页面/死 API 模块 —— 性价比最高，直接解决「面试被 grep 出两套实现」的问题。
2. **一轮「真 bug」**：#1 Redis 删除泄漏、#3/#4 阻塞事件循环、#7 前端 `res.ok`、#5 PHI 日志、#6 硬编码密码。
3. **一轮「接线」**：把 `reflection_gating` 开关接进 config + orchestrator、补 `use_function_calling=True`、补主链路集成测试。
4. **一轮「仓库卫生」**：`git rm --cached milvus.db/`、加 `.gitattributes`、拆提交。

## 七、已确认干净的加分项（面试可强调，不用动）

- 上传校验（扩展名白名单 / 大小限制 / 路径穿越防护 / null 字节）：`app/api/upload_validation.py`，有测试。
- Calculator 用 AST 节点白名单而非 `eval`：`app/core/tools/builtin/calculator.py`。
- Web search 无 SSRF：仅硬编码 `https://www.baidu.com/s` 目标，用户输入只进 query-string：`app/core/tools/builtin/search.py`。
- LLM 熔断器三态逻辑正确且有锁保护：`app/infrastructure/llm/circuit_breaker.py`。
- DomainPolicy 急诊关键词短路在工具/LLM 链之前，免责声明与回答边界干净：`app/core/domain/policy.py`。
- 记忆层 Redis → PostgreSQL → 内存降级阶梯 + 失败隔离标志设计合理；FC 多工具调用消息顺序的回归测试覆盖到位。
