# 项目优化记录

> 本文统一记录项目在“项目优化 V3.0”阶段已经完成或正在实施的优化调整，便于后续复盘、面试讲解和继续迭代。
>
> 记录日期：2026-08-11

## 一、项目定位调整

### 1. 从医疗专用 Agent 调整为通用 Agent/RAG 平台

项目不再把医疗业务逻辑硬编码为底层核心，而是调整为：

```text
通用 Agent/RAG 底座
+
心血管慢病管理默认 Demo
+
可插拔领域安全策略
```

通用底座负责：

- 文档上传与解析；
- 文档分块与向量化；
- RAG 检索；
- 工具调用；
- Agent 编排；
- 记忆管理；
- 执行轨迹追踪；
- 错误处理和故障降级。

心血管慢病管理作为默认演示领域，通过领域策略插件提供：

- 医疗领域系统提示；
- 高风险关键词识别；
- 急诊安全分流；
- 非诊断免责声明；
- 禁止擅自停药、换药和调整剂量等安全约束。

这样，用户上传其他领域的 PDF、Markdown 或 TXT 文档后，平台仍然可以构建对应知识库并完成通用 RAG 问答，而不需要修改核心 Agent 逻辑。

### 2. 控制“万能 Agent”边界

项目没有追求无边界的万能 Agent，而是采用“通用底座 + 领域 Profile + 可插拔策略”的方式：

- 通用能力保持稳定；
- 领域安全规则独立封装；
- 不同领域可以拥有不同的 Prompt、风险规则和评测集；
- 领域策略不污染 RAG、工具注册和任务编排代码。

## 二、存储与基础设施调整

### 1. 明确分层存储职责

项目对不同类型的数据采用分层存储：

| 存储 | 主要职责 |
|---|---|
| PostgreSQL | 用户、会话、消息、文档元数据、文档块和长期结构化数据 |
| Redis | 短期会话记忆、滑动窗口、TTL、热点缓存和摘要缓存 |
| Milvus Lite | 文档向量检索、长期语义记忆和相似度搜索 |
| 内存 | 本地开发、测试以及外部基础设施不可用时的降级 |

核心原则是让关系数据、短期状态和语义数据分别使用适合的存储，而不是让一个数据库承担所有职责。

### 2. 保留向量数据库替换边界

新增并使用 `VectorStore` 抽象，RAG 业务层不直接依赖具体 Milvus 类型。当前使用 Milvus Lite，未来可以替换为：

- pgvector；
- Milvus Server；
- 其他向量数据库。

本阶段不迁移 MySQL，也不实现 pgvector，避免在核心 Agent/RAG 优化阶段扩大基础设施改造范围。

### 3. 不强制要求所有基础设施同时启动

项目保留多级降级能力：

```text
完整基础设施
  ↓ 不可用
内存或本地实现
```

因此，本地开发和测试不要求 PostgreSQL、Redis、Milvus 同时启动，降低项目运行门槛，也方便面试现场演示。

## 三、RAG 能力优化

### 1. 支持通用文档知识库

文档处理链路调整为：

```text
文件上传
  ↓
格式与安全校验
  ↓
文本解析
  ↓
文档分块
  ↓
Embedding
  ↓
向量库和数据库存储
```

当前支持：

- PDF；
- TXT；
- MD；
- Markdown。

### 2. 使用混合检索

RAG 不再只依赖向量相似度，而是组合使用：

- 向量语义检索；
- BM25 关键词检索；
- 混合召回；
- RRF 倒数排名融合；
- 可选重排序。

这样可以同时兼顾语义相似问题和专业术语、指标名、关键词等精确匹配场景。

### 3. 增加检索降级

Embedding 和向量存储均提供降级路径：

```text
sentence-transformers
  ↓ 失败
字符 n-gram Embedding
  ↓
Milvus Lite
  ↓ 失败
内存向量存储
```

即使本地没有完整启动向量基础设施，也可以完成基本检索。

### 4. RAG 工具化

RAG 既可以作为独立的 `/chat/rag` 问答能力，也可以通过注册工具的方式被 Agent 调用。这样既保留了简单问答链路，也支持复杂任务中将 RAG 与 Web Search、Calculator 等工具组合使用。

## 四、Agent 架构优化

### 1. 明确上层模式只有两种

对外的 Agent 任务编排模式统一为：

- `react`；
- `plan_execute`。

没有新增 `function_calling` 对外模式，前端和 API 也不展示第三种模式。

### 2. 重新明确三者关系

三者不属于同一个层次：

```text
任务编排层
├── ReAct
└── Plan-and-Execute

工具调用后端
└── Function Calling

具体工具
├── RAG Search
├── Web Search
└── Calculator
```

其中：

- ReAct 负责根据当前观察动态决定下一步；
- Plan-and-Execute 负责复杂任务的拆解、执行顺序、失败重规划和结果汇总；
- Function Calling 负责将工具名和参数结构化传递给程序；
- RAG、搜索和计算器是被执行器调用的具体工具。

### 3. Function Calling 作为 ReAct 主后端

当前推荐链路为：

```text
ModeRouter
├── react
│    └── _invoke_react()
│         └── FunctionCallAgent
│
└── plan_execute
     ├── PlannerAgent
     ├── 每个子任务调用 _invoke_react()
     │    └── FunctionCallAgent
     ├── Replanner
     └── Synthesizer
```

Function Calling Agent 使用 LangChain 的 `bind_tools()` 和结构化 `tool_calls`，避免依赖自然语言正则解析工具名和参数。

### 4. 保留文本协议 ReAct 作为隐藏兼容层

文本协议 ReAct 实现没有删除，但不再作为独立产品模式或主要面试卖点。它仅用于兼容不支持原生工具调用的模型，或在 Function Calling 执行失败时作为内部 fallback。

内部降级链路为：

```text
Function Calling
  ↓ 返回失败或抛出可恢复异常
文本协议 ReAct
```

上层模式保持不变，用户不会看到额外的第三种模式。

### 5. 统一 ReAct 执行入口

`AgentOrchestrator._invoke_react()` 作为普通 ReAct 和 Plan-and-Execute 子任务的统一执行入口：

- 优先调用 Function Calling Agent；
- Function Calling 成功时直接返回结果；
- Function Calling 返回失败或执行异常时，记录 `react.backend_fallback` 事件；
- 使用新的文本协议 ReAct 执行器完成内部降级；
- 复用 query、session_id、工具白名单、trace_id 和执行步骤上下文；
- 不复用不兼容的 LangChain `AIMessage(tool_calls)` / `ToolMessage` 历史；
- 不让执行器重复写入会话记忆，记忆写入统一由服务层负责。

### 6. Plan-and-Execute 复用统一入口

Plan-and-Execute 的每个子任务都通过 `_invoke_react()` 执行，因此：

- 普通 ReAct 和计划执行使用一致的工具调用后端；
- Function Calling 的主路径只需维护一处；
- fallback 行为自动覆盖 Plan-and-Execute 子任务；
- 复杂任务仍然可以执行失败重规划和最终汇总。

## 五、多轮记忆优化

### 1. 修复 Function Calling 后端未注入历史的问题

此前 Function Calling 后端虽然已经接入，但没有读取会话记忆，导致多轮对话中模型只看到当前问题。

现已调整为：

```python
session_id = context.get("session_id", "default")
mem_snippets = await memory.get_relevant(
    session_id,
    query,
    limit=8,
)
```

读取到的相关记忆会注入 Function Calling Agent 的系统提示词，使其与文本协议 ReAct 后端的记忆行为保持一致。

### 2. 统一记忆写入边界

执行器内部不再写入最终 assistant 消息，避免以下问题：

- AgentService 重复写入 user/assistant；
- Plan-and-Execute 子任务结果污染主会话；
- 同一轮消息出现重复记录。

当前由 `AgentService.chat()` 统一负责：

1. 写入 user 消息；
2. 调用编排器；
3. 写入 assistant 消息。

### 3. 意图识别和模式路由使用历史

在编排前读取会话相关记忆，并将其传入：

- 意图识别；
- 模式路由。

多轮追问、指代和省略表达可以结合历史判断真实意图和任务复杂度。记忆读取失败时仍然可以按单轮请求降级处理。

## 六、当前记忆读写逻辑与具体存储内容

### 1. 统一入口

当前对话记忆由 `PersistentMemoryManager` 统一管理，对上层暴露两个核心方法：

- `get_relevant(session_id, query, limit)`：读取与当前会话相关的记忆片段；
- `append_turn(session_id, role, content, metadata)`：写入一条用户或助手消息。

`AgentService.chat()` 是主写入边界，编排器和具体 Agent 只负责读取记忆，不直接写入最终 assistant 消息。这样可以避免 ReAct 子任务、Plan-and-Execute 子任务和主会话重复写入。

### 2. 一次请求的读取流程

普通 Agent 请求的读取顺序如下：

```text
AgentService.chat()
  ↓
PersistentMemoryManager.get_relevant()
  ├── Redis ShortTermMemory
  ├── PostgreSQL 最近消息
  └── Python 内存降级
        ↓
  叠加 Milvus 长期语义记忆（如果已启用）
  ↓
意图识别与 ModeRouter 注入历史
  ↓
FunctionCallAgent / ReActAgent 再次读取相关记忆
  ↓
生成最终回答
```

当前具体行为：

1. `AgentService.chat()` 在意图识别前读取最多 6 条历史片段，供意图识别和模式路由消解追问、指代和省略。
2. `FunctionCallAgent` 和文本协议 `ReActAgent` 在真正执行 ReAct 前再次读取最多 8 条相关记忆，供最终回答生成使用。
3. `PersistentMemoryManager` 优先从 Redis 读取最近窗口；Redis 失败或没有结果时读取 PostgreSQL 最近消息；两者都不可用时读取进程内内存。
4. 如果配置了 Milvus 长期语义记忆，则召回最多 3 条语义相关记录，并放在短期历史之前，最后按 `limit` 截断。
5. 当前 Redis 和 PostgreSQL 的读取内容本质上是“最近消息窗口”，不是对消息本身做向量相似度筛选；语义相关召回由 Milvus 长期记忆负责。

### 3. 一次请求的写入流程

成功、失败和高风险安全分流请求均由服务层写入用户消息；普通 Agent 请求在编排完成后再写入 assistant 消息：

```text
收到用户请求
  ├── 高风险请求
  │    ├── 写入 user
  │    └── 写入 safety assistant
  │
  └── 普通请求
       ├── 意图识别 / 编排 / 生成
       ├── 写入 user
       └── 写入 assistant（附 trace_id、agent_mode）
```

每次 `append_turn()` 会同步尝试写入以下位置：

```text
PersistentMemoryManager.append_turn()
  ├── Python 内存：始终写入，作为最终降级副本
  ├── PostgreSQL：主持久化路径
  ├── Redis：短期热路径副本
  └── Milvus：user / assistant 内容的长期语义记忆旁路写入
```

Milvus 写入失败不会阻断主对话；Redis、PostgreSQL 和 Milvus 的异常都会记录日志并尽量继续完成其他路径。

### 4. Redis 中保存的内容

Redis 使用 List 结构保存每个会话的消息，键格式为：

```text
stm:session:{session_id}
```

每条 List 元素是 JSON 字符串，结构为：

```json
{
  "role": "user | assistant | system",
  "content": "消息正文",
  "metadata": {}
}
```

写入使用 `RPUSH`，读取使用 `LRANGE 0 -1`，因此天然保持时间顺序。短期记忆默认：

- 最多保留 20 条消息；
- 总 token 估算超过 4000 时触发压缩；
- 压缩时把较早消息交给 LLM 生成 `[历史摘要]` 系统消息；
- 保留尾部较新的消息；
- LLM 摘要失败时退回截断文本摘要。

需要注意：代码当前设置了窗口和 token 压缩，但 `PersistentMemoryManager` 本身没有为会话键设置 Redis TTL；文档中“TTL”属于设计职责，尚未在当前记忆写入代码中真正执行过期策略。

### 5. PostgreSQL 中保存的内容

PostgreSQL 是冷存储和会话持久化路径，主要使用两张表：

#### `conversations`

保存会话级信息：

- `id`：会话 ID；
- `title`：会话标题，首条 user 消息自动生成，最多取前 30 个字符；
- `user_id`：可选用户标识；
- `meta`：会话级 JSON 元数据；
- `created_at`、`updated_at`：创建和更新时间。

#### `messages`

保存消息级信息：

- `id`：消息 ID；
- `conversation_id`：所属会话；
- `role`：`user`、`assistant` 或其他消息角色；
- `content`：完整消息正文；
- `token_count`：预留的 token 数字段，当前写入路径没有主动计算；
- `meta`：JSON 元数据；
- `created_at`：消息创建时间。

普通 assistant 消息当前至少会携带：

```json
{
  "trace_id": "本次请求的链路 ID",
  "agent_mode": "react 或 plan_execute"
}
```

### 6. Python 内存中保存的内容

内存降级实现使用两个字典：

```text
_sessions[session_id] → 消息列表
_session_meta[session_id] → 会话标题、创建时间、更新时间
```

消息结构与 Redis 基本一致：

```json
{
  "role": "user | assistant",
  "content": "消息正文",
  "metadata": {}
}
```

内存数据只存在于当前进程：

- 适合本地开发和离线测试；
- Redis、PostgreSQL 不可用时保证基本对话能力；
- 服务重启后丢失；
- 不适合作为生产持久化方案。

### 7. Milvus 长期语义记忆中保存的内容

Milvus 使用 `long_term_memory` 集合保存可语义召回的会话消息。每条记录包含：

| 字段 | 内容 |
|---|---|
| `pk` | UUID 形式的记忆 ID |
| `embedding` | 消息正文的向量，当前按 384 维配置 |
| `content` | 原始消息正文 |
| `session_id` | 所属会话 ID，用于限定会话范围 |
| `meta` | JSON 字符串，包含 `memory_id` 以及写入时的 metadata |

当前只将非空的 `user` 和 `assistant` 消息写入长期语义记忆，不写入 `system` 消息和空白内容。召回时：

1. 对当前 query 生成 embedding；
2. 使用 COSINE 相似度搜索；
3. 通过 `session_id` 过滤，只召回当前会话的长期记忆；
4. 默认最多取 3 条；
5. 转为 `[历史记忆] {content}` 文本后，与短期消息合并。

因此，Milvus 保存的是“消息正文的语义索引副本”，不是完整会话的唯一事实来源。完整会话仍以 PostgreSQL 为主，Redis 是短期副本，内存是降级副本。

### 8. 当前记忆架构的优点与待改进点

优点：

- 读写通过统一管理器抽象，Agent 不感知具体数据库；
- PostgreSQL 保证会话消息的持久化；
- Redis 提供短期窗口和摘要压缩；
- Milvus 支持跨较长时间范围的语义召回；
- 内存降级使本地测试不依赖完整基础设施；
- Function Calling 和文本协议 Agent 使用一致的记忆接口。

当前需要继续完善的点：

- Redis 会话键尚未真正设置 TTL；
- `append_turn()` 的多存储写入目前是逐个旁路执行，不是跨存储事务，极端情况下可能出现副本不一致；
- Milvus 当前按每条 user/assistant 消息写入，长期运行后需要考虑去重、重要性筛选和定期清理；
- `token_count` 字段已存在，但当前消息写入没有统一计算；
- 删除会话时 Redis 路径目前只有读取检查，尚未明确执行按键删除；
- `get_relevant()` 的短期记忆主要是最近窗口，后续可以引入触发式上下文注入和分层记忆策略。

## 七、领域安全优化

### 1. 引入可插拔 DomainPolicy

领域策略从通用 Agent 逻辑中独立出来，当前包含：

- `general`；
- `cardiovascular`。

未来可以增加教育、法律、企业知识库等领域策略，而不需要重写 Agent 核心流程。

### 2. 增加高风险问题分流

心血管领域对胸痛、呼吸困难等高风险输入提前进行安全分流，优先提示及时就医，不继续生成可能造成误导的普通回答。

安全检查覆盖：

- 普通聊天；
- 流式聊天；
- RAG 问答；
- Agent 问答。

### 3. 增加医疗回答边界

普通医疗回答追加非诊断免责声明，并明确禁止：

- 擅自停药；
- 擅自换药；
- 擅自调整药物剂量；
- 将模型回答作为医生诊断或处方。

## 七、文件上传与安全优化

已对文档上传链路增加基础安全校验：

- 文件扩展名白名单；
- 文件大小限制；
- 空文件校验；
- 路径穿越防护；
- 文件名和保存路径安全处理；
- 解析失败时返回可控错误。

这些校验既服务通用 RAG，也降低了默认 Demo 中的上传风险。

## 八、可观测性与故障处理优化

### 1. 统一执行轨迹

Agent 请求使用 `trace_id` 关联完整执行过程，记录：

- 编排开始和结束；
- ReAct 步骤；
- 工具调用；
- Plan-and-Execute 规划；
- 重规划；
- 反思评分；
- Function Calling fallback；
- 最终 degraded 状态。

### 2. 增加多层降级

项目对以下失败场景提供降级或错误处理：

- LLM 意图识别失败 → 规则识别；
- Function Calling 失败 → 文本协议 ReAct；
- Plan-and-Execute 失败 → ReAct；
- Embedding 模型不可用 → 字符 n-gram；
- Milvus 不可用 → 内存向量存储；
- Redis 不可用 → 内存记忆；
- 外部搜索失败 → 可控错误或替代结果。

降级不会静默发生，关键路径会通过日志、trace 事件或 `degraded` 状态反映出来。

## 九、前端与工程化优化

## 十三、2026-08-12 存储故障修复

### 1. PostgreSQL 未启动时的降级行为

本机排查确认 Docker Compose 当前没有运行 PostgreSQL，应用配置仍指向 `localhost:5432`。应用启动阶段的建表失败不会阻断服务，但此前每次消息写入都会再次尝试 PostgreSQL。

本次将 `PersistentMemoryManager.append_turn()` 的 PostgreSQL 异常处理与读取、会话管理路径统一：首次写入失败后标记 `_pg_ok=False`，后续请求直接使用内存副本和其他可用旁路，避免重复连接失败；原始异常仍通过日志保留，便于区分数据库未启动、连接失败和 SQL 错误。

### 2. Milvus 长期记忆 embedding 接口修复

长期记忆协议要求 `embed_query(text) -> list[float]`，而 RAG 侧懒加载的是只提供 `encode()` 的原生 `SentenceTransformer`，因此 Milvus 的 `store` 和 `recall` 在真正执行 insert/search 前就失败。

新增 `SentenceTransformerEmbeddingAdapter`，复用 RAG 的 384 维 `all-MiniLM-L6-v2` 单例模型，以归一化向量实现 `embed_query()`，并在 `AgentService` 注入长期记忆时使用该适配器。RAG 原有 `.encode()` 调用保持不变，避免影响文档检索路径。
