# 记忆层 — 四层存储调用全貌

## 总览

每轮对话经历 **2 次读取** + **2 次写入**，每次都经过四层存储（读取走优先级链，写入走多写旁路）。

| 层次 | 存储 | 角色 | 数据形态 |
|------|------|------|----------|
| L1 | **内存** | 最终降级兜底，始终可用 | Python `dict[str, list[dict]]` |
| L2 | **Redis** | 热路径，滑动窗口 + LLM 摘要压缩 | List `stm:session:{id}` |
| L3 | **PostgreSQL** | 冷存储，持久化主路径 | `conversations` + `messages` 表 |
| L4 | **Milvus** | 长期语义召回（向量相似度） | `long_term_memory` + `rag_chunks` 集合 |

---

## 一、每轮对话调用次数汇总

| 序号 | 阶段 | 内存 | Redis | PostgreSQL | Milvus |
|------|------|------|-------|------------|--------|
| 1 | 读：意图识别历史上下文 | dict 查一次 | 1 × LRANGE | 降级时才查 | 1 × search |
| 2 | 读：Agent 执行上下文 | dict 查一次 | 1 × LRANGE | 降级时才查 | 1 × search |
| 3 | 写：用户消息 | dict 写一次 | 1 × RPUSH | 2-3 × SQL | 1 × insert + flush |
| 4 | 写：AI 回复 | dict 写一次 | 1 × RPUSH | 2-3 × SQL | 1 × insert + flush |

> **注**：两次读取的 Redis 结果缓存后 PG 不再查；写入时三方并行写入互不阻塞。

## 二、读取链路：逐层降级

```
get_relevant(session_id, query, limit)
  │
  ├─ L2 Redis ──── 命中 → 返回 + 叠加 L4 语义
  │  (ShortTermMemory.get_relevant)
  │
  ├─ L3 PG ─────── Redis 失败 → 返回 + 叠加 L4 语义
  │  (SessionRepository.get_recent_messages)
  │
  └─ L1 内存 ───── 全部失败 → 兜底返回 + 叠加 L4 语义
     (_InMemoryMemoryManager.get_relevant)

  L4 Milvus ───── 始终附加（如已启用）
     (_append_long_term → LongTermMemory.recall)
```

### 各层读操作详情

#### L1 内存读
- 位置：[persistent_memory.py:77-89](../../app/core/persistent_memory.py#L77-L89)
- 操作：`dict.get(session_id, [])` → 取最近 N 条
- 返回格式：`["role: content", ...]`

#### L2 Redis 读
- 位置：[short_term.py:79-102](../../app/core/memory/short_term.py#L79-L102)
- 命令：`LRANGE stm:session:{id} 0 -1`
- 数据结构：List，每个元素是 JSON `{"role": "...", "content": "...", "metadata": {...}}`
- 返回最近 `limit` 条

#### L3 PostgreSQL 读
- 位置：[session_repository.py:227-247](../../app/core/session_repository.py#L227-L247)
- SQL：`SELECT * FROM messages WHERE conversation_id={id} ORDER BY created_at DESC LIMIT {limit}`
- 返回格式：`["role: content", ...]`

#### L4 Milvus 读
- 位置：[long_term.py:123-186](../../app/core/memory/long_term.py#L123-L186)
- 操作：`search(expr="session_id == '{sid}'", limit=3)` — 按会话隔离
- 结果以 `[历史记忆]` 前缀插入最前面，优先级最高

## 三、写入链路：四写旁路

```
append_turn(session_id, role, content, metadata)
  │
  ├─ L1 内存 ─── 始终同步写入（兜底保证不丢数据）
  │
  ├─ L3 PG ───── 主持久化路径
  │
  ├─ L2 Redis ─── 辅路径（滑动窗口 + 自动压缩）
  │
  └─ L4 Milvus ── 旁路（仅 user/assistant，失败不阻塞）
```

### 各层写操作详情

#### L1 内存写
- 位置：[persistent_memory.py:92-110](../../app/core/persistent_memory.py#L92-L110)
- 操作：`dict[session_id].append({"role": ..., "content": ..., "metadata": ...})`
- 首条 user 消息自动设为会话标题（截取前 30 字符）
- 始终执行，无任何外部依赖

#### L2 Redis 写
- 位置：[short_term.py:104-120](../../app/core/memory/short_term.py#L104-L120)
- 命令：`RPUSH stm:session:{id} {json}`
- 写入后自动触发压缩检查（`_compress_if_needed`）

**压缩触发条件**（[short_term.py:122-163](../../app/core/memory/short_term.py#L122-L163)）：
- 消息数 > `window_size`（默认 20 条）
- 或总 token 数 > `max_tokens`（默认 4000）

**压缩流程**：
```
if n > 20 or tokens > 4000:
    保留尾部 10 条（window_size // 2）
    其余交由 LLM 生成中文摘要
    → DELETE key
    → RPUSH [摘要] + RPUSH [尾部消息...]
```

#### L3 PostgreSQL 写
- 位置：[session_repository.py:158-205](../../app/core/session_repository.py#L158-L205)
- 操作：
  1. `SELECT` 检查 conversation 是否存在，不存在则 `INSERT` 创建
  2. 首条 user 消息 → `UPDATE` 自动标题
  3. `INSERT INTO messages` 写入消息
  4. `UPDATE conversations SET updated_at` 更新时间

**涉及表**：

| 表 | 关键字段 | 说明 |
|------|------|------|
| `conversations` | id, title, user_id, meta, created_at, updated_at | 会话元数据 |
| `messages` | id, conversation_id, role, content, token_count, meta, created_at | 消息记录，外键级联删除 |

#### L4 Milvus 写
- 位置：[long_term.py:81-121](../../app/core/memory/long_term.py#L81-L121)
- 操作：`insert([row])` + `flush()`
- 写入内容：`{pk: uuid, embedding: vec(384), content: text, session_id: sid, meta: json}`
- 仅 user / assistant 消息，空白跳过，失败静默

## 四、各层数据结构对照

| 维度 | L1 内存 | L2 Redis | L3 PostgreSQL | L4 Milvus |
|------|---------|----------|---------------|-----------|
| **存储形式** | `dict[str, list]` | List (JSON 字符串) | 关系表 (行) | 向量集合 (文档) |
| **Key/主键** | `session_id` | `stm:session:{id}` | UUID (conversations.id) | `pk` (VARCHAR UUID) |
| **消息格式** | `{role, content, metadata}` | JSON 序列化的 Message | `role, content, meta` 列 | `content, session_id, meta` 字段 |
| **容量上限** | 无限制 (内存) | 窗口 20 条 + 4K token 压缩 | 无限制 (磁盘) | 无限制 (磁盘) |
| **生命周期** | 进程重启即丢失 | TTL 跟随 Redis 配置 | 永久持久化 | 永久持久化 |
| **查询能力** | 按 session_id 取最近 N 条 | 按 session_id 取全部 / 最近 N 条 | 按时间排序 SQL 查询 | 语义相似度搜索 + session 过滤 |

## 五、调用链路全图

```
用户发送消息
  │
  ├─ [读-1] 意图识别前获取历史上下文
  │   │
  │   ├─ L2 Redis: LRANGE stm:session:{id} 0 -1     ← 热路径
  │   │   (失败 → L3 PG: SELECT messages LIMIT 6)
  │   │   (失败 → L1 内存: dict.get)
  │   └─ L4 Milvus: search(expr="session_id=...", top_k=3)  ← 语义附加上下文
  │
  ├─ 意图识别（LLM + 关键词双通道）+ 模式路由（规则 + LLM）
  │
  ├─ Agent 执行（ReAct / Plan-Execute 循环）
  │   │
  │   ├─ [读-2] Agent 推理上下文
  │   │   ├─ L2 Redis: LRANGE stm:session:{id} 0 -1
  │   │   └─ L4 Milvus: search(expr="session_id=...", top_k=3)
  │   │
  │   └─ [可选] rag_chunks.search()   ← Agent 自主调用 rag_search 工具
  │
  └─ 记忆保存（四次旁路写入）
      │
      ├─ [写-1] user 消息
      │   ├─ L1 内存: dict.append(立即)
      │   ├─ L3 PG: INSERT INTO messages (主持久化)
      │   ├─ L2 Redis: RPUSH + 压缩检查
      │   └─ L4 Milvus: insert + flush (旁路)
      │
      └─ [写-2] assistant 回复
          ├─ L1 内存: dict.append(立即)
          ├─ L3 PG: INSERT INTO messages (主持久化)
          ├─ L2 Redis: RPUSH + 压缩检查
          └─ L4 Milvus: insert + flush (旁路)
```

## 六、各层降级策略

```
L2 Redis 不可用
  → self._redis_ok = False（单向，永不恢复）
  → 后续读取跳过 Redis，直接走 PG
  → 写入跳过 Redis

L3 PostgreSQL 不可用
  → self._pg_ok = False（单向，永不恢复）
  → 后续读取跳过 PG，走内存
  → 写入跳过 PG，仅内存 + Redis
  → 真相源从 PG 漂移到内存

L4 Milvus 不可用
  → self._long_term = None
  → get_relevant 中 _append_long_term 直接返回 short_items
  → 写入 _append_long_term_turn 直接 return

L1 内存
  → 始终可用，无降级场景
```

### 降级的代价

| 降级层 | 数据丢失风险 | 恢复条件 |
|------|------|------|
| Redis → PG | 无（PG 有全量数据） | 需重启服务 |
| PG → 内存 | **有**（内存重启即丢） | 需重启服务 + 丢失降级期间数据 |
| Milvus → 跳过 | 无（语义召回暂停，短期记忆仍工作） | 需重启服务 |

## 七、已知问题

### Redis 压缩的 LLM 调用

压缩摘要会额外调用一次 LLM（[short_term.py:165-188](../../app/core/memory/short_term.py#L165-L188)），当窗口内消息超过 20 条或总 token 超过 4000 时触发。如果 LLM 不可用，退回纯文本截断（取前 2000 字符）。

### Milvus Lite Windows flush 兼容性

Milvus Lite 内部 `manifest.py` 使用 `os.rename()` 在 Windows 上触发 `FileExistsError`（Linux/Mac 正常）。pymilvus 包装为 `MilvusException`。

**影响**：数据已成功写入（`insert` 已完成），仅 flush 刷盘失败，后续自动重试。

**处理**：`LongTermMemory` 和 `MilvusVectorStore` 中已对 `WinError 183` 做静默处理。

## 八、数据一致性问题分析

### 核心结论：存在不一致窗口，且降级后缺乏恢复机制

四层定位不同，但 **"真相源"会随降级而漂移** — 一旦 PG 故障，内存临时接管成为实际真相源，而内存重启即丢失。

| 层 | 定位 | 一致性要求 | 降级行为 |
|------|------|------|------|
| L1 内存 | 兜底缓存 | 允许丢失（重启即清空） | **无降级**（始终可用） |
| L2 Redis | 热路径加速 + 滑动窗口 | 允许不完整（压缩会丢弃旧消息） | 失败后降级到 PG |
| L3 PostgreSQL | **设计上的真相源** | 必须完整准确 | **⚠️ 一次失败即永久禁用** |
| L4 Milvus | 语义索引 | 允许丢失（旁路写入，失败静默） | 失败后跳过，不影响其他层 |

### ⚠️ 关键设计缺陷：无恢复机制

`_pg_ok` 和 `_redis_ok` 是**单向熔断**（[persistent_memory.py:316](../../app/core/persistent_memory.py#L316)、[persistent_memory.py:245](../../app/core/persistent_memory.py#L245)），失败一次即永久 `False`：

```python
# 写路径
except Exception as exc:
    self._pg_ok = False  # 一次失败 → 永久跳过 PG
    logger.warning("PG append_turn 失败，后续降级内存: {}", exc)

# 读路径
except Exception as exc:
    self._pg_ok = False  # 一次失败 → 永久跳过 PG
    logger.warning("PG get_recent_messages 失败，降级内存: {}", exc)
```

**没有**：重试、半开探测、定时健康检查、恢复后的数据回补。

### 最坏场景模拟

```
时刻 T1: PG 正常 — 消息 1-10 在 PG ✅
时刻 T2: PG 短暂故障（网络抖动/连接池耗尽）
时刻 T3: 用户发消息 11 → PG 写入失败 → _pg_ok = False
         内存写入 msg11 ✅, Redis 写入 msg11 ✅, Milvus 写入 msg11 ✅
时刻 T4: PG 恢复正常（但系统不知道，_pg_ok 仍是 False）
时刻 T5: 用户发消息 12-20 → 全部只写内存 + Redis，PG 永久缺失 msg11-20
时刻 T6: 服务重启 → 内存清空 → msg11-20 全部丢失 ❌
         Redis 可能还有 msg11-20（如果没过期）
         但下次读先走 Redis → 命中 → 不会触发 PG 恢复
结果：PG 只有 msg1-10，Redis 有 msg11-20，两者永久分裂
```

### 设计取舍：AP 优先于 CP

系统选择了 **可用性（Availability）优先** 而非强一致性（Consistency）。这体现在：

1. **写入无事务**：[append_turn()](../../app/core/persistent_memory.py#L292) 是顺序调用四个独立存储，没有分布式事务。PG 写入失败不会回滚 Redis，反之亦然。
2. **读取多副本**：[get_relevant()](../../app/core/persistent_memory.py#L208) 从 Redis/PG/内存中任一可用源读取即返回，不做多副本比对。
3. **失败即降级**：任何一层失败只标记自身不可用，不影响其他层继续服务。

### 六种不一致场景及影响

#### 场景 1：PG 写成功，Redis 写失败

```
内存 ✅ → PG ✅ → Redis ❌ → Milvus ✅
```

| 影响 | 严重程度 |
|------|------|
| 下次读到 Redis 时返回空 → 降级到 PG 读 → 拿到完整数据 | 无影响 |
| 但 PG 读成功后 **不会恢复 Redis 数据**，Redis 永久缺失此条 | 低（窗口满后旧数据本就会被压缩丢弃） |
| 如果用户立刻追问，Redis 可能丢失最近一条上下文 | **中** |

#### 场景 2：PG 写失败，Redis 写成功

```
内存 ✅ → PG ❌ → Redis ✅ → Milvus ✅
```

| 影响 | 严重程度 |
|------|------|
| 自我标记 `_pg_ok = False`，后续读/写全部降级到内存 | 中 |
| 本次已写入 Redis 的消息与 PG 状态永久不一致 | 低（PG 恢复前都走内存） |
| 重启后 Redis 仍有数据但 PG 没有 → 会话列表可能不一致 | **中** |

#### 场景 3：内存写入成功，其余全部失败

```
内存 ✅ → PG ❌ → Redis ❌ → Milvus ❌
```

| 影响 | 严重程度 |
|------|------|
| 当前会话可继续对话（内存兜底） | 无 |
| 进程重启后数据全部丢失 | **高** |

#### 场景 4：Redis 压缩导致的内容差异（设计如此）

```
PG:     [msg1, msg2, msg3, ..., msg20, msg21, msg22]
Redis:  [摘要(msg1~msg12), msg13, ..., msg22]
Milvus: [msg1 的向量, msg2 的向量, ..., msg22 的向量]
```

| 影响 | 严重程度 |
|------|------|
| 读 Redis 返回摘要而非原文 → 丢失细节 | 低（摘要保留关键事实与用户意图） |
| 这是**有意设计**：控制 context window 成本，避免 token 爆炸 | N/A |

#### 场景 5：并发请求同一会话

```
请求 A: append_turn(sid, "user", "问题A")     ← 同时
请求 B: append_turn(sid, "user", "问题B")     ← 同时
```

| 存储 | 并发安全性 |
|------|------|
| 内存 | ❌ `dict.append` 在 asyncio 单线程中是安全的，但两个协程可能交错 |
| Redis | ✅ `RPUSH` 是原子操作，但 A/B 顺序取决于调度 |
| PG | ⚠️ 两个请求可能同时读到 `title="新对话"`，都尝试 UPDATE |
| Milvus | ✅ `threading.Lock` 保护，串行写入 |

#### 场景 6：Milvus 语义召回不到刚写入的内容

```
刚写入 Milvus 的消息 → flush 失败（Windows bug）
→ 下一次 recall 搜不到刚写的内容
```

| 影响 | 严重程度 |
|------|------|
| 对"立刻追问"场景，语义记忆可能缺失最近一轮 | **低**（短期记忆 Redis/PG 已覆盖最近对话） |
| Milvus 定位是召回**很久以前**的语义相似内容，丢一轮影响极小 | N/A |

### 为什么不加分布式事务？

| 方案 | 代价 |
|------|------|
| 两阶段提交 (2PC) | 性能骤降，引入协调者单点 |
| Saga 补偿 | 复杂度爆炸，每层需要补偿操作 |
| 只写 PG + 异步同步到其他层 | 读 Redis/Milvus 时可能拿到过期数据 |
| **当前方案**：多写 + 降级 | 有短暂不一致窗口，但对话场景容忍度高 |

**结论**：对于 AI 对话应用，消息顺序要求大于原子性要求。用户发一条消息后等回复才发下一条，写冲突概率极低。不一致窗口通常在毫秒级，且下次读写自动修正（降级链路）。当前架构是合理的工程权衡。

### 改进方向

相比分布式事务，**更紧迫的是恢复机制**：

| 改进 | 实现方式 | 解决什么问题 |
|------|------|------|
| **熔断器改为三态** | Closed → Open → Half-Open → 探测成功 → Closed | PG 恢复后自动重新启用，不再永久降级 |
| **降级期间写 WAL** | PG 不可用时写本地日志文件，恢复后回放 | 防止降级期间数据丢失 |
| **定期健康检查** | 后台协程定时 ping PG/Redis，自动恢复 | 减少降级窗口长度 |
| **读取多副本校验** | 同时读 PG + Redis，不一致时以 PG 为准修复 Redis | 消除缓存不一致 |
| **Redis 预热** | PG 恢复后从 PG 批量回灌 Redis | 快速恢复热缓存 |

其中**熔断器三态改造**成本最低、收益最大，约 30 行代码即可实现——这正是项目已有的 [infrastructure/llm/circuit_breaker.py](../../app/infrastructure/llm/circuit_breaker.py)，只是记忆层没有复用。当前可以手动触发恢复：重启服务即可重置所有 `_ok` 标志。
