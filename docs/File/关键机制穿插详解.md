## 一、Function Calling：工具调用的两种后端

### 1.1 它在哪里

Function Calling 发生在 **`_invoke_react()` 方法内部**——这是 Orchestrator 中执行 ReAct 循环的统一入口。

```
AgentService.chat()
  └── Orchestrator.run(mode=...)
        │
        ├── mode="react" ──────────────┐
        │                               │
        └── mode="plan_execute" ───┐    │
              │                     │    │
              _run_plan_execute()   │    │
                │                   │    │
                react_factory() ────┘    │
                      │                  │
                      ▼                  ▼
                  _invoke_react()   ← 统一入口
                      │
                      ├── use_function_calling=True?
                      │     YES → FunctionCallAgent.run()   ← LangChain bind_tools
                      │     NO  → ReActAgent.run()          ← 正则解析
```

源码位置：[orchestrator.py:147-190](../app/core/agent/orchestrator.py#L147-L190)

```python
async def _invoke_react(self, query, session_id, intent, trace_id, steps,
                         max_steps=10, suffix="", allowed_tools=None):
    ctx = {
        "session_id": session_id,
        "tool_names": allowed_tools or self._tool_names(intent),
        "tool_descriptions": ...,   # 工具描述文本
        "trace_callback": trace_cb,
        "extra_system": suffix + f"意图：{intent.intent}，槽位：{intent.slots}",
    }

    if self._use_function_calling and self._fc_agent is not None:
        # ═══════════ Function Calling 后端 ═══════════
        self._fc_agent.max_steps = max_steps
        result = await self._fc_agent.run(query, ctx)
    else:
        # ═══════════ 正则解析 ReAct 后端 ═══════════
        llm = _LLMAdapter(self._model_router.get_llm("react"))
        agent = ReActAgent(llm=llm, tools=self._tools,
                           memory=self._memory, max_steps=max_steps,
                           session_id=session_id)
        result = await agent.run(query, ctx)

    return result
```

**关键设计**：`_invoke_react()` 对外暴露的签名完全一致——调用方（纯 ReAct 模式和 Plan-and-Execute 子任务执行）不需要知道底层是正则解析还是 Function Calling。这是一个**策略模式**：两种后端是可替换的实现，不是两种不同的 Agent 模式。

### 1.2 两种后端的区别在具体的一次 LLM 交互中

以调用计算器工具 `calculator("123*456")` 为例：

#### 正则解析后端（ReActAgent）

```
第 1 步：构造 Prompt（纯文本，工具描述嵌入 system prompt）
────────────────────────────────────────────────
System: 你是严谨的智能助手，使用 ReAct 方式回答。
        ## 可用工具
        - calculator: 计算数学表达式，参数 expression (string)

User:   ## 用户问题
        帮我算 123*456

        ## 已执行的步骤
        （尚无）

        请输出下一步：Action + Action Input 或 Final Answer。
────────────────────────────────────────────────

第 2 步：LLM 返回原始文本
────────────────────────────────────────────────
Thought: 需要调用计算器工具来计算这个数学表达式。

Action: calculator
Action Input: {"expression": "123*456"}
────────────────────────────────────────────────

第 3 步：正则解析（react_agent.py:101-139）
────────────────────────────────────────────────
_parse_react_step(raw_text)
  → 正则: Thought:\s*(.+?)(?=\n(?:Action:|Final Answer:)|\Z)
  → 正则: Action:\s*(\S+)
  → 正则: Action Input:\s*(\{[\s\S]*\})
  → 结果: {thought: "...", action: "calculator", action_input: {"expression": "123*456"}}
────────────────────────────────────────────────

第 4 步：执行工具
────────────────────────────────────────────────

  → "56088"
────────────────────────────────────────────────

第 5 步：构造历史轨迹（文本追加到下一轮 prompt）
────────────────────────────────────────────────
Step 1
Thought: 需要调用计算器...
Action: calculator
Observation: 56088
────────────────────────────────────────────────
```

#### Function Calling 后端（FunctionCallAgent）

```
第 1 步：初始化时注册工具 Schema（agent_service.py:253-296）
────────────────────────────────────────────────
from langchain_core.tools import StructuredTool
from pydantic import BaseModel, Field, create_model

# 为每个工具动态创建 args_schema
class calculator_args(BaseModel):
    expression: str = Field(description="数学表达式")

fc_tool = StructuredTool.from_function(
    coroutine=_execute,
    name="calculator",
    description="计算数学表达式",
    args_schema=calculator_args,    # ← Pydantic 模型描述参数结构
)

# 注入 LLM
self._llm = ChatOpenAI(model=..., api_key=..., base_url=...).bind_tools([fc_tool, ...])
#                                                            ↑
#                                     LangChain 在这里：将工具 Schema 注入模型请求
────────────────────────────────────────────────

第 2 步：调用 LLM（function_call_agent.py:122-126）
────────────────────────────────────────────────
messages = [SystemMessage("你是严谨的智能助手..."), HumanMessage("帮我算 123*456")]
response: AIMessage = self._llm.invoke(messages)
# ↑ LLM 返回的 AIMessage 可能包含 tool_calls 字段
────────────────────────────────────────────────

第 3 步：检查 LLM 返回（function_call_agent.py:135-165）
────────────────────────────────────────────────
if response.tool_calls:
    # AIMessage 结构：
    # {
    #   "content": "需要调用计算器",
    #   "tool_calls": [
    #     {
    #       "id": "call_abc123",
    #       "name": "calculator",
    #       "args": {"expression": "123*456"}
    #     }
    #   ]
    # }
    # ↑ 原生结构化，不需要正则解析！

    for tc in response.tool_calls:
        obs = await self._invoke_tool(tc["name"], tc["args"])
        # obs = "56088"

        history.append(ToolMessage(content=obs, tool_call_id=tc["id"]))
        # ↑ LangChain 要求 tool_call_id 关联，用于下一次 LLM 调用
────────────────────────────────────────────────

第 4 步：无 tool_calls → 直接返回答案
────────────────────────────────────────────────
# 当 LLM 认为不需要调用工具时，response.tool_calls 为空
answer = str(response.content)
return AgentResult(success=True, final_answer=answer)
────────────────────────────────────────────────
```

### 1.3 两种后端的对比

| 维度 | 正则解析 | Function Calling |
|------|----------|------------------|
| LLM 输出格式 | 自由文本（需符合 ReAct 模板） | 结构化 JSON（原生 tool_calls） |
| 解析失败率 | ~10-15%（JSON 格式错误、模板不匹配） | ~0%（模型原生能力保证） |
| 模型要求 | 任意 LLM | 需支持 function calling API |
| 历史管理 | 纯文本追加 | AIMessage + ToolMessage 对（需 tool_call_id 关联） |
| 编排控制 | 自研 for 循环 ← 完全相同 | 自研 for 循环 ← 完全相同 |
| 记忆注入 | memory.get_relevant() ← 完全相同 | 直接从 context 读取 |
| 步数限制 | max_steps ← 完全相同 | max_steps ← 完全相同 |

**当前项目默认使用正则解析后端**。要切换到 FC 后端，只需在配置中设置 `use_function_calling=True`，并在 AgentService 初始化时注入 FunctionCallAgent（当前已创建但只有在配置开启时才使用）。

## 二、RAG：与 Agent 管道的平行系统

### 2.1 RAG 不在 Agent 主流程中

一个常见的误解是 RAG 嵌在 Agent 流程内部——Agent 先检索知识库，再基于检索结果回答。**实际架构不是这样**。

RAG 和 Agent 是两套**平行系统**：

```
                    POST /chat/rag          POST /chat/agent
                         │                        │
                         ▼                        ▼
                    RAGService.chat()       AgentService.chat()
                         │                        │
                    ┌────┴────┐              ┌────┴────┐
                    │ 检索    │              │ 意图识别 │
                    │ (向量+  │              │ 模式路由 │
                    │  BM25+  │              │ 编排执行 │
                    │  RRF)   │              │ (ReAct/  │
                    │         │              │  Plan)   │
                    │ 生成    │              │ 工具调用 │
                    │ (引用)  │              │ 反思评估 │
                    └─────────┘              └─────────┘
```

**RAG 端点**（[chat.py:205-231](../app/api/routes/chat.py#L205-L231)）：检索知识库 → 基于检索的上下文生成带引用的回答。用已有文档回答问题。

**Agent 端点**（[chat.py:178-188](../app/api/routes/chat.py#L178-L188)）：意图识别 → 模式路由 → ReAct/Plan 循环 → 调用外部工具（如网络搜索）→ 生成回答。用工具和推理能力解决问题。

两者走不同的路由，调用不同的服务，互不嵌套。

### 2.2 RAG 和 Agent 的唯一切入点：kb_available

RAG 影响 Agent 行为的唯一途径是通过 ModeRouter 的 `kb_available` 标记：

```python
# agent_service.py:332-339
kb_available = False
if self._rag_service is not None:
    try:
        kb_available = self._rag_service.chunks_count > 0   # ← 知识库有内容吗？
    except Exception:
        pass
self._mode_router.kb_available = kb_available
```

这个标记被传入 LLM Router 的 prompt：

```python
# mode_router.py:93-115
def _build_router_user_prompt(..., kb_available, tool_names):
    return f"""...
## 上下文
- 知识库可用: {"是" if kb_available else "否"}   ← 影响 LLM 决策
- 可用工具: {", ".join(tool_names)}
..."""
```

**影响逻辑**：

- 如果 `kb_available=True`（用户上传过文档）：LLM Router 在判断模式时知道知识库有资料，某些简单知识问答可以用 react+RAG 路径快速回答
- 如果 `kb_available=False`（知识库为空）：需要外部信息的查询必须走 plan_execute 用搜索工具获取信息

### 2.3 RAG 如果接入 Agent，应该在哪个位置

虽然当前项目 RAG 和 Agent 是平行的，但架构上预留了集成点。如果要让 Agent 在回答时自动检索知识库，接入位置是：

```
选项 A：作为 Agent 的一个工具
─────────────────────────────
Agent 的可用工具中增加 "rag_search" 工具
→ ReAct 循环中：Thought → Action: rag_search → Observation: 检索结果 → 继续推理

选项 B：注入到 ReAct 的 system prompt
──────────────────────────────────────
在构造 ReAct prompt 时，先调用 RAGService.search() 获取相关上下文
→ 类似记忆摘要的注入方式，附在 system prompt 中

选项 C：影响 ModeRouter 的决策（当前已实现）
─────────────────────────────────────────
如果 kb_available=True，ModeRouter 可能倾向于 react（直接从知识库获取答案）
如果 kb_available=False，ModeRouter 可能倾向于 plan_execute（需要搜索工具）
```

当前采用选项 C，且已实现。选项 A 和 B 是可能的扩展方向。

## 三、短期记忆：每轮对话的上下文注入

### 3.1 短期记忆读在哪里

短期记忆在 **ReActAgent.run() 的第一步** 被读取，发生在每一次 ReAct 循环开始之前。

源码位置：[react_agent.py:187-194](../app/core/agent/react_agent.py#L187-L194)：

```python
async def run(self, query, context):
    # ... 参数初始化 ...

    # ═══════════ ① 读取记忆 ═══════════
    mem_snippets: List[str] = []
    if self._memory is not None:
        try:
            mem_snippets = await self._memory.get_relevant(
                session_id, query, limit=8   # ← 取最近 8 条
            )
        except Exception:
            logger.warning("读取记忆失败，将继续无记忆上下文")

    mem_block = "\n".join(f"- {s}" for s in mem_snippets) if mem_snippets else "（无）"

    # ═══════════ ② 注入到 system prompt ═══════════
    for step_idx in range(self.max_steps):
        messages = [
            {
                "role": "system",
                "content": REACT_SYSTEM_PROMPT
                    + ("\n\n" + extra_system if extra_system else "")
                    + f"\n\n## 检索记忆摘要\n{mem_block}",    # ← 记忆在这里！
            },
            {"role": "user", "content": user_prompt},
        ]
        # ... LLM 调用 ...
```

**最终 LLM 收到的 system prompt 大概长这样**：

```
你是严谨的智能助手，使用 ReAct 方式回答问题。
[子任务] 当前识别意图：知识问答，槽位：{'numbers': ['三个']}

## 检索记忆摘要
- user: 我父亲有糖尿病，最近在考虑保健品
- assistant: 了解，建议在选择保健品时特别注意糖分含量
- user: 有没有什么推荐？
- assistant: 可以选择无糖配方的维生素和矿物质补充剂
- user: 帮我搜一下最近 AI Agent 领域有什么新突破，然后总结成三个要点
（本次查询，在构造 prompt 之前单独处理）

## 可用工具
- web_search: 搜索互联网获取实时信息
- calculator: 数学计算
```

### 3.2 短期记忆写在哪里

每次对话完成后，AgentService 将用户消息和助手回复写入记忆：

```python
# agent_service.py:364-372
# ① 写用户消息
await self._memory.append_turn(session_id, "user", user_text)

# ② 写助手回复
if agent_resp.answer:
    await self._memory.append_turn(
        session_id, "assistant", agent_resp.answer,
        metadata={"trace_id": trace_id, "agent_mode": agent_resp.mode_used},
    )
```

触发 PersistentMemoryManager 的三写：**内存同步 + Redis 异步 + PostgreSQL 异步**。

### 3.3 写了之后，下一次对话就看到了

```
第一轮对话：
  用户: "我父亲有糖尿病"
  → 写记忆: {role: "user", content: "我父亲有糖尿病"}
  → 写记忆: {role: "assistant", content: "了解，请问有什么具体问题？"}

第二轮对话（同一个 session_id）：
  用户: "推荐什么保健品"
  → 读记忆: get_relevant(session_id, "推荐什么保健品", limit=8)
  → 返回最近 8 条格式化字符串，包含第一轮的对话
  → 注入 system prompt: "## 检索记忆摘要\n- user: 我父亲有糖尿病\n- assistant: 了解..."
  → LLM 看到记忆中有"糖尿病"信息 → 回答会结合这个上下文
```

**短期记忆的影响范围**：仅在同一个 `session_id` 内有效。不同会话之间的短期记忆是隔离的。

## 四、长期语义记忆：跨会话的向量召回

### 4.1 长期记忆在哪里被读取

长期记忆不是在 ReActAgent 中直接调用的——它由 **PersistentMemoryManager** 在 `get_relevant()` 内部自动叠加。

源码位置：[persistent_memory.py:225-248](../app/core/persistent_memory.py#L225-L248)：

```python
async def _append_long_term(self, short_items, session_id, query, limit):
    """在短期记忆的基础上，叠加上层长期语义记忆。"""
    if self._long_term is None:
        return short_items         # ← 没有长期记忆，直接返回短期记忆

    try:
        # ═══════════ ① 语义召回 ═══════════
        ltm_items = await self._long_term.recall(
            query,          # ← 用当前 query 做语义搜索
            session_id,     # ← 只召回当前会话的记忆（session_id 过滤）
            top_k=3         # ← 取最相似的 3 条
        )
        # ════════════════════════════════════

        if ltm_items:
            semantic = [
                f"[历史记忆] {item.content}"    # ← [历史记忆] 前缀标识
                for item in ltm_items
                if hasattr(item, "content")
            ]
            # ═══════════ ② 插入最前面 ═══════════
            combined = semantic + short_items
            return combined[:limit]             # ← 截断到 limit 条
    except Exception:
        logger.warning("长期语义记忆召回失败，跳过")

    return short_items
```

### 4.2 长期记忆的底层实现

`LongTermMemory.recall()` 内部做的是 **Milvus 向量搜索 + session_id 过滤**（[long_term.py:110-154](../app/core/memory/long_term.py#L110-L154)）：

```python
async def recall(self, query, session_id, top_k=5):
    # ① query 向量化
    vec = self._embed.embed_query("推荐什么保健品")

    # ② 构造过滤表达式（只搜当前会话的记忆）
    expr = f'session_id == "{session_id}"'

    # ③ Milvus 向量搜索
    out = self._coll.search(
        data=[vec],                              # 查询向量 (384-dim)
        anns_field="embedding",                  # ANN 检索字段
        param={"metric_type": "L2", "params": {"nprobe": 16}},
        limit=top_k,
        expr=expr,                               # ← 会话过滤！
        output_fields=["pk", "content", "meta"],
    )

    # ④ 解析返回
    items = []
    for hit in out[0]:
        items.append(MemoryItem(
            id=hit.entity.get("pk"),
            content=hit.entity.get("content"),    # ← "用户父亲有糖尿病史，需注意糖分摄入"
            score=hit.distance,
            metadata=json.loads(hit.entity.get("meta")),
        ))
    return items
```

### 4.3 长期记忆如何被写入

长期记忆需要**显式调用** `store()` 写入——不是每条消息都自动写入长期记忆。这是一条"需要保留"的信号。

```python
# long_term.py:77-108
async def store(self, session_id, content, metadata):
    memory_id = str(uuid.uuid4())
    vec = self._embed.embed_query(content)

    row = {
        "pk": memory_id,
        "embedding": vec,
        "content": content,         # ← 要记住的事实
        "session_id": session_id,   # ← 所属会话
        "meta": json.dumps(meta),
    }
    self._coll.insert([row])
    self._coll.flush()
```

**什么时候写**：通常由上层业务逻辑决定——比如 Agent 检测到用户提供了重要的个人信息（病史、偏好、背景），主动调用 `ltm.store()` 保存。当前项目中这个触发逻辑尚未在 Agent 主流程中自动化，需要手动调用或由特定业务规则触发。

### 4.4 短期记忆 vs 长期记忆：注入效果对比

以同一个用户的第三轮对话为例，两者的**同时存在**效果：

```
## 检索记忆摘要

[历史记忆] 用户父亲有糖尿病史，医生建议控制糖分摄入         ← 长期记忆（Milvus 语义召回）
[历史记忆] 用户本人对青霉素过敏                             ← 长期记忆（Milvus 语义召回）

user: 我最近在关注健康                                     ← 短期记忆（Redis，最近 8 条）
assistant: 好的，有什么具体问题？
user: 父亲的糖尿病管理有什么注意点？
assistant: 主要是饮食控制和定期监测血糖...
user: 帮我搜一下最近 AI Agent 领域有什么新突破               ← 当前 query
```

**两种记忆的区别一目了然**：

- `[历史记忆]` 前缀的内容来自 Milvus 向量搜索——可能是 3 天前另一轮对话中用户提到的信息。它们靠语义相似度被召回（"糖分"→"保健品"→"健康"），而不是时间顺序。
- 不带前缀的内容来自 Redis 短期记忆——按时间倒序取最近 8 条。它们是当前对话窗口内的消息。
- 语义记忆**插入最前面**（重要性最高），短期记忆跟在后面。

### 4.5 长期记忆的初始化

长期记忆在 AgentService 初始化时创建，但如果 Milvus 不可用则跳过：

```python
# agent_service.py:162-215
try:
    from pymilvus import MilvusClient

    _ltm_client = MilvusClient(settings.milvus_db_path)
    _ltm_coll_name = "long_term_memory"
    if not _ltm_client.has_collection(_ltm_coll_name):
        _ltm_client.create_collection(
            collection_name=_ltm_coll_name,
            dimension=384,
            metric_type="COSINE",
        )

    # 适配器桥接 MilvusClient → Collection 接口
    _ltm_coll = _LTMCollectionAdapter(_ltm_client, _ltm_coll_name)
    ltm = LongTermMemory(milvus_collection=_ltm_coll, embedding_model=_ltm_embed)
    self._memory.set_long_term(ltm)    # ← 注入 PersistentMemoryManager
except Exception:
    logger.warning("长期语义记忆不可用，跳过")
    # ← 长期记忆为 None，_append_long_term() 直接返回短期记忆，无感知降级
```

## 总结

| 机制 | 在哪一步 | 干了什么 | 代码入口 |
|------|----------|----------|----------|

| **短期记忆** | ReActAgent 每轮循环开始前 | 取最近 8 条注入 system prompt；每次对话结束写入 | 读: [react_agent.py:188-194](../app/core/agent/react_agent.py#L188-L194)；写: [agent_service.py:365-372](../app/core/agent_service.py#L365-L372) |
