## 一、Agent 任务规划与执行框架（Q1-Q8）

### Q1：为什么设计两种 Agent 模式（ReAct 和 Plan-and-Execute），而不是统一成一种？

**答**：两种模式对应两类本质不同的任务：

| 维度 | ReAct | Plan-and-Execute |
|------|-------|-------------------|
| 适用场景 | 单步工具调用、闲聊、简单计算 | 多步协作、搜索+分析+整合 |
| 执行方式 | Thought→Action→Observation 单循环 | 先规划子任务列表，再逐个以 ReAct 执行 |
| 延迟 | 低，直接进入执行 | 高，多一次规划 LLM 调用 |
| 容错 | 单步失败即结束 | 子任务失败可重规划 |

统一成一种的代价：如果只用 ReAct，复杂任务缺乏全局规划容易跑偏；如果只用 Plan-and-Execute，简单问题（如"你好"）白白多一次规划调用。

**代码位置**：[orchestrator.py](../app/core/agent/orchestrator.py) — `OrchestrationMode = Literal["react", "plan_execute"]`

### Q2：ModeRouter 的具体决策流程是怎样的？规则快路径和 LLM Router 如何分工？

**答**：三段式决策，延迟递增、可靠性递减：

```
用户输入 → 意图识别 → ModeRouter
                         │
                         ├── 1. 规则快路径（命中则直接返回，0 延迟）
                         │      查 _INTENT_MODE_RULES 映射表
                         │      例：数学计算 conf≥0.70 → react
                         │      特殊逻辑：知识问答含时间敏感词 → 升级为 plan_execute
                         │
                         ├── 2. LLM Router（规则未命中或置信度不足时触发）
                         │      将意图、置信度、槽位、可用工具打包为 prompt
                         │      调用 LLM 做二分类（react / plan_execute）
                         │
                         └── 3. 兜底 → react（最安全默认）
```

**规则表设计**（[mode_router.py](../app/core/agent/mode_router.py#L42-L48)）：

```python
_INTENT_MODE_RULES = {
    "数学计算": ("react", 0.70),
    "实时搜索": ("plan_execute", 0.70),
    "闲聊对话": ("react", 0.0),    # threshold=0 表示不设门槛
    "知识问答": ("react", 0.0),
    "文档管理": ("react", 0.0),
}
```

**为什么设置两层**：规则快路径覆盖 80% 常见场景（零 token 消耗），LLM Router 仅处理模糊边界，避免每次都调用 LLM。

### Q3：Plan-and-Execute 中执行阶段的每个子任务为什么也要走 ReAct，而不是直接调工具？

**答**：这是架构设计的关键决策——**执行 = ReAct 循环**，而不是简单的一次性工具调用。

原因：
1. **子任务本身可能需要多步推理**：即使规划出了"搜索最新 AI Agent 进展"，执行时也需要 Thought（判断搜什么关键词）→ Action（调用搜索工具）→ Observation（看结果够不够）→ 可能再搜一次
2. **保持架构一致性**：规划和执行两个阶段解耦，执行层可以统一优化（切换正则解析/FC 后端），不影响规划层
3. **每个子任务有独立的 max_steps 限制**，防止单个子任务跑偏

**代码位置**：[orchestrator.py](../app/core/agent/orchestrator.py#L300-L316) — `react_factory` 回调，每个子任务调用 `_invoke_react()`

### Q4：Function Calling 为什么不算第三种 Agent 模式？

**答**：Function Calling 是**工具调用的实现机制**，不是执行范式。

```
ReAct 模式
  ├── 后端 A：正则解析（parse Thought/Action/Action Input 文本）
  └── 后端 B：Function Calling（LLM 原生 tool_calls，通过 LangChain bind_tools）

Plan-and-Execute 模式
  └── 执行阶段 → 复用 ReAct（自动继承其后端选择）
```

两种后端的效果是一样的（都是 Thought→Action→Observation 循环），区别在于：
- **正则解析**：不依赖特定 API，可适配任何模型
- **Function Calling**：利用模型原生的 tool_calls 能力，结构化更好，但绑定了 OpenAI 风格 API

**切换方式**：`config.use_function_calling = True` → `orchestrator.set_function_call_agent(fc_agent)`

**代码位置**：[orchestrator.py](../app/core/agent/orchestrator.py#L174-L188) — `_invoke_react()` 中根据配置选择后端

### Q6：如何限制 ReAct 循环不跑飞？循环终止条件有哪些？

**答**：三层防护：

1. **硬限制 `max_steps`**（默认 10）：ReAct 循环超过此次数直接终止，返回已收集的部分结果
2. **Final Answer 自然终止**：LLM 输出 `Final Answer: xxx` 时正常结束
3. **重复检测（隐式）**：通过 Reflection 评估质量，低质量结果会标记但不阻塞返回

```python
# react_agent.py 核心循环
for step in range(max_steps):
    thought, action, action_input, final_answer = self._parse_react_step(response)
    if final_answer:
        return AgentResult(success=True, final_answer=final_answer, ...)
    observation = await tools.invoke(action, action_input)
    # ... 继续下一轮
```

Plan-and-Execute 额外还有 `max_replan_attempts`（默认 2），防止无限重规划。

### Q7：Reflection（反思评估）是怎么做的？评估了哪些维度？

**答**：在 Agent 生成答案后，用一个独立的评估 LLM 调用对答案质量打分。评估维度：

- **准确性**：是否基于实际工具返回结果，有无编造
- **完整性**：是否回答了用户的所有问题
- **幻觉检测**：`likely_hallucination` 标记 — 当答案与工具观测结果不一致时触发
- **质量评分**：0-100，低于 `reflection_min_quality`（默认 60）时标记

**代码位置**：[reflection.py](../app/core/agent/reflection.py) — `ReflectionAgent.reflect()`，通过 `ReflectionReport` 返回评估结果。

## 二、混合 RAG 知识增强模块（Q9-Q14）

### Q9：为什么选择 BM25 + 向量检索的混合方案，而不是纯向量检索？

**答**：两者互补——向量检索擅长语义匹配，BM25 擅长精确关键词匹配。

| 场景 | 纯向量 | 纯 BM25 | 混合 |
|------|--------|---------|------|
| "高血压的饮食建议" | ✅ 语义匹配好 | ❌ 可能漏掉"血压"相关 | ✅ |
| "阿司匹林 禁忌症" | ❌ 语义漂移可能返回不相关内容 | ✅ 精确关键词命中 | ✅ |
| "这个药怎么吃"（口语化） | ✅ 理解口语意图 | ❌ "吃"字匹配不到药名 | ✅ |

**代码位置**：[rag_service.py](../app/core/rag_service.py#L638-L656) — 支持 `vector` / `keyword` / `hybrid` 三种模式，默认 hybrid。

### Q10：RRF 融合排序的具体公式是什么？为什么 k 取 60？

**答**：RRF（Reciprocal Rank Fusion）公式：

```
RRF_score(doc) = Σ( 1 / (k + rank_in_channel + 1) )
```

- 向量检索和 BM25 各取 `top_k × 2` 条结果
- 对每条文档在两路中的排名分别计算 RRF 分数后相加
- 按融合分数降序取最终 top_k

**k=60 的原因**：这是 RRF 原始论文的经验值。k 越大，两路的权重越接近（排名差异的影响越小）；k 越小，高排名文档的优势越大。60 是经过大量实验验证的平衡点。

```python
# rag_service.py:332-353
rrf_k = 60
scores: dict[str, float] = {}
for rank, r in enumerate(vec_results):
    scores[r.id] = 1.0 / (rrf_k + rank + 1)
for rank, r in enumerate(kw_results):
    scores[r.id] = scores.get(r.id, 0.0) + 1.0 / (rrf_k + rank + 1)
```

### Q11：文档分块用了什么策略？chunk_size 和 overlap 怎么选的？

**答**：实现了 4 种分块策略，默认使用递归分块：

| 策略 | 逻辑 | 适用场景 |
|------|------|----------|
| `fixed` | 固定字符窗口 | 简单场景 |
| `recursive`（默认） | 按 `\n\n → \n → 。 → . → 空格` 优先级递归切分 | 通用中文文档 |
| `paragraph` | 按空行分段后合并 | 结构化文档 |
| `langchain` | LangChain RecursiveCharacterTextSplitter | 需要与 LangChain 生态对齐时 |

**参数选择**：`chunk_size=512, chunk_overlap=64`

- **512 token**：基于 `all-MiniLM-L6-v2` 的上下文窗口（最大 256 token 输入，512 块保证单块不会过长且保留足够语义）
- **overlap=64（12.5%）**：防止关键信息被切在边界上丢失，12.5% 是常见实践平衡点

使用 tiktoken `cl100k_base` 编码器精确计算 token 数，中文按字符近似。

**代码位置**：[chunker.py](../app/etl/chunker.py) — `DocumentChunker` 类

### Q12：为什么选 all-MiniLM-L6-v2 作为嵌入模型？

**答**：综合考量四个维度：

| 维度 | all-MiniLM-L6-v2 | 备选方案 |
|------|------------------|----------|
| 维度 | 384（小，存储友好） | text-embedding-3-large: 3072 |
| 速度 | ~1400 sentences/sec（CPU 友好） | OpenAI API 有网络延迟 |
| 中文支持 | 多语言训练，中文可用 | 纯英文模型不可用 |
| 成本 | 免费，本地运行 | API 按 token 计费 |
| 质量 | MTEB 排名中上 | 不如专用中文模型（如 bge-large-zh） |

**妥协之处**：作为面试项目选型合理，生产环境中文场景可能换 `BAAI/bge-large-zh-v1.5`（1024 维，中文 SOTA）。

### Q13：Milvus 不可用时怎么处理？

### Q14：RAG 生成答案时的引用标注是怎么做的？

**答**：三步流程：

1. **上下文编号**：检索结果按 `[1] [2] ... [n]` 编号后拼入 prompt
2. **LLM 生成**：要求模型在引用时使用 `[n]` 标注
3. **后解析**：用正则 `\[(\d+)\]` 从答案中提取引用索引，映射回 `RetrievalResult` 生成 `Citation` 对象（含 result_id + 前 200 字符 snippet）

```python
# generator.py:79-93
def _extract_citations(self, answer, contexts):
    refs = [int(x) for x in re.findall(r"\[(\d+)\]", answer)]
    citations = []
    for idx in set(refs):  # 去重
        if 1 <= idx <= len(contexts):
            r = contexts[idx - 1]
            citations.append(Citation(index=idx, result_id=r.id, snippet=r.content[:200]))
    return citations
```

## 三、多层记忆管理机制（Q15-Q18）

### Q15：四层记忆架构各层的职责和优先级是什么？

**答**：记忆读取优先级：**Milvus 长期语义 > Redis 短期 > PostgreSQL 冷存储 > 内存兜底**

```
┌─────────────────────────────────────────┐
│ Layer 0: LongTermMemory (Milvus)        │  ← 语义向量召回，跨会话
│   存储：向量 embedding                  │     重要性最高，插入结果最前面
├─────────────────────────────────────────┤
│ Layer 1: ShortTermMemory (Redis)        │  ← 热路径，滑动窗口
│   存储：JSON 序列化消息                  │     LLM 自动摘要压缩
├─────────────────────────────────────────┤
│ Layer 2: SessionRepository (PostgreSQL) │  ← 冷存储，持久化
│   存储：Conversation + Message 表       │     支持历史回溯
├─────────────────────────────────────────┤
│ Layer 3: _InMemoryMemoryManager (dict)  │  ← 最终兜底
│   存储：Python dict                     │     进程重启即丢失
└─────────────────────────────────────────┘
```

**代码位置**：[persistent_memory.py](../app/core/persistent_memory.py#L194-L223) — `get_relevant()` 按优先级逐层尝试

### Q16：LLM 摘要压缩的触发条件和策略是什么？

**答**：两个触发条件（满足任一即触发）：

1. **消息数超过窗口**：`n > window_size (20)`
2. **总 Token 超过阈值**：`total_tokens > max_tokens (4000)`，使用 tiktoken `cl100k_base` 精确计算

**压缩策略**：

```
┌─────────────────────────────────────────────────────┐
│ 原始 25 条消息                                        │
│ [msg1] [msg2] ... [msg17] [msg18] ... [msg25]       │
│ ◄────── to_summarize ──────► ◄─── keep=10 ───►      │
│         调用 LLM 压缩              保留不压缩          │
└─────────────────────────────────────────────────────┘
│
▼
┌─────────────────────────────────────────────────────┐
│ 压缩后 11 条                                          │
│ [摘要(role=system)] [msg18] ... [msg25]              │
└─────────────────────────────────────────────────────┘
```

- **保留尾部**：`keep = max(2, window_size // 2)` = 10 条，保证最近上下文不丢失
- **摘要 Prompt**："请将以下对话压缩为简洁中文摘要，保留关键事实与用户意图"
- **存储方式**：摘要以 `role=system` 身份插入，`metadata` 记录 `compressed_from`（原始消息数）

**代码位置**：[short_term.py](../app/core/memory/short_term.py#L106-L145)

### Q17：长期语义记忆（LongTermMemory）和短期记忆的本质区别是什么？

**答**：

| 维度 | 短期记忆 | 长期语义记忆 |
|------|----------|--------------|
| 存储引擎 | Redis List | Milvus 向量数据库 |
| 检索方式 | 时间倒序取最近 N 条 | 语义向量相似度召回 |
| 生命周期 | 单会话内，压缩后逐渐淘汰 | 跨会话持久化 |
| 召回策略 | `lrange` 取尾部 | `search` + `session_id` 过滤 |
| 适用信息 | 本轮对话上下文 | 用户偏好、历史重要事实 |
| 相似度 | — | COSINE / L2 |

**实际应用场景**：用户 3 天前说过"我父亲有糖尿病史"，今天问"推荐什么保健品"——短期记忆里没有，但长期语义记忆通过 `recall("保健品 健康建议", session_id)` 能召回"糖尿病史"相关信息。

**代码位置**：[long_term.py](../app/core/memory/long_term.py) — `LongTermMemory.recall()` / `store()`

### Q18：记忆模块写入是双写还是单写？如何保证一致性？

**答**：采用**三写策略**——内存兜底同步写入 + PG/Redis 异步写入，不强求一致性：

```python
# persistent_memory.py:250-273
async def append_turn(self, session_id, role, content, metadata=None):
    # 1. 内存兜底：同步写入（始终成功）
    await self._fallback.append_turn(session_id, role, content, metadata)
    # 2. PostgreSQL：异步写入（失败仅日志警告，不阻塞）
    if self._pg_ok:
        try:
            await self._pg.add_message(session_id, role, content, metadata)
        except Exception: ...
    # 3. Redis：异步写入（失败仅日志警告）
    if self._redis_ok:
        try:
            await self._redis_stm.append_turn(session_id, role, content, metadata)
        except Exception: ...
```

**一致性策略**：最终一致性。对话场景对实时一致性要求不高（读操作优先热路径 Redis），PG 短暂不同步不影响用户体验。

## 四、系统设计与综合（Q19-Q20）

### Q19：整个系统的请求链路是怎样的？从用户发消息到返回结果。

**答**：

```
POST /api/agent/chat
        │
        ▼
┌──────────────────────────────────────────────────┐
│ AgentService.chat(request)                        │
│                                                   │
│ 1. IntentRecognizer.recognize(user_text)          │
│    ├── LLM 分类（优先）                            │
│    └── 关键词降级（LLM 失败时）                     │
│                                                   │
│ 2. ModeRouter.resolve(query, intent_result)       │
│    ├── 规则快路径 → react / plan_execute          │
│    ├── LLM Router → react / plan_execute          │
│    └── 兜底 → react                               │
│                                                   │
│ 3. Orchestrator.run(user_input, session_id, mode) │
│    ├── mode == "react":                           │
│    │     _invoke_react()                          │
│    │       ├── FunctionCall 后端 (if configured)   │
│    │       └── 正则解析 ReAct 后端 (default)       │
│    │                                              │
│    └── mode == "plan_execute":                     │
│          _run_plan_execute()                       │
│            ├── PlannerAgent.run_with_replan()      │
│            │   ├── Plan: LLM → subtask list       │
│            │   ├── Execute: _invoke_react() 每子任务│
│            │   ├── Replan: 必要时重规划             │
│            │   └── Summarize: LLM → final answer  │
│            └── 失败降级 → _invoke_react()          │
│                                                   │
│ 4. ReflectionAgent.reflect(query, answer)         │
│    └── 质量评分 + 幻觉检测                          │
│                                                   │
│ 5. Memory.append_turn (三写)                      │
│                                                   │
│ 6. 返回 AgentChatResponse                         │
│    (answer + trace_id + steps + intent + score)   │
└──────────────────────────────────────────────────┘
```

### Q20：如果给你两个月时间继续改进这个项目，你会做哪三件事？

**答**：

**1. 工具生态扩展与沙箱化（优先级最高）**

当前只有 2 个工具（计算器 + 搜索），生产级 Agent 需要：
- 代码解释器沙箱（Docker 隔离执行 Python/SQL）
- 更多 API 工具（天气、股票、日历等）
- 工具权限分级（只读/写入/敏感），用户确认机制
- 工具结果缓存（相同参数短时间内复用结果）

**2. 流式输出与用户体验优化**

当前是非流式（全量返回），用户体验差：
- SSE 流式输出 Thought/Action/Observation 每个阶段
- 前端实时展示 Agent 思考过程（类似 ChatGPT 的 "正在搜索..."）
- 用户可中断正在执行的 Agent 循环

**3. 评估体系与 A/B 实验**

当前只有 Reflection 自评，缺乏客观指标：
- 构建测试用例集（含预期工具调用序列和答案）
- 端到端准确率、工具调用正确率、幻觉率统计
- A/B 对比不同 LLM、不同 prompt、不同 chunk_size 的效果
- LangSmith / LangFuse 等可观测性平台接入
