## 一、意图识别

### 1.1 模块定位

意图识别是整个 Agent 管道的**第一站**。在用户消息到达后，任何工具调用或任务规划之前，系统必须先理解"用户想干什么"。

```
用户输入 → IntentRecognizer → IntentResult → ModeRouter → Orchestrator
```

意图识别器位于 [app/core/intent/recognizer.py](../app/core/intent/recognizer.py)，核心类 `IntentRecognizer`。

### 1.2 两段式识别：LLM 优先 + 关键词兜底

```
recognize(query)
    │
    ├── self._llm is not None?
    │   ├── YES → _llm_classify(query)
    │   │         │
    │   │         ├── 成功 → 返回 IntentResult（含 intent, confidence, slots, rationale）
    │   │         └── 异常 → 落入关键词降级
    │   │
    │   └── NO / 异常 → _keyword_classify(query)
    │                    └── 返回 IntentResult（含 sub_intent, 较低 confidence）
```

```python
# recognizer.py:197-236
async def recognize(self, query, context=None):
    if self._llm is not None:
        try:
            result = await self._llm_classify(query)
            return result       # ← LLM 成功
        except Exception:
            pass                # ← 落入关键词降级

    # 关键词降级
    intent, child, conf, why = _keyword_classify(query)
    return IntentResult(intent=intent, confidence=conf, sub_intent=child, rationale=why)
```

### 1.3 LLM 分类路径

**Prompt 设计**（[recognizer.py:27-64](../app/core/intent/recognizer.py#L27-L64)）：

```python
INTENT_CLASSIFY_PROMPT = """你是意图分类专家。分析用户输入，输出 JSON。

- 知识问答：询问概念、原理、对比、方法（什么/为什么/如何/区别）
- 实时搜索：需要最新资讯、新闻、事实核查（今天/最近/最新/2026）
```

### 1.4 关键词降级路径

当 LLM 不可用（网络故障、API 配额耗尽等），系统自动降级为**关键词规则匹配**。

**意图树结构**（[recognizer.py:70-91](../app/core/intent/recognizer.py#L70-L91)）：

```python
_INTENT_TREE = {
    "知识问答": {
        "概念原理": ["什么", "为什么", "如何", "解释", "含义", "区别", "对比", "哪个好", "原理"],
        "教程指导": ["怎么做", "步骤", "教程", "方法", "技巧"],
    },
    "实时搜索": {
        "新闻资讯": ["今天", "最近", "最新", "新闻", "2026", "2025", "目前", "当前", "实时"],
        "事实核查": ["真的吗", "是不是", "有没有"],
    },
    "数学计算": {
        "表达式计算": ["计算", "等于", "算一下", "+", "-", "*", "/"],
        "单位换算": ["换算", "多少", "等于多少"],
    },
    "文档管理": {
        "上传文档": ["上传", "导入", "文档", "pdf", "word"],
        "文档查询": ["文档列表", "有哪些文件", "已上传"],
    },
    "闲聊对话": {
        "日常寒暄": ["你好", "谢谢", "再见", "嗨", "哈喽", "hello"],
        "身份询问": ["你是谁", "你能做什么", "你叫什么"],
    },
}
```

**匹配逻辑**：遍历所有意图的所有子类别，统计关键词命中次数，取最高分。

```python
# recognizer.py:117-137
def _keyword_classify(query):
    q = query.strip().lower()
    best_intent = "知识问答"
    best_hits = 0
    for intent, children in _INTENT_TREE.items():
        for child, kws in children.items():
            hits = sum(1 for kw in kws if kw.lower() in q)
            if hits > best_hits:
                best_hits = hits
                best_intent = intent
                best_child = child

    if best_hits == 0:
        conf = 0.35 if ("?" in q or "？" in q) else 0.25
        return "知识问答", None, conf, "关键词未命中，弱规则推断"

    conf = min(0.95, 0.45 + 0.12 * best_hits)
    return best_intent, best_child, conf, f"关键词命中 {best_hits} 次"
```

**置信度公式**：`conf = min(0.95, 0.45 + 0.12 × hits)`

| 命中次数 | 置信度 |
|----------|--------|
| 1 | 0.57 |
| 2 | 0.69 |
| 3 | 0.81 |
| 4+ | 0.93+ → 0.95 cap |

关键词语义的置信度天然低于 LLM，且设置了 0.95 的上限（承认规则匹配的不确定性）。

### 1.5 置信度与澄清机制

当置信度低于阈值（默认 0.55），系统可以主动向用户发起澄清：

```python

        "请问您是想要：\n"
        "  • 知识问答（概念、原理、对比）\n"
        "  • 实时搜索（最新资讯、新闻）\n"
        "  • 数学计算\n"
        "  • 文档管理\n"
        "请补充更多信息。"
    )
```

### 1.6 意图识别结果的数据结构

```python
class IntentResult(BaseModel):
    intent: str              # "知识问答" | "实时搜索" | "数学计算" | "文档管理" | "闲聊对话"
    confidence: float        # 0.0 ~ 1.0
    slots: dict[str, Any]    # {"numbers": [...], "doc_action": "upload", "compare_entities": [...]}
    sub_intent: str | None   # 关键词模式下的子意图（如"概念原理"），LLM 模式为 None
    rationale: str           # "询问天气需要实时信息"
```

### 1.7 设计决策总结

| 决策 | 理由 |
|------|------|
| LLM 优先于规则 | LLM 理解语义，规则只匹配字面——"帮我看看这个"规则无法识别意图 |
| 关键词兜底 | API 故障时系统仍可用，用户无感知 |
| 5 类意图（而非 20 类） | 意图粒度与下游 Agent 模式匹配——过细的分类对路由无帮助 |
| temperature=0.1 | 分类不是创意任务，确定性 > 多样性 |
| 数字槽位正则兜底 | LLM 有时忘记填 numbers，正则 100% 可靠补充 |

## 二、模式路由（ModeRouter）

### 2.1 模块定位

ModeRouter 是意图识别和执行编排之间的**决策层**——根据意图分析结果，自动选择 ReAct（直接执行）还是 Plan-and-Execute（先规划再执行）。

```
IntentResult → ModeRouter.resolve() → ModeDecision → Orchestrator.run(mode=...)
```

核心代码位于 [app/core/agent/mode_router.py](../app/core/agent/mode_router.py)。

### 2.2 ModeRouter 在请求链路中的位置

```python
# agent_service.py:312-354
async def chat(self, request):
    # 1. 意图识别
    intent_result = await self._intent_recognizer.recognize(user_text)

    # 2. 模式选择
    _EXPLICIT_MODES = frozenset({"react", "plan_execute"})
    if requested_mode in _EXPLICIT_MODES:
        selected_mode = requested_mode          # 用户显式指定，跳过 Router
    else:
        decision = await self._mode_router.resolve(user_text, intent_result)
        selected_mode = decision.mode           # Router 自动决策

    # 3. 执行编排
    agent_resp = await self._orchestrator.run(mode=selected_mode, ...)
```

用户可以在请求中通过 `agent_mode` 参数显式指定模式——这是给前端/高级用户的手动超控。未指定（默认 `"auto"`）时走 ModeRouter。

### 2.3 三段式决策管道

```
意图识别结果 + 用户查询
        │
        ▼
┌──────────────────────────────────────────────────────┐
│  第一道：规则快路径 (source="rule")                    │
│  ───────────────────────────────────────────────     │
│  条件：意图在 _INTENT_MODE_RULES 中                     │
│        && confidence ≥ 0.50（全局底线）                │
│        && confidence ≥ 该意图门槛                      │
│                                                      │
│  命中 → 0 token 消耗，0 延迟返回                       │
│  未命中 → 进入第二道                                   │
└──────────────────────────────────────────────────────┘
        │ (未命中)
        ▼
┌──────────────────────────────────────────────────────┐
│  第二道：LLM Router (source="llm_router")             │
│  ───────────────────────────────────────────────     │
│  条件：self._llm is not None                          │
│                                                      │
│  命中 → 1 次 LLM 调用（约 200-500 token）              │
│  异常 → 进入第三道                                    │
└──────────────────────────────────────────────────────┘
        │ (LLM 不可用或调用失败)
        ▼
┌──────────────────────────────────────────────────────┐
│  第三道：兜底 (source="fallback")                     │
│  ───────────────────────────────────────────────     │
│  条件：无条件（最后防线）                               │
│  → 直接返回 mode="react", confidence=0.0              │
└──────────────────────────────────────────────────────┘
```

**源码对应**（[mode_router.py:160-201](../app/core/agent/mode_router.py#L160-L201)）：

```python
async def resolve(self, query, intent_result) -> ModeDecision:
    # 1. 规则快路径
    decision = self._rule_resolve(query, intent_result)
    if decision is not None:
        return decision   # ← source="rule", 零 token

    # 2. LLM Router
    if self._llm is not None:
        try:
            decision = await self._llm_resolve(query, intent_result)
            return decision   # ← source="llm_router"
        except Exception:
            pass              # ← 异常落入兜底

    # 3. 最终兜底
    return ModeDecision(mode="react", source="fallback", confidence=0.0)
```

### 2.4 第一道闸门：规则快路径

#### 规则映射表

```python
# mode_router.py:42-48
_INTENT_MODE_RULES: dict[str, tuple[str, float]] = {
    "数学计算": ("react", 0.70),           # 单步计算，ReAct 直接调计算器
    "实时搜索": ("plan_execute", 0.70),    # 搜索→筛选→整合，多步
    "闲聊对话": ("react", 0.0),            # 无需工具，直接回答
    "知识问答": ("react", 0.0),            # LLM 直接回答
    "文档管理": ("react", 0.0),            # 单步上传/删除/列表
}
```

- `threshold=0.70`：数学计算和实时搜索——特征明确但容易误判，高门槛保证信任
- `threshold=0.0`：闲聊和知识问答——即使低置信度，用 ReAct 也是安全的默认

#### 三层过滤逻辑

```python
# mode_router.py:207-245
def _rule_resolve(self, query, intent_result) -> ModeDecision | None:

    # 过滤1：意图在映射表中
    pair = _INTENT_MODE_RULES.get(intent_result.intent)
    if pair is None:
        return None   # 未知意图 → LLM Router

    mode, threshold = pair

    # 过滤2：全局底线 0.50
    if intent_result.confidence < 0.50:
        return None   # 置信度过低 → LLM Router

    # 过滤3：意图特定门槛
    if threshold > 0 and intent_result.confidence < threshold:
        return None   # 低于门槛 → LLM Router
```

#### 特殊规则：知识问答的时间敏感升级

```python
_TIME_SENSITIVE_KW = {"今天", "最近", "最新", "目前", "当前", "实时", "新闻", "2025", "2026"}

if intent_result.intent == "知识问答":
    if any(kw in query for kw in _TIME_SENSITIVE_KW):
        return ModeDecision(
            mode="plan_execute",    # ← 覆盖查表结果！需要搜索+整合
            source="rule",
            rationale="知识问答含时间敏感词，升级为 plan_execute 多步搜索",
            confidence=intent_result.confidence,
        )
```

**场景**：用户问"最近 AI Agent 有什么新进展"——意图分类器可能因"什么"关键词将其分到"知识问答"（概念原理），但实际需要搜索最新资讯。此规则在路由层修正了意图分类的边界错误。

### 2.5 第二道闸门：LLM Router

#### 触发条件

| 场景 | 示例 | 未命中原因 |
|------|------|-----------|
| 意图在映射表中但置信度过低 | 意图=数学计算, conf=0.45 | 低于全局底线 0.50 |
| 意图在映射表中但低于特定门槛 | 意图=实时搜索, conf=0.55 | 低于 0.70 的门槛 |
| 意图不在映射表中 | LLM 分类出了未知标签 | 映射表无匹配 |

#### Prompt 设计

```python
# mode_router.py:61-90
ROUTER_SYSTEM_PROMPT = """你是 Agent 模式路由器。根据意图分析结果，选择最合适的 Agent 执行模式。

## 可选模式
- react: 思考→行动→观察循环。适合简单问答、闲聊、单步工具调用。
- plan_execute: 先规划再逐步执行（每个子任务走 ReAct 循环），失败时重规划。适合多步复杂任务。

## 决策原则
1. 需要多步协调（搜索+分析+整合）→ plan_execute
2. 简单问答、闲聊、单步计算 → react
3. 意图不明确时保守选择 react
"""
```

#### 输入上下文（比规则引擎多 4 个维度）

```python
# mode_router.py:93-115
def _build_router_user_prompt(query, intent, confidence, sub_intent, slots,
                               kb_available, tool_names):
    return f"""## 用户查询
{query}

## 意图分析结果
- 主意图: {intent}
- 置信度: {confidence:.2f}
- 子意图: {sub_intent or "无"}
- 槽位: {json.dumps(slots)}           ← 规则引擎看不到的结构化信息

## 上下文
- 知识库可用: {"是" if kb_available else "否"}   ← 影响是否需要搜索
- 可用工具: {", ".join(tool_names)}               ← 工具能力影响模式选择

请选择最合适的执行模式并输出 JSON。"""
```

**LLM Router 能利用规则引擎不具备的 4 个维度**：

| 额外信息 | 如何影响决策 |
|----------|-------------|
| `sub_intent` | "教程指导"比"概念原理"更可能需要多步编排 |
| `slots` | 槽位中有多个实体（如 compare_entities）暗示对比任务，需要多步 |
| `kb_available` | 知识库有资料时，某些搜索意图可以直接走 RAG，不需要 plan_execute |
| `tool_names` | 只有计算器没有搜索工具时，"实时搜索"意图也不该走 plan_execute |

### 2.7 完整决策示例

```
示例 1: "帮我算 (123+456)*789"
  意图 → 数学计算 conf=0.95
  → 规则快路径：映射命中 ✅，0.95 ≥ 0.70 ✅
  → ModeDecision(mode="react", source="rule", confidence=0.95)  [0 token]

示例 2: "你好呀"
  意图 → 闲聊对话 conf=0.98
  → 规则快路径：映射命中 ✅，threshold=0 无额外门槛
  → ModeDecision(mode="react", source="rule", confidence=0.98)  [0 token]

示例 3: "最近 AI Agent 领域有什么新突破"
  意图 → 知识问答 conf=0.82 ("什么" 误导分类器)
  → 规则快路径：知识问答 → react，但检出 "最近" 时间敏感词！
  → 升级覆盖 → ModeDecision(mode="plan_execute", source="rule", ...)  [0 token]
        ↑ 规则修正了意图分类的边界错误

示例 4: "帮我搜一下今天有没有重大新闻，然后总结要点"
  意图 → 实时搜索 conf=0.55
  → 规则快路径：门槛 0.70，0.55 < 0.70 ❌
  → LLM Router：综合 query + 槽位 → plan_execute
  → ModeDecision(mode="plan_execute", source="llm_router", confidence=0.80)  [~300 token]

示例 5: LLM API 全线故障
  意图 → 数学计算 conf=0.95
  → 规则快路径 ✅ 正常通过
  但如果规则也未命中：
  → LLM Router：调用失败 → 异常捕获
  → 兜底 → ModeDecision(mode="react", source="fallback", confidence=0.0)  [0 token]
        ↑ 系统继续运行，不崩溃
```

### 2.8 关键设计决策

| 决策 | 理由 |
|------|------|
| 规则 → LLM → 兜底，串行非并行 | 依次降级，每一步是下一步的 fallback |
| 规则内部仍有置信度门槛 | 低置信度意味着意图可能分类错误，交给 LLM Router 用更多上下文判断 |
| LLM Router temperature=0.1 | 路由不是创意任务，需要确定性 |
| 规则中包含硬编码特殊逻辑 | 时间敏感词这种高频边界 case，规则修正比重新训练意图分类器成本低 |
| 兜底→react 而非抛异常 | 降级优于失败，用户体验不受影响 |
| Function Calling 不是路由目标 | FC 是 ReAct 内部的工具调用实现，通过 config 控制，不参与模式决策 |

## 三、执行编排

### 3.1 模块定位

执行编排是 Agent 系统的**核心引擎**——接收 ModeRouter 的决策结果，实际驱动 LLM 完成工具调用和答案生成。

```
ModeDecision → Orchestrator.run(mode=...) → AgentResponse
                   │
      ┌────────────┴────────────┐
      │                         │
   mode="react"           mode="plan_execute"
      │                         │
  _invoke_react()         _run_plan_execute()
      │                         │
      │                    PlannerAgent.run_with_replan()
      │                         │
      │                    ┌─────┴──────┐
      │                    │  Plan       │
      │                    │  Execute    │──→ _invoke_react() × N
      │                    │  Replan     │
      │                    │  Summarize  │
      │                    └────────────┘
      │                         │
      └────────────┬────────────┘
                   │
            ReflectionAgent.reflect()
                   │
               AgentResponse
```

### 3.2 两种 Agent 范式

| 维度 | ReAct | Plan-and-Execute |
|------|-------|-------------------|
| 结构 | 单层循环：Thought→Action→Obs | 双层：规划层 + 执行层（每子任务走 ReAct） |
| LLM 调用次数 | 每次循环 1 次 | 1（规划） + N×M（N 子任务 × M 步/子任务） + 1（汇总） |
| 适用场景 | 单步工具调用、闲聊、简单计算 | 搜索+筛选+整合、对比分析、多源信息汇总 |
| 容错能力 | 单步失败即终止 | 子任务失败可重规划 |
| 延迟 | 低（无规划开销） | 高（多一次规划 + 汇总调用） |
| 路线修正 | 无（历史轨迹不可改） | 有（重规划机制） |

### 3.3 Orchestrator 主入口

### 3.4 ReAct 执行路径（`_invoke_react`）

这是两种模式**共享**的执行原语——react 模式直接用它，plan_execute 模式通过 `react_factory` 回调调用它来执行每个子任务。

```python
# orchestrator.py:147-190
async def _invoke_react(self, query, session_id, intent, trace_id, steps,
                         max_steps=10, suffix="", allowed_tools=None):
    ctx = {
        "session_id": session_id,
        "tool_names": allowed_tools or self._tool_names(intent),
        "tool_descriptions": getattr(self._tools, "get_tools_description", lambda: "")(),
        "trace_callback": trace_cb,
        "extra_system": suffix + f"当前识别意图：{intent.intent}，槽位：{intent.slots}",
    }

    # 根据配置选择 ReAct 后端
    if self._use_function_calling and self._fc_agent is not None:
        # ── Function Calling 后端 ──
        self._fc_agent.max_steps = max_steps
        result = await self._fc_agent.run(query, ctx)
    else:
        # ── 正则解析 ReAct 后端 ──
        llm = _LLMAdapter(self._model_router.get_llm("react"))
        agent = ReActAgent(llm=llm, tools=self._tools, memory=self._memory,
                           max_steps=max_steps, session_id=session_id)
        result = await agent.run(query, ctx)

    return result
```

```python
            # ← Observation 写入历史，下一轮 LLM 会看到
            continue

        # 5. 解析失败 → 返回错误
        return AgentResult(success=False, error="未解析到 Action 或 Final Answer")
```

**正则解析器**（[react_agent.py:101-139](../app/core/agent/react_agent.py#L101-L139)）：

```python
def _parse_react_step(text):
    # Thought: 匹配到下一个 Action:/Final Answer: 之前的所有内容
    thought_m = re.search(r"Thought:\s*(.+?)(?=\n(?:Action:|Final Answer:)|\Z)", text, re.S)

    # Final Answer: 匹配到文本末尾
    if re.search(r"Final Answer:\s*", text, re.I):
        fa_m = re.search(r"Final Answer:\s*(.+)\Z", text, re.S | re.I)
        ...

    # Action: 取一个非空白 token
    action_m = re.search(r"Action:\s*(\S+)", text, re.I)

    # Action Input: 优先匹配 JSON 对象，失败则宽松匹配到空行
    input_m = re.search(r"Action Input:\s*(\{[\s\S]*\})", text)
    ...
```

**解析的容错设计**：
- 大小写不敏感（`re.I`）
- 跨行匹配（`re.S`）
- Action Input 先尝试严格 JSON 匹配，失败后宽松匹配任意文本
- JSON 解析失败不崩溃，返回空字典 + `parse_error` 标记

#### 3.4.2 Function Calling 后端（可选配置）

位于 [function_call_agent.py](../app/core/agent/function_call_agent.py)。

Function Calling **不是第三种 Agent 模式**——它是 ReAct 的另一种工具调用实现。两者的编排逻辑完全相同（for 循环、步数上限、历史管理），区别仅在于 LLM 如何表达工具调用意图：

```
两种后端的对比：

正则解析：
  LLM 输出 → "Action: calculator\nAction Input: {\"expression\": \"1+1\"}"
           → 正则可解析，但不稳定（~10-15% 失败率）

Function Calling：
  LLM 输出 → AIMessage(tool_calls=[{"name": "calculator", "args": {"expression": "1+1"}}])
           → 原生结构化，失败率 ~0%
```

**FC 后端主循环**：

```python
# function_call_agent.py:99-185
async def run(self, query, context):
    for step_idx in range(self.max_steps):
        response = self._llm.invoke(messages)   # bind_tools 已注入 Schema

        if response.tool_calls:
            # 执行所有工具调用，将 AIMessage + ToolMessage 对加入历史
            for tc in response.tool_calls:
                obs = await self._invoke_tool(tc["name"], tc["args"])
                history.append(AIMessage(content=..., tool_calls=response.tool_calls))
                history.append(ToolMessage(content=obs, tool_call_id=tc["id"]))
            continue

        # 无 tool_calls → 最终答案
        return AgentResult(success=True, final_answer=response.content)

    return AgentResult(success=False, error="已达到最大步数限制")
```

**关键实现细节**：LangChain 只负责 `ChatOpenAI.bind_tools()`（让模型输出结构化 tool_calls），编排逻辑（循环控制、步数上限、历史消息管理、错误处理）全部自研。这是"用 LangChain 的零件，不用它的流水线"。

### 3.5 Plan-and-Execute 执行路径

**四阶段流程**（[planner.py:208-337](../app/core/agent/planner.py#L208-L337)）：

```
Plan-and-Execute = Plan → Execute(ReAct × N) → Replan? → Summarize
```

#### 阶段 1：制定计划（Plan）


#### 阶段 2：执行子任务（Execute）

每个子任务通过 `react_factory` 回调创建一个 ReAct 执行器执行：

```python
# orchestrator.py:300-316
async def react_factory(subtask_description, allowed_tools):
    subtask_steps = []
    result = await self._invoke_react(
        query=subtask_description,     # ← 子任务的 description 作为 ReAct 的 query
        allowed_tools=allowed_tools,    # ← 规划中 expected_tools 或全部工具
        suffix="[子任务] ",             # ← 标记这是子任务（日志/追踪用）
        max_steps=5,                    # ← 子任务步数限制（比纯 ReAct 的 10 更紧）
        ...
    )
    return result
```

**架构一致性保证**：Plan-and-Execute 的执行阶段**不是**直接调工具或直接调 LLM 推理——它是完整的 ReAct 循环。这意味着：
- 子任务"搜索最新进展"可能包含 Thought（判断关键词）→ Action（搜索）→ Observation → Thought（不够，换个角度搜）→ Action（再搜）→ Final Answer
- 每个子任务有独立的 `max_steps` 限制（默认 5）
- 每个子任务自动继承当前配置的 ReAct 后端（正则解析或 FC）

#### 阶段 3：重规划（Replan）

```python
# planner.py:239-306
for replan_attempt in range(self.max_replan_attempts + 1):  # 最多 2 次重规划
    for task in current_plan:
        result = await react_factory(task.description, ...)
        if not result.success:
            failed = True       # 标记失败但不立即中断——收集所有结果

    if not failed:
        break                   # 全部成功，不需要重规划

    if replan_attempt >= self.max_replan_attempts:
        break                   # 重规划次数耗尽

    # 调用 LLM 重新规划（基于已执行结果 + 错误信息）
    new_plan = await self.replan(query, current_plan, subtask_results)
    if not new_plan:
        break                   # LLM 返回空计划 → 认为已完成
    current_plan = new_plan
```

**重规划 prompt**（[planner.py:44-54](../app/core/agent/planner.py#L44-L54)）：

```python

若任务已完成，返回：
```

重规划时 LLM 会收到完整的上下文（原始问题 + 原计划 + 已执行每个子任务的结果 + 错误），可以：
- 调整失败子任务的执行方式
- 删除不再需要的子任务
- 新增补救子任务
- 返回空数组表示"已经够了"

### 3.7 异常降级全景

系统中有 **五条降级路径**，确保任何单点故障不影响用户体验：

| 编号 | 故障点 | 降级策略 | 用户感知 |
|------|--------|----------|----------|
| 1 | 意图识别 LLM 失败 | 关键词规则匹配 | 无（意图仍可识别） |
| 2 | ModeRouter LLM 失败 | 降级 react | 无（仍能处理） |
| 3 | Plan-and-Execute 规划/执行失败 | 降级纯 ReAct | 回答可能稍简略，`degraded=True` |
| 4 | 子任务执行失败 | 重规划（最多 2 次） | 可能多等几秒，结果更可靠 |
| 5 | 反思 LLM 调用失败 | 跳过反思，保守评分 | 无（反思是增值而非必需） |
| 6 | 记忆系统（Redis/PG）故障 | 纯内存 dict 兜底 | 无（数据不持久但功能正常） |

### 3.9 关键设计决策总结

| 决策 | 理由 |
|------|------|
| Plan 子任务执行复用 ReAct | 执行 = ReAct 循环是架构一致性原则——不是直接调 LLM 或直接调工具 |
| 子任务全部执行完再判断是否重规划 | 收集完整信息比提前中断更优——LLM 看到全部失败原因后能做出更好的重规划 |
| `summary_llm` 独立可配置 | 汇总和规划是不同任务——规划需要结构化输出（JSON），汇总需要自然语言 |
| 正则解析和 FC 后端用统一协议 | `_invoke_react()` 是统一入口，切换后端不影响上层 |
| 反思是增值而非阻塞 | 反思失败不抛异常，不阻塞回答返回——用户不需要等反思完成才能看到答案 |
| 五条独立降级路径 | 每条路径独立降级，互不影响——意图识别失败不影响执行，反思失败不影响答案返回 |
