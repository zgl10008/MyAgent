## 1. 项目概述

**心康助手**是一个面向心血管慢病管理的 AI Agent 项目，同时也是一个 **Agent 架构教学项目**——从零自研了 ReAct 编排引擎、RAG 混合检索管线、三层记忆架构、三态熔断器等核心组件。

### 核心能力

| 能力 | 说明 |
|------|------|
| **多范式 Agent** | 支持 2 种执行范式：`react`（纯 ReAct 循环）和 `plan_execute`（规划→执行→汇总）。`function_call` 是 ReAct 内部的可替换工具调用后端（正则解析 vs LangChain bind_tools），非独立模式 |
| **RAG 知识库** | 文档上传 → 自动分块 → 向量化 → 混合检索。★ 已打通为 Agent 的 `rag_search` 工具，Agent 可自主决定查知识库或搜网络；同时保留独立 `/chat/rag` 端点 |
| **三层记忆** | Redis 热路径（滑动窗口+摘要压缩）→ PostgreSQL 冷存储（持久化）→ 内存兜底 + 可选 Milvus 长期语义记忆 |
| **意图识别** | LLM few-shot 5 分类，LLM 不可用时关键词规则降级 |
| **模型路由** | 多模型加权随机负载均衡，每个模型独立三态熔断器（Closed→Open→Half-Open） |
| **反思评估** | 输出后自动质量评分（幻觉检测、完整性评估），低于阈值可触发重试 |
| **智能降级** | 基础设施不可用时自动降级：Milvus → 内存向量库、Redis → PG → 内存、LLM → 关键词规则 |

### 设计哲学

```
核心设计原则：
  1. Function Calling 不是 Agent 模式，是 ReAct 内部的工具调用实现升级
     → 两种范式 (react / plan_execute)，两种后端 (正则解析 / FC)
     → 通过 _invoke_react() 统一入口切换，上层逻辑无感知
  2. LangChain 只用在 bind_tools 这一个环节，其余编排、记忆、RAG、熔断全部自研
  3. RAG 不是独立端点——已打通为 Agent 的 rag_search 工具，Agent 可自主决定查知识库、搜网络或交叉验证
  4. 记忆分层：短期(Redis)负责当前会话上下文，长期(Milvus)负责跨会话语义召回
```

### 请求处理全链路

```
用户输入
  → 意图识别 (IntentRecognizer): "知识问答" / "数学计算" / ...
  → 模式路由 (ModeRouter):
      规则快路径 → react 或 plan_execute
  → Agent 编排器 (AgentOrchestrator):
      根据 mode 选择执行路径:
        react         → _invoke_react() → ReActAgent 或 FunctionCallAgent
                          ├── ★ 短期记忆读取: memory.get_relevant()
                          │     → Redis(热路径) → PG(冷存储) → 内存(兜底)
                          ├── ★ 长期记忆读取: _append_long_term()
                          │     → Milvus 语义向量召回 + session_id 过滤
                          ├── ★ FC 后端切换: use_function_calling?
                          │     YES → FunctionCallAgent (bind_tools)
                          │     NO  → ReActAgent (正则解析)
                          └── ★ 工具调用 (含 rag_search):
                                ReAct 循环中按需调用:
                                - calculator: 数学计算
                                - web_search: 互联网搜索
                                - rag_search: 知识库检索 (与web_search互补)
        plan_execute  → PlannerAgent.run_with_replan()
                          1. Plan: LLM 拆解子任务
                          2. Execute: 每个子任务 → _invoke_react() (同上)
                          3. Replan: 失败时重规划 (最多 2 次)
                          4. Summarize: LLM 汇总
  → 反思评估 (ReflectionAgent):
      对最终答案评分（质量分/幻觉检测/完整性）
  → 记忆写入 (PersistentMemoryManager):
      ★ 短期记忆写入: 内存(同步) + Redis(异步) + PG(异步)
      (可能触发 Redis LLM 摘要压缩)
  → 返回 AgentChatResponse (含步骤追踪、意图、工具调用列表)
```

## 4. 核心模块详解

### 4.1 Agent 编排引擎

**文件位置**: `app/core/agent/`

这是项目的心脏。架构**只有 2 种执行范式**，Function Calling 是 ReAct 内部的可替换后端。

#### 架构全景

```
Orchestrator.run(mode)
      │
      ├── mode="react"
      │     └── _invoke_react()  ← 统一入口
      │           ├── ★ 短期记忆: memory.get_relevant() → Redis/PG/内存
      │           ├── ★ 长期记忆: _append_long_term() → Milvus 语义召回
      │           └── ★ FC 后端切换:
      │                 use_function_calling=True  → FunctionCallAgent (bind_tools)
      │                 use_function_calling=False → ReActAgent (正则解析)
      │
      └── mode="plan_execute"
            └── _run_plan_execute()
                  ├── 1. Plan: LLM → 子任务列表 JSON
                  ├── 2. Execute: 每个子任务 → _invoke_react() (共享上述全部能力)
                  ├── 3. Replan: 失败时重规划 (最多 2 次)
                  └── 4. Summarize: LLM 汇总最终答案
```

#### 两种范式 vs 两种后端

```
┌──────────────────────────────────────────────────────────────┐
│                     执行范式 (2 种)                          │
│                                                              │
│  react ──────────────── plan_execute                         │
│  单层循环                 双层结构                             │
│  Thought→Action→Obs       Plan → ReAct执行 → 汇总            │
│       │                        │                             │
│       └────────┬───────────────┘                             │
│                │                                             │
│         _invoke_react()  统一执行入口                         │
│                │                                             │
│     ┌──────────┴──────────┐                                  │
│     │   工具调用后端 (2 种) │                                  │
│     │                     │                                  │
│     │  正则解析 ReActAgent │  ← 默认                          │
│     │  FunctionCallAgent  │  ← 可选 (LangChain bind_tools)   │
│     └─────────────────────┘                                  │
└──────────────────────────────────────────────────────────────┘
```

**Function Calling 为什么不是第三种模式**：FC 只负责"LLM 如何表达工具调用"这一件事。循环控制、步数上限、记忆注入、历史管理全部相同。它是在 `_invoke_react()` 内部的一个 if-else 分支，不是执行范式的差异。

#### 范式一：react — 纯 ReAct 循环

**文件**: [react_agent.py](../app/core/agent/react_agent.py)

```
核心流程:
  1. ★ 读取记忆:
       memory.get_relevant(session_id, query, limit=8)
       → PersistentMemoryManager:
           短期(Redis→PG→内存) + 长期(Milvus语义召回) → 合并为记忆摘要
  2. 构造 System Prompt（含工具描述 + ★记忆摘要块）
  3. for step in range(max_steps):
       a. LLM 生成文本
       b. 正则解析 → Thought / Action / Action Input / Final Answer
       c. 如果是 Final Answer → 返回结果
       d. 如果是 Action → 调用工具 → 将 Observation 追加到 history → 循环
  4. 耗尽步数 → 返回失败

关键实现:
  - _parse_react_step(): 正则匹配 Thought: / Action: / Action Input: / Final Answer:
  - Action Input 要求合法 JSON，解析失败会记录 parse_error
  - ★ 记忆在循环外读取一次，注入 system prompt 后在整个循环中保持不变
```

#### 范式二：plan_execute — 先规划再执行

**文件**: [planner.py](../app/core/agent/planner.py)

```
核心流程:
  1. plan(query) → LLM 生成 JSON 子任务列表
     每个子任务: {id, title, description, expected_tools}
  2. execute → 按序执行，每个子任务通过 react_factory → _invoke_react()
     ★ 每个子任务 = 一次完整 ReAct 循环（含记忆读取 + FC/正则后端切换）
  3. 如有失败 → replan() 重规划（最多 2 次）
  4. LLM 汇总所有子任务结果生成最终答案

降级策略:
  - plan 失败 → 退化为单子任务 (原始 query)
  - 全部子任务失败 → 编排器降级为 react 模式 (degraded=true)
  - 汇总 LLM 失败 → 拼接子任务输出
```

#### ★ Function Calling 后端（ReAct 内部的工具调用升级）

**文件**: [function_call_agent.py](../app/core/agent/function_call_agent.py)

```
定位: _invoke_react() 内部的分支:
  if self._use_function_calling and self._fc_agent is not None:
      result = await self._fc_agent.run(query, ctx)   ← FC 后端
  else:
      agent = ReActAgent(...)                         ← 正则解析后端

FC 后端流程:
  1. ChatOpenAI(…).bind_tools(tools) → LLM 知道每个工具的参数 Schema
  2. for step in range(max_steps):
       a. llm.invoke(messages) → 返回 AIMessage
       b. 如果 response.tool_calls 非空:
            - 执行每个 tool_call → ToolMessage
            - AIMessage + ToolMessage 对加入 history (LangChain 要求 tool_call_id 关联)
       c. 如果 response.tool_calls 为空 → response.content 就是最终答案

两种后端对比:
  正则解析: LLM 输出自由文本 → 正则提取 Action/Action Input → ~10-15% 解析失败率
  FC 后端:  LLM 输出原生 tool_calls JSON → 结构化解析 → ~0% 失败率
  共同点:   编排逻辑 (for循环/步数/错误处理) 完全自研，不依赖 LangGraph
```

#### 编排器 (AgentOrchestrator)

**文件**: [orchestrator.py](../app/core/agent/orchestrator.py)

```
职责:
```

### 4.4 RAG 检索增强生成

**文件**: [app/core/rag_service.py](../app/core/rag_service.py) + [app/core/tools/builtin/rag_search.py](../app/core/tools/builtin/rag_search.py) + `app/core/rag/`

**★ RAG 已打通为 Agent 工具**，不再是独立端点。Agent 在 ReAct 循环中可以自主决定何时调用 `rag_search` 查知识库、何时用 `web_search` 搜互联网。`POST /chat/rag` 独立端点保留用于纯知识库问答场景。

Architecture: **文档摄入 → 分块 → 向量化 → 注册为 Agent 工具 → ReAct 循环中按需调用**。

#### 文档摄入

```
用户上传文件 (PDF/TXT/Word)
  → DocumentParser.parse_bytes()     # 提取纯文本
  → DocumentChunker.chunk(text)      # 按策略分块 (默认递归分块, 512 token/块)
  → sentence-transformers.encode()   # 向量化 (all-MiniLM-L6-v2, 384维)
  → MilvusClient.insert() + BM25.add()  # 双写向量库和关键词索引
```

#### 分块策略 (chunker.py)

```
ChunkStrategy 枚举:
  FIXED      — 固定窗口切片 (按字符)
  RECURSIVE  — 递归分隔符切分 (\n\n → \n → 。 → . → 空格)
  PARAGRAPH  — 按空行分段合并
  LANGCHAIN  — 使用 LangChain RecursiveCharacterTextSplitter
```

#### 多路检索 + RRF 融合

```
用户查询
  ├── 向量检索 (Milvus COSINE 相似度) → top_k * 2 结果
  ├── 关键词检索 (BM25 Okapi)        → top_k * 2 结果
  └── RRF 融合 (k=60):
        score[doc] = 1/(60+rank_vector+1) + 1/(60+rank_keyword+1)
        按融合分降序取 top_k
```

#### Cross-Encoder 精排

```
RRF 融合结果 (通常 10-20 条)
  → CrossEncoder(ms-marco-MiniLM-L-6-v2).predict([(query, doc1), (query, doc2), …])
  → 按精排分数重新排序 → 取 top_k
```

#### 答案生成

```
RAGGenerator.generate():
  1. 构造 Prompt: System("仅根据上下文作答…") + 上下文 [1]...[n] + 历史对话 + 用户问题
  2. LLM 生成答案
  3. 正则提取 [n] 引用 → 映射到具体文档块 → 返回 Citation 列表
```

#### RAG 在 Agent ReAct 循环中的调用流程

```
Agent ReAct 循环中:
  Thought: 用户询问高血压饮食建议，知识库中有上传的医学指南
  Action: rag_search
  Action Input: {"query": "高血压 饮食 低盐 建议", "top_k": 5}
  Observation: [知识库检索结果]
               --- 结果 1 (相关度: 0.9200) [hybrid] ---
               高血压患者应控制钠盐摄入，每日不超过5克...
               --- 结果 2 (相关度: 0.8500) [hybrid] ---
               DASH饮食模式推荐每日4-5份蔬菜、4-5份水果...
               ============================================
               共找到 5 条相关文档块。

  Thought: 知识库找到了相关指南。如果结果不充分，可以再调用 web_search 补充
  [如果 rag_search 返回空 → 自动降级: Action: web_search]
  Final Answer: 根据知识库中的指南，高血压患者应注意...
```

#### RAGSearchTool 设计要点

**文件**: [rag_search.py](../app/core/tools/builtin/rag_search.py)

```
设计:
  - 封装 RAGService.search() 为 BaseTool 实现
  - 参数: query (检索词) + top_k (返回条数, 1-20)
  - 内部使用 hybrid 模式 (向量+BM25+RRF融合)
  - 边界处理:
      - 知识库为空 → "知识库当前为空，建议上传文档或使用 web_search"
      - 检索无结果 → "未找到相关内容，建议换关键词或使用 web_search"
      - 检索异常 → "检索失败，请尝试 web_search 或直接基于已有知识回答"
  - 结果格式化: 每条含相关度分数 + 来源标注，总长度限制 8K 字符
  - 注册方式: set_rag_service() 中动态创建 → ToolRegistry.register()
```

### 4.5 记忆系统

**文件**: [app/core/persistent_memory.py](../app/core/persistent_memory.py) + `app/core/memory/`

项目实现了一套 **四层级联记忆架构**，短期和长期记忆在请求链路中的位置明确分离：

#### ★ 记忆在请求链路中的具体位置

```
每次 Agent 对话请求:

  ① 执行前 (读取):
     ReActAgent.run() 第一步
       → memory.get_relevant(session_id, query, limit=8)
           │
           ├── ★ 短期记忆 (时间顺序):
           │     Redis ShortTermMemory.lrange() → 最近 8 条格式化字符串
           │     (Redis 不可用 → PG get_recent_messages → 内存 dict)
           │
           ├── ★ 长期记忆 (语义相似度):
           │     LongTermMemory.recall(query, session_id, top_k=3)
           │     → Milvus 向量搜索 + session_id 过滤
           │     → 格式化为 "[历史记忆] ..." 前缀
           │     (Milvus 不可用 → 跳过)
           │
           └── 合并: [长期记忆...] + [短期记忆...]
              → 截断到 limit 条
              → 注入 system prompt: "## 检索记忆摘要\n- ..."

  ② 执行后 (写入):
     AgentService.chat() 结尾
       → memory.append_turn(session_id, "user", user_text)
       → memory.append_turn(session_id, "assistant", answer)
           │
           ├── ★ 短期记忆写入 (三写):
           │     内存 dict (同步, 始终成功)
           │     PostgreSQL (异步, Conversation + Message 表)
           │     Redis (异步, rpush + 可能触发 LLM 摘要压缩)
           │
           └── ★ 长期记忆写入:
                 需显式调用 LongTermMemory.store() 才会写入 Milvus
                 (当前未在主流程自动化，由业务规则决定)
```

#### 各层详解

| 层级 | 实现 | 触发时机 | 检索方式 |
|------|------|----------|----------|
| **★ 短期记忆** | `ShortTermMemory` (Redis) | 每条消息自动写入 | 时间倒序取最近 N 条 |
| **PostgreSQL 冷存储** | `SessionRepository` | 每条消息自动写入 | SQL 按时间排序 |
| **内存兜底** | `_InMemoryMemoryManager` | 每条消息自动写入 | 时间倒序 |
| **★ 长期语义记忆** | `LongTermMemory` (Milvus) | 需显式 store() | 语义向量相似度 + session 过滤 |

#### ShortTermMemory 压缩机制

```
触发条件: 消息数 > window_size(20) 或 总 token > max_tokens(4000)
压缩策略:
  1. 保留尾部 keep 条 (window_size/2 = 10)
  2. 对其余消息调用 LLM: "请将以下对话压缩为简洁中文摘要，保留关键事实与用户意图"
  3. 摘要作为 SystemMessage (role=system, content="[历史摘要]\n...") 插入列表头部
  4. 原子替换 Redis 中的整个列表: DELETE key → RPUSH [摘要, 尾部10条...]

效果: 25 条消息 → 1 条摘要 + 10 条原文 = 11 条
```

#### 短期 vs 长期记忆对比

| 维度 | 短期记忆 | 长期语义记忆 |
|------|----------|--------------|
| 存储 | Redis List | Milvus 向量库 |
| 写入 | 自动 (每条消息) | 显式调用 store() |
| 检索 | 时间倒序，取最近 8 条 | 语义相似度，取 top_k=3 |
| 范围 | 仅当前会话 | 当前会话 (session_id 过滤) |
| 时效 | 压缩后逐步淘汰 | 持久化 (除非主动 forget) |
| 标识 | 无前缀 | `[历史记忆]` 前缀 |
| 注入位置 | 短期记忆列表 | 插入最前面 (重要性最高) |

### 4.7 模型路由与熔断

#### ModelRouter — 多模型路由

**文件**: [app/infrastructure/llm/model_router.py](../app/infrastructure/llm/model_router.py)

```
配置: list[ModelConfig]  (每路模型: model_id, api_key, base_url, priority, weight)

调度策略:
  1. 按 priority 分组
  2. 同优先级内加权随机排序: random.random() ** (1/weight)
     权重越大越容易被排前面
  3. 按候选顺序依次尝试，失败则自动降级到下一个
  4. 所有候选都失败 → 抛出 RuntimeError

使用示例:
  router = ModelRouter([
    ModelConfig("gpt-4o", key1, base_url1, priority=0, weight=3),
    ModelConfig("claude-3", key2, base_url2, priority=0, weight=1),
    ModelConfig("gpt-4o-mini", key3, base_url3, priority=1, weight=1),  # 降级备选
  ])
```

#### CircuitBreaker — 三态熔断器

**文件**: [app/infrastructure/llm/circuit_breaker.py](../app/infrastructure/llm/circuit_breaker.py)

```
状态机: Closed → Open → Half-Open → Closed/Open

  Closed (正常):
    - 放行所有调用
    - 累计失败次数
    - failure_count >= threshold(5) → 切换到 Open

  Open (熔断):
    - 快速失败，拒绝所有调用
    - 等待 recovery_timeout(60s)
    - 超时后 → 切换到 Half-Open

  Half-Open (试探):
    - 允许有限次试探调用 (half_open_max=3)
    - 成功 → 切换到 Closed，重置计数
    - 失败 → 回到 Open

实现细节:
  - 使用 asyncio.Lock 保证状态变更的原子性
  - time.monotonic() 计时（不受系统时钟调整影响）
  - 每个模型独立一个 CircuitBreaker 实例
```

### RAG 使用方式（两种路径）

```
方式一: Agent 工具调用 (★ 推荐, 已打通)
  Agent ReAct 循环中:
    Thought → Action: rag_search → Observation: 检索结果 → 继续推理 → Final Answer
    如果知识库无结果 → Agent 可自动降级调用 web_search

方式二: 独立 RAG 端点 (保留)
  POST /chat/rag → RAGService.chat() → 检索 + 生成（含引用标注）

文档摄入（两种方式共用）
  用户上传文档
    → DocumentParser.parse_bytes() → 提取纯文本
    → DocumentChunker.chunk()      → 递归分块 (512 token/块)
    → sentence-transformers.encode() → 向量化 (384维)
    → MilvusClient.insert() + BM25.add() → 双写入库
```

## 附录：关键设计决策

| 决策 | 选择 | 原因 |
|------|------|------|
| Agent 编排 | 自研 for 循环 | 完全掌控控制流，易于调试和定制 |
| LangChain 使用边界 | 仅 bind_tools | 面试可控，不引入不熟悉的 LangGraph |
| 依赖抽象 | Protocol | 不依赖具体实现，方便测试和替换 |
| 向量库 | Milvus Lite | 嵌入式部署，无需 Docker，本地文件持久化 |
| 记忆架构 | 三层级联 | 渐进降级，保证服务在任何基础设施条件下可用 |
| 熔断器 | 三态 (Closed/Open/Half-Open) | 防止雪崩，支持自动恢复 |
| RAG 检索 | RRF 融合 + 注册为 Agent 工具 | 向量+关键词互补；RAG 打通为 rag_search，Agent 可自主调度知识库和网络搜索 |
| 意图识别 | LLM + 关键词降级 | 保证 LLM 不可用时系统仍可工作 |
| 反思 | 编排器后置 | 不影响主流程，失败只记日志 |
| 配置 | pydantic-settings | 类型安全，支持 .env / 环境变量 / 默认值 |

## 附录：评测体系

项目配套完整的量化评估与单元测试，见 [评估报告-混合检索.md](./评估报告-混合检索.md)：

### 检索效果评估

- 数据集：7 份心血管临床指南、270+ 文档块（噪声过滤后）、29 条覆盖四类难度的标注查询。
- 指标：Recall@K / Precision@K / NDCG@K / MRR / 检索耗时；消融对比
  vector / keyword / hybrid(RRF) / hybrid+CrossEncoder 重排序。
- 结论：混合检索相比纯向量 Recall@5 提升 28.3%、MRR 提升 10.2%，重排序后 MRR 再提升 9.8%。
- 复现：`scripts/eval_full_kb.py`（全量）、`scripts/eval_rag.py`（真实管线）、
  `scripts/eval_rag_standalone.py` 与 `scripts/eval_real_doc.py`（轻量离线）。

### 评估驱动的缺陷修复

评测过程中发现并修复两个真实问题：

1. `_MilvusRAGStore` 重启后不重建内存 BM25 索引，keyword 检索静默失效、hybrid 退化为纯向量；
2. `_tokenize` 中文整段分词，关键词检索对中文基本不可用——统一为 jieba 分词
   （`rag_service.py` / `retriever.py` 一致），并加入依赖。

### 单元测试

`tests/` 下 67 个用例，覆盖熔断器、ReAct 解析、Planner、意图识别降级与多轮上下文、模式路由、工具注册、
BM25/RRF、短期记忆压缩、引用提取、rag_search 降级、Schema 校验等核心逻辑，
全部离线运行（`python -m pytest`），并接入 GitHub Actions CI。
