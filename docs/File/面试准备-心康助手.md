## 第1条：LangGraph StateGraph Agent 执行框架

### 1.1 代码实现

**核心文件**：`app/core/agent/langgraph_agent.py`（161行）

#### StateGraph 构建

```python
# langgraph_agent.py 第 83-113 行
def _build_graph(self):
    llm_with_tools = self._llm.bind_tools(self._tools)   # LangChain 模型绑定工具
    tool_node = ToolNode(self._tools)                    # LangGraph 内置工具节点

    def call_model(state: AgentState) -> dict:
        response = llm_with_tools.invoke(state["messages"])
        return {"messages": [response]}                  # 返回新消息，自动累加

    def should_continue(state: AgentState) -> str:       # 条件路由函数
        last = state["messages"][-1]
        if isinstance(last, AIMessage) and last.tool_calls:
            return "tools"                                # 有工具调用 → 去执行
        return END                                        # 无工具调用 → 结束

    workflow = StateGraph(AgentState)
    workflow.add_node("agent", call_model)               # LLM 推理节点
    workflow.add_node("tools", tool_node)                # 工具执行节点
    workflow.add_edge(START, "agent")                    # 入口
    workflow.add_conditional_edges("agent", should_continue,
        {"tools": "tools", END: END})                    # 条件路由
    workflow.add_edge("tools", "agent")                  # 工具完成后回到 agent
    return workflow.compile()
```

### 1.3 面试追问

**Q: StateGraph 的节点和边是怎么设计的？**

A: 两个节点——`agent`（LLM 推理）和 `tools`（工具执行）。入口 `START → agent`，agent 之后设 conditional edge：如果最后一条 AIMessage 包含 tool_calls → 去 tools 节点；否则 → END。tools 执行完 → 回到 agent 继续推理，形成循环。`recursion_limit` 控制最大循环次数。

**Q: add_messages 是做什么的？**

A: 它是 LangGraph 的消息 reducer。每次节点返回 `{"messages": [new_msg]}` 时，不是替换整个 messages 列表，而是把新消息追加到末尾。这样对话历史自动累积，不需要手动维护。

**Q: bind_tools 做了什么？**

A: LangChain 的 `ChatOpenAI.bind_tools()` 会将工具的 name、description、parameters（JSON Schema）注入到 API 请求的 `tools` 字段。模型收到后自动判断是否需要调用工具，如果需要就返回结构化的 `tool_calls`（含工具名 + JSON 参数），而不是文本 "Action: web_search"。这就是 Function Calling 机制。

**Q: 自研 ReAct 和 LangGraph 版有什么区别？**

A: 自研版用 `for` 循环 + 正则解析 Thought/Action/Final Answer，LangGraph 版用 StateGraph 状态机 + Function Calling 结构化输出。前者展示底层理解，后者展示工业框架能力。两种可以随时切换，LangGraph 失败还会降级到自研版兜底。

**Q: Evaluator 节点在 LangGraph 图内怎么工作的？**

A: Evaluator 是 StateGraph 的第三个节点（agent / tools / evaluator）。agent 生成最终答案（无 tool_calls）后，conditional edge 路由到 evaluator。evaluator 调用 LLM 对答案评分（0-100），检查完整性与清晰度。评分 ≥ 60 → should_retry 返回 END；评分 < 60 且重试次数 < 2 → 注入改进反馈 HumanMessage → 回 agent 重新生成。这样就实现了图内的自动质量闭环，不需要外部编排器干预。MAX_RETRIES=2 防止无限重试。

### 2.3 面试追问

**Q: 为什么用混合检索而不是纯向量检索？**

A: 向量检索擅长语义匹配但可能漏掉精确关键词匹配。比如用户搜索"硝苯地平"，BM25 能精确匹配术语，而向量检索可能被同义词干扰。两者互补，RRF 融合兼顾精确匹配和语义近似。

**Q: RRF 融合的原理？**

A: Reciprocal Rank Fusion，不比较原始分数（BM25 和向量分数的量纲不同，不可直接比较），而是比较排序位置。公式：`score(d) = Σ 1/(k + rank_i(d) + 1)`，k 通常取 60。k 的作用是平滑——减小高排名文档的优势，防止某个检索器的一个排名极高结果主导融合结果。

**Q: 为什么还要加 Cross-Encoder？**

A: BM25 + 向量检索都是双塔模型（Bi-Encoder），query 和 doc 分别编码后再算相似度，速度快但精度有损。Cross-Encoder 把 (query, doc) 作为一对输入拼接后编码，捕捉细粒度交互，精度更高但计算量大。所以先用混合检索粗筛（top 10），再用 Cross-Encoder 精排（top 5），性价比最高。

**Q: RecursiveCharacterTextSplitter 的递归逻辑？**

A: 按优先级尝试分隔符列表 `["\n\n", "\n", "。", ". ", " "]`。先用 `\n\n` 切分，如果某段仍超过 chunk_size，换 `\n` 继续切，依次递进。保证优先在自然段落边界切分，实在不行才在单词边界切，最大限度保持语义单元完整。

**Q: 如果 Milvus 不可用怎么办？**

A: 项目有降级机制。Milvus 初始化失败时自动切换到纯内存版（字符 n-gram 嵌入 + list 暴力搜索）。同时 BM25 是纯内存实现，不依赖外部服务。

```
写入 (append_turn):
  user/assistant 消息
    ├──→ Redis: RPUSH + 检查压缩条件 → 必要时 LLM 摘要
    ├──→ PostgreSQL: INSERT INTO messages (主路径)

  1. Redis: LRANGE 获取滑动窗口 → 成功则返回
  2. ↓ 失败 → PostgreSQL: SELECT ... ORDER BY created_at DESC LIMIT 8
  3. ↓ 失败 → InMemory: dict[-8:]
```

### 3.3 面试追问

**Q: 为什么要三层记忆？一层不够吗？**

A: 速度和可靠性的权衡。Redis 最快（微秒级），但数据可能丢失；PostgreSQL 可靠但每次 SQL 查询有延迟；InMemory 最快但进程重启就丢。三层级联保证：正常情况下用 Redis 高性能读取，Redis 挂掉自动切 PostgreSQL，PG 也挂掉还有 InMemory 保底不崩。

**Q: 为什么用 LLM 摘要而不是简单截断？**

A: 简单截断会丢失旧对话的关键信息。LLM 摘要将历史对话浓缩为一段文字保留核心语义，节省 token 同时保持上下文连贯性。比如用户三回合前说了"我有高血压"，截断会丢，摘要会保留"用户有高血压病史"。

**Q: 长期记忆的语义检索是怎么实现的？**

A: 将历史对话片段通过 embedding 模型向量化存入 Milvus，当用户提出新问题时，用同样的 embedding 模型编码问题，在 Milvus 中做向量相似度检索（L2 距离），召回语义相关但时间上可能很久远的历史信息。

**Q: 记忆系统的并发安全怎么保证？**

A: Redis 的 List 操作（RPUSH/LRANGE）本身是原子的。PostgreSQL 有事务保证。LLM 摘要压缩时有并发风险——多个请求同时触发压缩。当前实现通过 Redis 的乐观锁（比对消息数量）避免重复压缩。

```tsx
// 右栏 (w-80): Agent 分析面板
//   - Agent 模式: IntentBadge + ToolCallLog + AgentSteps (推理步骤可视化)
//   - RAG 模式: 知识库状态 + RAGContext (检索上下文+引用)

```

**自动模式路由**（`ChatPage.tsx` 第 88 行）：
```typescript
const resolveMode = (text: string, hasDocs: boolean): ChatMode => {
    // 有文档 + 医学关键词 → RAG 模式
    if (hasDocs && /什么|如何|为什么|禁忌|副作用/.test(text)) return 'rag';
    // 搜索/计算关键词 → Agent 模式
    if (/今天|搜索|计算/.test(text)) return 'agent';
    // 默认 → Agent 模式
    return 'agent';
};
```

### 4.2 面试追问

**Q: 为什么用 FastAPI 而不是 Flask？**

A: FastAPI 原生支持 async/await，适合 Agent 这种大量 I/O 等待（调 LLM、查数据库、调工具）的场景。自动生成 OpenAPI 文档（/docs），pydantic 做请求验证，类型提示全覆盖。

**Q: Agent 的请求处理流程是怎样的？**

A: 用户消息 → IntentRecognizer 意图分类 → AgentOrchestrator 根据模式和意图选择 ReAct/Plan-and-Execute/LangGraph → 执行推理循环（调 LLM → 调工具 → 观察结果 → 循环）→ 反思质检 → 保存记忆 → 返回结构化响应（含步骤、工具调用、反思评分）。

**Q: 前端如何展示 Agent 推理过程？**

A: 后端 `AgentChatResponse` 包含 `steps: List[StepInfo]`，每个 step 记录 thought/action/observation/final_answer。前端右栏 AgentSteps 组件逐条渲染：思想卡片（Thought）→ 动作卡片（Action + Action Input）→ 观察卡片（Observation），医学场景用中文标签（"正在分析"/"🩺 执行健康分析"/"分析结果"）。

**Q: 三个模式在前端怎么切换？**

A: 默认自动模式（autoMode=true），前端 `resolveMode()` 函数根据用户输入正则匹配 + 知识库状态自动选择。用户可以点击"手动选择"切换到手动模式，在三个按钮（Agent/RAG/Direct）中明确指定。

## 高频交叉追问

### Q: 整个项目的难点在哪里？

**回答框架**（3 个层次）：

1. **编排层面**：三模式共存 + 降级兜底 + 反思质检，保证任何模式下任务不失败
2. **检索层面**：自研 BM25 + Milvus 向量 + RRF 融合 + Cross-Encoder 精排，四阶段管线在 CPU 环境可运行
3. **工程层面**：Protocol 依赖注入（5 个抽象接口）实现模块零耦合，三层记忆级联保活

### Q: 如果让你重新设计，会改什么？

**回答要点**：

1. 反思环节已集成到 LangGraph 图内作为 Evaluator 节点 → 评分 < 60 自动重试（已实现）
2. Function Calling 失败时增加重试机制（当前直接返回错误）
3. 流式输出接入 Agent 模式（当前仅 Direct 模式支持 SSE）
4. 增加 LangSmith/LangFuse 可观测性追踪

### Q: 模型调用的可靠性怎么保证？

**回答要点**：

1. 三态熔断器：每个模型独立熔断器，连续 5 次失败 → 熔断 60 秒 → 半开探测
2. 多模型路由：同优先级内加权随机，单模型故障自动切换下一个
3. 编排降级：LangGraph/Plan 失败 → 自动降级 ReAct
