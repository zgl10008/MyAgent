## 序：一个请求的故事

用户在前端输入框中敲下：

> "帮我搜一下最近 AI Agent 领域有什么新突破，然后总结成三个要点"

按下发送键。以下是从这条消息抵达后端到前端收到完整回复的全过程。

```
浏览器 ──HTTP POST──▶ 服务器 ──┬── IntentRecognizer ──── 意图识别
                               ├── ModeRouter ──────── 模式路由（★ RAG 连接点：kb_available）
                               ├── Orchestrator ───── 执行编排
                               │   ├── _invoke_react() ── 统一入口（★ FC 后端切换点）
                               │   │   ├── FunctionCallAgent ─ FC 后端（bind_tools）
                               │   │   └── ReActAgent ────── 正则解析后端
                               │   │       └── memory.get_relevant() ── ★ 短期记忆读取
                               │   │           └── _append_long_term() ── ★ 长期记忆读取
                               │   ├── Planner ───────── 任务规划
                               │   └── ReflectionAgent ── 质量审查
                               ├── PersistentMemory ── ★ 记忆持久化（三写）
                               └── AgentChatResponse ── 响应组装
```

## 第一阶段：请求到达

### 1.1 HTTP 入口

请求抵达 `POST /api/chat/agent`，被 FastAPI 路由到 [app/api/routes/chat.py:178](../app/api/routes/chat.py#L178)：

```python
@router.post("/chat/agent", response_model=AgentChatResponse)
async def chat_agent(request: AgentChatRequest) -> AgentChatResponse:
    agent = _get_agent()
    return await agent.chat(request)
```

这个阶段做了两件事：

1. **获取 AgentService 单例**：`_get_agent()` 如果发现还没有实例，会创建一个。创建过程中会初始化模型路由器、工具注册表、记忆管理器、意图识别器、ModeRouter、编排器、FunctionCall Agent 等全部组件。

2. **调用 `agent.chat(request)`**：进入主流程。

### 1.2 request 里有什么

```python
class AgentChatRequest:
    messages: list[ChatMessage]   # 对话历史 + 当前用户消息
    model: str | None             # 可选指定模型
    temperature: float = 0.7
    conversation_id: str | None   # 会话 ID（用于记忆关联）
    agent_mode: str = "auto"      # "auto" | "react" | "plan_execute"
```

对当前请求，`agent_mode="auto"`（默认），意味着系统需要自动决定用哪种 Agent 范式。

即使 LLM 没有正确识别数字槽位，正则引擎也会从 query 中自动提取。这是双重保障。

## 第三阶段：模式路由

### 3.1 检查是否需要路由

```python
# agent_service.py:325-329
_EXPLICIT_MODES = frozenset({"react", "plan_execute"})
requested_mode = (request.agent_mode or "").strip().lower()

if requested_mode in _EXPLICIT_MODES:
    selected_mode = requested_mode   # ← 用户显式指定，跳过 Router
else:
    decision = await self._mode_router.resolve(...)  # ← 自动路由
```

当前请求的 `agent_mode="auto"`，不在显式模式集合中，进入自动路由。

### 3.2 更新知识库状态——RAG 与 Agent 的唯一连接点

```python
# agent_service.py:333-339
kb_available = False
if self._rag_service is not None:
    kb_available = self._rag_service.chunks_count > 0
self._mode_router.kb_available = kb_available
```

ModeRouter 在做决策前需要知道一个关键信息：**RAG 知识库当前有没有内容**。

**RAG 和 Agent 是两套平行系统，不是嵌套关系**。`POST /chat/rag` 是独立的 RAG 对话端点（检索知识库 → 基于检索上下文生成带引用的回答），`POST /chat/agent` 是独立的 Agent 端点（意图识别 → 路由 → 工具调用）。两者的唯一切入点就是此处——ModeRouter 检查知识库是否有内容，影响路由决策：

- `kb_available=True`（用户上传过文档）：LLM Router 知道知识库有资料，某些知识问答可以走 react 快速回答
- `kb_available=False`（知识库为空）：需要外部信息的查询必须走 plan_execute 用搜索工具获取信息

如果要在 Agent 内部直接使用 RAG 检索结果，架构上的接入方式是将其注册为一个工具（如 `rag_search`），让 ReAct 循环中可以通过 `Action: rag_search` 触发检索。当前项目未启用此方式，RAG 以独立端点形式提供服务。

### 3.3 三段式决策

```python
decision = await self._mode_router.resolve(user_text, intent_result)
```

ModeRouter 内部走完三段决策管道（[mode_router.py:160-201](../app/core/agent/mode_router.py#L160-L201)）：

#### 第一道：规则快路径

```python
_INTENT_MODE_RULES = {
    "知识问答": ("react", 0.0),    # ← 查表：知识问答 → react
}
```

规则表说"知识问答 → react"。

但等等——ModeRouter 在返回之前，还会执行一个**额外检查**：

```python
_TIME_SENSITIVE_KW = {"今天", "最近", "最新", "目前", "当前", "实时", "新闻", "2025", "2026"}

if intent_result.intent == "知识问答":
    if any(kw in query for kw in _TIME_SENSITIVE_KW):
        return ModeDecision(
            mode="plan_execute",   # ← 覆盖！从 react 升级为 plan_execute
            source="rule",
            rationale="知识问答含时间敏感词，升级为 plan_execute 多步搜索",
        )
```

用户的 query 中包含 **"最近"**——这是时间敏感关键词。规则引擎识别到：虽然意图分类器认为是"知识问答"，但这个知识问答需要最新信息，单步 ReAct 不够，应该走 Plan-and-Execute 多步搜索+整合。

**这就是规则快路径的价值**：它在某种程度上比 LLM 意图分类器更"聪明"——因为它有硬编码的业务知识（含时间敏感词的查询需要多步编排），而 LLM 分类器只能做意图标签分类。

#### 规则命中，直接返回

```python
ModeDecision(
    mode="plan_execute",
    source="rule",
    rationale="知识问答含时间敏感词，升级为 plan_execute 多步搜索",
    confidence=0.82
)
```

`source="rule"` 意味着这一步**零 token 消耗**。第二道（LLM Router）和第三道（兜底）没有被触发。

### 3.4 路由结果

```python
selected_mode = "plan_execute"
```

这个决策被封装进 IntentContext，传给编排器：

```python

    intent="知识问答",
    confidence=0.82,
    slots={"numbers": ["三个"]},
    preferred_mode="plan_execute",
)
```

### 4.5 阶段二：执行子任务（Execute × 3）

PlannerAgent 按顺序逐个执行子任务。每个子任务通过 `react_factory` 调用，走**完整的 ReAct 循环**。

#### 子任务 t1："搜索最新 AI Agent 突破"

Tracer 记录：

```
trace_cb({"phase": "execute_subtask", "subtask_id": "t1", "title": "搜索最新 AI Agent 突破"})
```

`react_factory` 被调用，进入 `_invoke_react()`（[orchestrator.py:147-190](../app/core/agent/orchestrator.py#L147-L190)）：

```python
async def _invoke_react(self, query, ..., allowed_tools=["web_search"], suffix="[子任务] "):
    ctx = {
        "session_id": session_id,
        "tool_names": ["web_search"],
        "tool_descriptions": "- web_search: 搜索互联网获取实时信息\n- calculator: 数学计算",
        "trace_callback": trace_cb,
        "extra_system": "[子任务] 当前识别意图：知识问答，槽位：{'numbers': ['三个']}",
    }

    if self._use_function_calling and self._fc_agent is not None:
        # ═══════════ Function Calling 后端 ═══════════
        # FC 后端：LLM 返回原生 tool_calls (结构化 JSON)，无需正则解析
        # 由 LangChain ChatOpenAI.bind_tools() 将工具 Schema 注入模型请求
        self._fc_agent.max_steps = max_steps
        result = await self._fc_agent.run(query, ctx)
    else:
        # ═══════════ 正则解析后端（当前使用）═══════════
        # ReActAgent：LLM 返回自由文本 → 正则解析 Thought/Action/Action Input
        agent = ReActAgent(llm=llm, tools=self._tools,
                           memory=self._memory, max_steps=max_steps,
                           session_id=session_id)
        result = await agent.run(query, ctx)
```

**这里是 Function Calling 的具体位置**。当前项目默认走正则解析后端（`use_function_calling=False`）。两种后端的关键区别：

```
正则解析后端（当前）：
  LLM 输出 → "Action: calculator\nAction Input: {\"expression\":\"1+1\"}"
           → 正则 _parse_react_step() 解析 → 提取 action + action_input
           → ~10-15% 解析失败率（JSON 格式错误、模板不匹配）

Function Calling 后端（可选）：
  LLM 输出 → AIMessage(tool_calls=[{"name":"calculator","args":{"expression":"1+1"}}])
           → 原生结构化，~0% 失败率
           → 但需要模型支持 FC API，绑定了 OpenAI 风格接口
```

不论走哪个后端，`react_factory` 和 Orchestrator 上层逻辑都无感知——**FC 是 ReAct 内部工具调用机制的实现升级，不是第三种执行模式**。

当前使用正则解析后端。ReActAgent 内部开始循环（[react_agent.py:168-294](../app/core/agent/react_agent.py#L168-L294)）：

**Step 0（子任务 t1 的第一步）**：

1. **读取记忆上下文（短期 + 长期）**：

   ReActAgent 调用 `memory.get_relevant(session_id, query, limit=8)`。这个调用触发了 PersistentMemoryManager 内部的完整检索链（[persistent_memory.py:194-248](../app/core/persistent_memory.py#L194-L248)）：

   ```
   get_relevant("abc123", "搜索 2026 年 AI Agent 领域的最新突破", limit=8)
       │
       ├── ① LongTermMemory.recall(query, session_id, top_k=3)
       │      ├── embed_query("搜索 2026 年 AI Agent...") → [384-dim 向量]
       │      ├── Milvus.search(vector, expr='session_id=="abc123"', top_k=3)
       │      │      ← 语义向量搜索 + session_id 过滤
       │      └── 返回: [MemoryItem("用户父亲有糖尿病史", score=0.92), ...]
       │             格式化为: ["[历史记忆] 用户父亲有糖尿病史，需控制糖分摄入"]
       │
       ├── ② Redis ShortTermMemory.get_relevant()
       │      └── lrange stm:session:abc123 -8 -1  → 最近 8 条消息
       │             格式化为: ["user: 我最近在关注健康", "assistant: 好的...", ...]
       │
       └── ③ 合并: [历史记忆...] + [短期记忆...] → 截断到 8 条
   ```

   **短期记忆的体现**：Redis List 中按时间顺序存储的消息，取最近 8 条。包含**当前会话**的完整上下文。

   **长期记忆的体现**：Milvus 向量搜索，按**语义相似度**召回。可能跨越多天前的其他对话轮次（只要在同一个 session_id 下）。结果以 `[历史记忆]` 前缀标识，插入记忆列表**最前面**（重要性最高）。

   如果 Redis 不可用，降级到 PostgreSQL → 内存 dict。
   如果 Milvus 不可用（`self._long_term is None`），跳过长期记忆，只返回短期记忆。

   返回的记忆列表被组装为**记忆摘要块**：

   ```

   - [历史记忆] 用户父亲有糖尿病史，医生建议控制糖分摄入
   - [历史记忆] 用户本人对青霉素过敏
   - user: 我最近在关注健康
   - assistant: 好的，有什么具体问题吗？
   - user: 父亲的糖尿病管理有什么注意事项？
   - assistant: 主要是饮食控制和定期监测血糖...
   - user: 帮我搜一下最近 AI Agent 领域有什么新突破
   ```

   这个摘要块直接注入到 system prompt 中。

2. **构造 Prompt**：

## 第四阶段（续）：执行编排（ReAct 路径）

如果 ModeRouter 决定走 `react` 模式（如简单计算、闲聊），编排器直接调用 `_invoke_react()`：

```python
# orchestrator.py:237-240
else:
    result = await self._invoke_react(
        user_input, session_id, intent_ctx, trace_id, steps,
        max_steps=int(self._config.get("react_max_steps", 10)),
    )
```

这与子任务执行的 `_invoke_react()` 是**同一个方法**。区别仅在于：
- `max_steps`：纯 ReAct 用 10，子任务用 5（子任务应该更简单）
- `suffix`：纯 ReAct 无后缀，子任务有 `"[子任务] "` 前缀
- `allowed_tools`：纯 ReAct 用全部工具，子任务可能限制工具范围

这正是架构一致性的体现——**执行 = ReAct 循环**，无论是顶层模式还是子任务执行。

### ReAct 路径示例："帮我算 (123+456)*789"

以纯 ReAct 模式为例，同样经过 `_invoke_react()`。如果是正则解析后端：

```
_invoke_react("帮我算 (123+456)*789", ...)
    │
    ├── ① 读取记忆：memory.get_relevant(session_id, query, limit=8)
    │      → 短期记忆：当前会话最近 8 条历史
    │      → 长期记忆：Milvus 语义召回（如有）
    │      → 合并为 "## 检索记忆摘要" 注入 system prompt
    │
    ├── ② 创建 ReActAgent（正则解析后端）或
    │       使用 FunctionCallAgent（FC 后端，如配置开启）
    │
    └── ③ ReAct 循环:

Step 0:
  LLM 看到: system prompt（含记忆摘要 + 工具列表）+ user query
  LLM 输出 → Thought: 需要调用计算器
             Action: calculator
             Action Input: {"expression": "(123+456)*789"}
  正则解析 → 提取 action + action_input
  执行工具 → Observation: 456531

Step 1:
  LLM 看到: system prompt + 上一步的历史轨迹
  LLM 输出 → Thought: 计算完成
             Final Answer: (123 + 456) × 789 = 456,531
  解析到 Final Answer → 返回结果
```

2 步完成，`max_steps=10` 只是安全上限。

## 第六阶段：记忆持久化

### 6.1 保存用户消息和助手回复

```python
# agent_service.py:364-372

```

**注意**：这里写入的是短期记忆（Redis + PG + 内存）。长期记忆（Milvus）需要显式调用 `LongTermMemory.store()` 才会写入——当前项目尚未在 Agent 主流程中自动化此触发，需要由特定业务规则决定哪些信息值得"长期记住"（如检测到用户提供了重要个人信息时主动调用 `store()`）。

### 6.2 三写策略

每条 `append_turn` 调用在 PersistentMemoryManager 内部触发三写（[persistent_memory.py:250-273](../app/core/persistent_memory.py#L250-L273)）：

```
append_turn(session_id, "user", "帮我搜一下最近 AI Agent...")
        │
        ├── ① 内存兜底（同步）
        │      _fallback.append_turn() → Python dict
        │      ✅ 始终成功，不丢失数据
        │
        ├── ② PostgreSQL（异步）
        │      pg_repo.add_message() → conversations + messages 表
        │      ⚠️ 失败仅日志警告，不影响响应
        │
        └── ③ Redis（异步）
               redis_stm.append_turn() → rpush + 可能的压缩触发
               ⚠️ 失败仅日志警告，不影响响应
```

**为什么内存兜底是同步的而 PG/Redis 是异步的**：内存写入是 O(1) 且不会失败（dict 操作），可以同步等待。PG/Redis 可能因网络/超时等原因失败，不能让对话响应等它们。这是一个简单的"先响应、再同步"模式。

### 6.3 压缩可能被触发

如果当前会话的 Redis 消息数超过 20 条或总 token 超过 4000，`redis_stm.append_turn()` 内部会自动触发 LLM 摘要压缩。压缩过程：

```
1. 取前 N-10 条消息 → 发送给 LLM 生成中文摘要
2. 保留最近 10 条消息不变
3. 重建 Redis List：[摘要消息(role=system)] + [最近10条]
```

这个压缩对用户透明——下一次请求时，记忆系统返回的已经是压缩后的消息列表。

## 附录 A：降级路径汇总

整个系统中，一个请求可能经过的**所有**降级点：

| 阶段 | 故障 | 降级方式 | 用户感知 |
|------|------|----------|----------|
| 意图识别 | LLM 分类失败 | 关键词规则匹配 | 无（意图仍可识别） |
| 模式路由 | 规则未命中且 LLM Router 失败 | 降级 react | 无（回答可能稍简略） |
| 模式路由 | LLM Router 返回非法 mode | 强制 react | 无 |
| Agent 初始化 | FunctionCall Agent 创建失败 | 仅正则解析可用 | 无 |
| 规划 | LLM 规划调用失败 | 降级为单子任务 fallback | 回答质量可能下降 |
| 执行 | 子任务执行失败 | 重规划（最多 2 次） | 可能多等几秒 |
| 执行 | Plan-and-Execute 整体失败 | 降级纯 ReAct | degraded=true |
| 汇总 | 汇总 LLM 调用失败 | 拼接子任务输出 | 回答格式可能稍乱 |
| 反思 | 反思 LLM 调用失败 | 跳过反思，保守评分 | 无 |
| ReAct | LLM 调用失败（单步） | 返回错误 | 最终 answer 为空 |
| ReAct | 达到 max_steps | 返回错误 | "已达到最大步数限制" |
| 记忆读取 | Redis 不可用 | 降级 PG | 无（读取稍慢） |
| 记忆读取 | PG 不可用 | 降级内存 dict | 无（无持久化） |
| 记忆写入 | PG/Redis 写入失败 | 仅写入内存 | 无（重启后丢失） |
| RAG（如在用） | Milvus 不可用 | 降级内存存储 | 检索精度下降 |
| RAG（如在用） | sentence-transformers 不可用 | 降级 n-gram 嵌入 | 语义精度下降 |

**核心设计原则**：任何单点故障都不会导致整个请求失败。系统一层层地降低能力，但始终保持可用。

## 附录 B：关键数据结构生命周期

### 一条用户消息的"旅程"

```
用户输入（字符串）
        │
        ▼ 意图识别
IntentResult（intent + confidence + slots）
        │
        ▼ 模式路由
ModeDecision（mode + source + rationale）
        │
        ▼ 封装
IntentContext（合并以上两者，加入 preferred_mode 和 allowed_tools）
        │
        ▼ 编排执行
Step dicts（每个 step 包含 step/phase/thought/action/observation/final_answer）
        │
        ▼ 结果
AgentResult（success + final_answer + steps）
        │
        ▼ 反思
ReflectionReport（quality_score + hallucination_check + suggestions）
        │
        ▼ 组合
AgentResponse（answer + mode_used + steps + reflection + degraded）
        │
        ▼ 记忆持久化
Memory.append_turn("user", ...)   →   Redis + PG + 内存
Memory.append_turn("assistant", ...) → Redis + PG + 内存
        │
        ▼ 转换
StepInfo list（标准化格式）
        │
        ▼ 最终
AgentChatResponse（content + trace_id + intent + steps + tool_calls + score）
        │
        ▼ 序列化
JSON → HTTP Response → 前端
```

### 整个流程涉及的 LLM 调用次数

以本文的 Plan-and-Execute 场景为例：

| 调用 | 用途 | temperature |
|------|------|-------------|
| 1 次 | 意图分类 | 0.1 |
| 0 次 | 模式路由（规则命中，跳过 LLM） | — |
| 1 次 | 任务规划 | 0.3 |
| 2 次 | t1 子任务 ReAct（2 步） | 0.2 |
| 1 次 | t2 子任务 ReAct（1 步） | 0.2 |
| 1 次 | t3 子任务 ReAct（1 步） | 0.2 |
| 1 次 | 最终汇总 | 0.2 |
| 1 次 | 反思评估 | 0.1 |

**共计 8 次 LLM 调用**。其中 5 次是实际"干活"的（规划 1 + 执行 4），3 次是辅助性的（意图 1 + 汇总 1 + 反思 1）。

对比纯 ReAct 路径完成同样的任务，可能需要 6-8 步 ReAct 循环——同样 6-8 次 LLM 调用。Plan-and-Execute 虽然多了规划和汇总两次调用，但子任务各有侧重、目标明确，每个子任务只需 1-2 步，总调用次数相当，但**可解释性和容错性更好**。

而如果是简单计算"帮我算 (123+456)*789"的纯 ReAct 路径：

| 调用 | 用途 | temperature |
|------|------|-------------|
| 1 次 | 意图分类 | 0.1 |
| 0 次 | 模式路由（规则命中 react） | — |
| 2 次 | ReAct 循环（调计算器 + 最终回答） | 0.2 |
| 1 次 | 反思评估 | 0.1 |

**共计 4 次 LLM 调用**。Plan-and-Execute 对于简单任务显然是过度设计——ModeRouter 避免了这种浪费。
