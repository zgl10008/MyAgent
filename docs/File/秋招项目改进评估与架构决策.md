# 秋招项目改进评估与架构决策

> 评估对象：心康助手——心血管慢病管理 AI Agent
>
> 评估目的：明确项目是否具备秋招展示价值、统一产品定位、解释存储架构取舍，并制定后续改进顺序。

## 一、结论先行

当前项目已经具备作为秋招项目展示的技术基础，但还没有达到“完成度很高、主线非常清晰、可以稳定复现”的优秀状态。

项目的主要问题不是技术点太少，而是技术点较多但主线偏宽：同时包含多种 Agent 范式、混合 RAG、三层记忆、模型路由、熔断降级、医疗前端和大量教学文档。如果没有统一叙事，面试官容易认为项目是在堆技术名词。

推荐最终定位为：

> **通用 Agent/RAG 平台 + 心血管慢病管理默认 Demo + 可插拔领域安全策略。**

通用底座解决文档上传、解析、分块、向量化、混合检索、引用回答、工具调用、记忆和 Agent 编排；心血管场景作为默认演示领域，提供领域 Prompt、默认知识库、风险分流和医疗安全边界。

这个定位既保留“上传什么文档，就可以对什么文档做 RAG”的通用能力，又避免项目退化为没有业务边界的“万能 Agent”。

## 二、当前项目质量评估

### 2.1 已有优势

1. **Agent 主链路比较完整**
   - 有意图识别、模式路由、ReAct、Plan-and-Execute、工具调用、反思和执行轨迹展示。
   - 能够解释不同任务为什么选择不同 Agent 模式，而不是只有一个简单的 LLM 对话接口。

2. **RAG 具备工程化特征**
   - 同时支持 BM25 和向量召回。
   - 使用 RRF 融合不同召回结果。
   - 可以接入 CrossEncoder 重排序。
   - 通过 `rag_search` 工具让 Agent 自主调度知识库。
   - 支持引用生成和文档管理。

3. **有明确的可靠性设计**
   - LLM 调用具备多模型路由和三态熔断器。
   - 意图识别支持 LLM 与规则双通道降级。
   - Redis、PostgreSQL、内存之间有记忆降级链路。
   - Milvus 不可用时可以退化到内存向量库。

4. **有可观测和可讲解能力**
   - 前端展示 Thought、Action、Observation 等 Agent 步骤。
   - 可以解释工具调用、检索结果和 Agent 决策过程。
   - 这对秋招面试中的系统设计和故障排查追问很有价值。

5. **已经开始做量化评估和自动化测试**
   - 有 Recall@K、MRR、NDCG@K 等 RAG 指标。
   - 有 BM25、RRF、熔断器、Planner、意图识别降级、记忆压缩等测试。
   - 有 GitHub Actions CI 和 Ruff 检查。

### 2.2 距离优秀秋招项目的主要差距

#### 差距一：产品主线需要收敛

目前 README 以心血管慢病管理为标题，同时又强调企业级通用 Agent 和教学项目。三种叙事叠加后，面试官可能不清楚项目到底服务谁、解决什么问题。

建议只保留一条主叙事：

> 用户上传任意领域文档，系统自动构建可引用的知识库问答 Agent；心血管慢病是默认 Demo，用于展示领域安全策略和完整产品体验。

#### 差距二：评测结果需要做到可复现

README 中的评测数字很有说服力，但面试官可能继续追问：

- 数据集如何构造？
- 标注查询和相关文档如何定义？
- 纯向量、BM25、混合检索的参数是否一致？
- 是否使用了测试集之外的知识？
- 重排模型是什么？
- 指标是单次运行还是多次平均？

因此需要补齐评测脚本、数据说明、参数配置、运行命令和原始结果，并明确哪些结果是离线实验、哪些结果来自真实 RAGService 管线。

#### 差距三：启动和依赖成本仍然偏高

PostgreSQL、Redis、Milvus Lite、Embedding 模型、CrossEncoder 和 LLM API 同时存在，初次运行成本较高。需要提供：

- 最小本地模式；
- 完整 Docker Compose 模式；
- 外部依赖不可用时的降级说明；
- 示例 `.env`；
- 一键初始化知识库命令。

#### 差距四：生产化基础能力仍需补充

如果目标是“优秀项目”，建议后续补充以下至少一部分：

- 用户认证和会话隔离；
- 文档归属和权限控制；
- 上传文件类型和大小限制；
- API 限流；
- 结构化日志与 trace_id；
- Prometheus 指标或基础监控；
- 数据库迁移工具；
- Docker Compose 和部署文档；
- 端到端 API、RAG、SSE 测试。

#### 差距五：医疗安全边界需要显式化

如果继续保留心血管 Demo，不能只把它描述为普通聊天机器人。至少应明确：

- 不进行疾病确诊；
- 不替代医生；
- 不直接给出处方和自行调整药物剂量建议；
- 对胸痛、呼吸困难、意识异常等高风险信号进行紧急就医提示；
- 对无法判断的问题给出谨慎、可追溯的回答；
- 回答尽量附带知识库引用。

## 三、通用 Agent 与医疗场景的定位决策

### 3.1 是否可以完全放弃医疗场景

技术上可以，但产品和面试表达上不建议直接完全放弃。

“知识库上传什么文档，就可以做什么 RAG 检索”这个判断在检索层面基本成立，但完整产品不只有检索。不同领域仍然需要不同的：

- Prompt 和回答风格；
- 元数据过滤策略；
- 权限模型；
- 风险控制；
- 评测集；
- 前端交互；
- 结果解释和拒答策略。

如果改成完全没有领域边界的通用 Agent，项目虽然看起来更通用，却容易出现两个问题：

1. 缺少具体用户和业务闭环；
2. 面试官难以判断系统在真实场景中的价值。

### 3.2 推荐的产品分层

#### 通用底座

- 文件上传和文档解析；
- 多格式文本抽取；
- 文档分块和元数据管理；
- Embedding 和向量存储；
- BM25 + 向量混合检索；
- RRF 融合和可选重排序；
- 引用回答；
- Agent 工具调用；
- 短期记忆和长期记忆；
- 运行轨迹、日志和评测。

#### 领域插件

- 领域 System Prompt；
- 领域术语和实体配置；
- 领域检索过滤器；
- 领域风险分流规则；
- 领域拒答和安全策略；
- 领域评测集；
- 领域默认知识库。

#### 默认 Demo

继续保留心血管慢病管理作为默认 Demo，重点展示：

- 用药和监测知识问答；
- 高风险症状分流；
- 引用知识库回答；
- 医疗免责声明和安全提示；
- 文档上传后构建个人知识库。

这样面试时可以用一句话解释：

> 我做的是一个领域可插拔的 Agent/RAG 平台，心血管慢病只是默认行业插件，用来验证通用底座在高风险场景下的安全边界。

## 四、存储机制职责划分

当前 Redis、PostgreSQL、内存和 Milvus 的职责可以合理共存，但必须在文档和代码中明确边界，不能让它们看起来像重复存储。

| 组件 | 推荐职责 | 数据特点 | 是否可被替代 |
|---|---|---|---|
| Redis | 短期会话、滑动窗口、临时状态、热点缓存、摘要缓存 | 高频读写、可设置 TTL | 可以由内存或其他缓存替代，但生产能力会下降 |
| PostgreSQL | 用户、会话、消息、文档元数据、持久化记忆、业务数据 | 强一致、可查询、需要长期保存 | 可以换 MySQL，但迁移成本不低 |
| 内存 | 本地开发兜底、故障降级、临时缓存 | 进程级、重启丢失、不适合多实例 | 不应作为生产主存储 |
| Milvus | 文档向量、长期语义记忆、大规模向量检索 | 高维向量、近似最近邻搜索 | 可以换 pgvector、Qdrant、FAISS 等 |

推荐的数据流是：

- 会话热数据优先放 Redis；
- 需要长期保存的数据写 PostgreSQL；
- Redis 或 PostgreSQL 暂时不可用时使用内存降级；
- 文档向量和长期语义记忆放向量存储；
- 原始文档本身不应只保存在向量数据库中，应保留文件存储或对象存储方案，并在 PostgreSQL 中保存元数据。

需要注意：Redis、PostgreSQL 和内存是记忆/业务数据的存储层级；Milvus 是向量检索基础设施。它们不是完全相同的存储角色。

## 五、PostgreSQL 能否替换为 MySQL

### 5.1 结论

可以替换，但不是只修改数据库连接字符串。当前继续使用 PostgreSQL 更合理。

### 5.2 需要修改或验证的内容

1. 将 `postgresql+asyncpg` 替换为 MySQL 对应的异步驱动和 SQLAlchemy URL，例如 `mysql+aiomysql`。
2. 检查 SQLAlchemy 模型中的 JSON、文本、时间和自增主键字段。
3. 检查索引、唯一约束、事务隔离级别和连接池行为。
4. 检查全文检索或数据库特有 SQL。
5. 重新验证异步会话、事务回滚和并发访问。
6. 如果增加向量能力，需要单独选择 Milvus、Qdrant、pgvector 之外的方案；MySQL 本身不能自动替代向量数据库。
7. 补充数据库迁移脚本，避免依赖启动时 `create_all`。

### 5.3 为什么当前推荐 PostgreSQL

- 项目已经使用 SQLAlchemy async 和 asyncpg，现有代码迁移成本较低。
- PostgreSQL 的 JSON、全文检索和扩展生态更适合知识库平台。
- 后续可以评估 pgvector，把关系数据和向量数据收敛到同一个数据库。
- 面试时更容易解释从独立 Milvus 到 PostgreSQL + pgvector 的演进路线。

如果目标岗位明确要求 MySQL，建议把 MySQL 作为兼容性扩展，而不是现在为了替换而替换。

## 六、Milvus 是否有必要保留

### 6.1 Milvus Lite 的价值

保留 Milvus Lite 有以下优点：

- 能够展示独立向量数据库的使用经验；
- 与关系型数据库职责分离，架构边界清晰；
- 更容易扩展到大规模向量数据和独立向量服务；
- 对 RAG 检索、长期语义记忆和向量索引有较直观的工程展示价值。

### 6.2 Milvus Lite 的问题

- 对一个小规模秋招 Demo 来说，独立向量数据库可能增加部署和解释成本；
- Milvus Lite、本地内存兜底和 PostgreSQL 同时存在，容易让架构显得过重；
- 如果没有展示数据规模、索引配置、召回评估和故障恢复，面试官可能认为只是“接入了一个组件”。

### 6.3 推荐决策

推荐采用“抽象接口 + 可替换实现”的折中方案：

1. 定义统一的 `VectorStore` 接口，隔离 RAG 和长期记忆对具体数据库的依赖。
2. 继续保留 Milvus Lite 作为当前演示实现，保证现有评测和功能稳定。
3. 后续补充 PostgreSQL + pgvector 实现，作为小规模部署方案。
4. README 明确：
   - 小规模单机部署可使用 pgvector；
   - 需要独立向量服务或更大规模数据时使用 Milvus；
   - 内存向量库只用于测试和故障降级。
5. 不要为了“技术栈更多”同时默认启动所有组件。

如果当前优先级是“最容易让面试官运行”，可以最终收敛为 PostgreSQL + pgvector + 可选 Redis；如果当前优先级是“突出向量检索工程能力”，则保留 PostgreSQL + Redis + Milvus Lite 更合适。

## 七、推荐目标架构

```text
                React + TypeScript
                       │ HTTP / SSE
                       ▼
                     FastAPI
                       │
        ┌──────────────┴──────────────┐
        │                             │
   AgentService                    RAGService
        │                             │
 意图识别 → 模式路由           解析 → 分块 → 入库
        │                             │
 ReAct / Plan-Execute       BM25 + VectorStore
        │                             │
 工具、记忆、反思             RRF → 重排 → 引用
        │                             │
        └──────────────┬──────────────┘
                       │
       ┌───────────────┼────────────────┐
       │               │                │
    Redis          PostgreSQL       VectorStore
   热数据/TTL      业务/持久化       Milvus 或 pgvector
                       │
                 内存降级兜底
```

核心设计原则：

- Agent 层不直接依赖 Milvus 类，而依赖 RAG 或 VectorStore 接口。
- PostgreSQL 保存可查询的业务事实和元数据。
- 向量库只负责向量及其检索，不承担完整业务数据职责。
- 所有外部依赖都应有超时、日志和降级策略。
- 默认启动路径尽可能少，完整能力通过配置打开。

## 八、分阶段改进路线

### P0：必须完成，决定项目是否能稳定展示

1. 统一 README 和项目标题，采用“通用底座 + 医疗 Demo”的定位。
2. 修正文档链接，确保 README 中的路径与 `docs/File/` 实际结构一致。
3. 补充 `.gitignore`，忽略 Milvus 本地数据库、上传文件、前端构建产物和临时文件。
4. 在 Python 3.11 或 3.12 虚拟环境中重新安装依赖并运行 pytest、ruff。
5. 提供最小运行模式和完整运行模式说明。
6. 补充 RAG 评测数据、脚本、参数和结果复现说明。
7. 显式加入医疗安全边界和高风险症状分流。

### P1：建议完成，决定项目是否“优秀”

1. 抽象 `VectorStore` 接口，降低对 Milvus 的耦合。
2. 增加端到端 API、RAG 和 SSE 测试。
3. 增加文档权限、用户隔离和文件大小/类型校验。
4. 增加数据库迁移工具，替代仅依赖 `create_all` 的初始化方式。
5. 增加结构化日志、trace_id、检索耗时和模型调用耗时统计。
6. 提供 Docker Compose，一键启动 PostgreSQL、Redis 和应用。
7. 将 Agent 评测从“能运行”扩展到任务成功率、工具调用准确率、引用覆盖率和延迟。

### P2：加分项

1. 增加 pgvector 实现并提供 Milvus/pgvector 配置切换。
2. 增加领域插件配置，而不是把医疗规则硬编码在通用流程中。
3. 增加后台任务处理大文件和批量入库。
4. 增加缓存命中率、熔断次数、降级次数等监控指标。
5. 增加多租户知识库和文档级权限过滤。
6. 增加人工反馈、答案评分和评测集自动回流。

## 九、面试表达建议

建议用以下顺序介绍项目：

1. **业务问题**：用户上传健康或企业文档后，希望获得有引用、可追溯的问答，而不是无依据的聊天。
2. **核心方案**：通用文档知识库 + 混合检索 + Agent 工具编排 + 多级记忆。
3. **关键难点**：中文关键词召回、BM25 重启重建、向量检索降级、Agent 模式选择和高风险回答控制。
4. **量化结果**：说明数据集、指标、基线、实验参数和提升结果。
5. **工程保障**：测试、CI、熔断、超时、降级、日志和 SSE 轨迹。
6. **领域 Demo**：最后介绍心血管慢病场景，以及它如何通过插件增加医疗安全策略。

不要把重点放在“我用了多少组件”，而应强调：

- 为什么需要混合检索；
- 为什么 Redis 和 PostgreSQL 分工；
- 为什么向量库可以替换；
- 发生故障时系统如何继续工作；
- 如何证明系统确实变好了。

## 十、最终决策

| 决策项 | 推荐方案 |
|---|---|
| 产品定位 | 通用 Agent/RAG 平台 + 心血管默认 Demo |
| PostgreSQL | 保留，作为业务和持久化主库 |
| Redis | 保留为可选短期记忆和热点缓存 |
| 内存 | 仅作为开发和故障降级方案 |
| Milvus | 当前保留 Milvus Lite，但通过 VectorStore 抽象隔离 |
| pgvector | 作为后续简化部署的可选实现 |
| MySQL | 暂不替换，除非岗位或部署环境有明确要求 |
| 医疗安全 | 作为领域插件和默认 Demo 能力显式保留 |
| 首要工作 | 统一定位、修正文档、保证可复现、补齐安全和端到端验证 |

最终目标不是让项目拥有最多的基础设施，而是让面试官能够在较短时间内看懂：项目解决什么问题、核心技术为什么这样设计、指标如何验证、故障如何降级，以及它如何从一个具体领域扩展为通用平台。
