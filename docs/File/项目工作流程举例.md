# 项目工作流程举例（新人必读 · 面试讲稿版）

> 目标读者：第一次接触本项目的人。读完本文，你能不看代码讲清楚
> "用户发一句话，系统内部发生了什么"，并且能应对面试官的各种追问。
> 配套阅读：[项目全景文档](./项目全景文档.md)、[评估报告-混合检索](./评估报告-混合检索.md)。

---

## 0. 一句话版本

用户输入 → **意图识别**（这是什么类型的问题）→ **模式路由**（该用哪种 Agent 范式）
→ **Agent 编排**（ReAct 循环或先规划再执行）→ **读取记忆 + 调用工具 + 知识库检索**
→ **反思打分** → **写入记忆** → 返回带步骤追踪的结构化回答。

---

## 1. 主链路总览（代码级）

```
前端 (React)
  │ POST /api/v1/chat/agent  {messages, agent_mode}
  ▼
chat.py::chat_agent                                   [app/api/routes/chat.py]
  ▼
AgentService.chat()                                    [app/core/agent_service.py]
  ├─ 1. 意图识别   IntentRecognizer.recognize()       [app/core/intent/recognizer.py]
  │      LLM 分类（5 类意图）→ 失败降级关键词规则
  ├─ 2. 模式路由   ModeRouter.resolve()                [app/core/agent/mode_router.py]
  │      规则快路径 → LLM Router → react 兜底
  ├─ 3. 编排执行   AgentOrchestrator.run()             [app/core/agent/orchestrator.py]
  │      ├─ react       → ReActAgent / FunctionCallAgent
  │      ├─ plan_execute → PlannerAgent（规划→执行→重规划→汇总）
  │      └─ 反思评估     ReflectionAgent（质量分/幻觉检测）
  ├─ 4. 记忆写入   PersistentMemoryManager.append_turn() [app/core/persistent_memory.py]
  │      内存兜底 + PostgreSQL 主路径 + Redis 热路径
  └─ 5. 组装响应   AgentChatResponse（steps / tool_calls / reflection_score / degraded）
```

**一次请求的完整生命周期**（以 `react` 模式为例）：

1. 取请求最后一条消息作为用户输入。
2. 意图识别：LLM few-shot 分类出"数学计算 / 知识问答 / 实时搜索 / 文档管理 / 闲聊对话"之一；
   LLM 不可用或超时时，用关键词规则降级，置信度低时进入澄清逻辑。
3. 模式路由：高置信度走规则映射（如"数学计算→react"、"实时搜索→plan_execute"）；
   低置信度交给 LLM 二次判断；LLM 也失败则默认 react。
4. 编排器执行：
   - ReAct 循环开始前，先读取记忆（短期 Redis→PG→内存，长期 Milvus 语义召回），
     合并成"记忆摘要"注入 system prompt；
   - 循环内：LLM 输出 → 正则解析 Thought/Action/Action Input → 调用工具
     （calculator / web_search / rag_search）→ 观察结果拼回上下文 → 直到 Final Answer；
   - 达到最大步数仍未出答案则返回失败。
5. 反思评估：对最终答案做质量分（0-100）、完整性、幻觉检测；失败只记日志不影响主流程。
6. 记忆写入：把"用户问题 + 助手回答"按 内存 → PostgreSQL → Redis 的顺序级联写入。
7. 返回 `AgentChatResponse`，前端据此渲染意图标签、执行步骤、工具调用日志、反思分数。

## 2. 场景一：简单知识问答（纯 LLM，无工具）

**用户输入**：`什么是高血压？`

**流程**：

| 步骤 | 发生什么 | 代码位置 |
|------|----------|----------|
| 意图 | LLM 识别为"知识问答"，置信度约 0.9 | recognizer.py::_llm_classify |
| 路由 | 规则：知识问答 → react（无时间敏感词，不升级） | mode_router.py::_rule_resolve |
| 记忆 | 读取该会话最近对话；新会话则为空 | persistent_memory.py::get_relevant |
| 执行 | ReAct 循环：LLM 直接给出 Final Answer，未调用任何工具 | react_agent.py::run |
| 反思 | 对答案打分（例如 85 分，无幻觉） | reflection.py |
| 写入 | 保存 user/assistant 两轮 | persistent_memory.py::append_turn |
| 返回 | `agent_mode=react, tool_calls=[]` | agent_service.py::chat |

**为什么不需要 RAG？** 高血压这类常识性问题，模型参数内已有足够知识，
直接回答延迟最低。RAG 是"需要依据"时的增强手段，不是所有问题都要走。

**追问点**：如果模型答错了怎么办？——反思阶段会给出低质量分并标记疑似幻觉，
当前设计是记录但不强制重试；阈值化重试是已声明的后续优化方向。

## 3. 场景二：数学计算（单步工具调用）

**用户输入**：`帮我算 123 * 456 等于多少？`

**流程**：

| 步骤 | 发生什么 | 代码位置 |
|------|----------|----------|
| 意图 | 命中关键词"计算/等于/*"，LLM 或规则识别为"数学计算" | recognizer.py::_keyword_classify |
| 路由 | 规则：数学计算 → react（置信度高于 0.70） | mode_router.py |
| 执行 | ReAct 循环第 1 轮：`Thought: 需要调用计算器` → `Action: calculator` → `Action Input: {"expression": "123*456"}` | react_agent.py::_parse_react_step |
| 工具 | ToolRegistry 查到 calculator，执行返回 `56088` | tools/builtin/calculator.py |
| 观察 | 工具结果作为 Observation 追加进上下文 | react_agent.py 循环 |
| 收尾 | 第 2 轮 LLM 看到结果，输出 `Final Answer: 123 × 456 = 56088` | react_agent.py |

**为什么不让 LLM 直接心算？** 数值计算是 LLM 的弱项，容易出错；
把计算委托给确定性工具，模型只负责"决定调用什么工具、怎么解读结果"，
这正是 Agent 相对纯 ChatBot 的核心价值。

**追问点**：`Action Input` 解析失败怎么办？——解析器捕获 JSON 错误并记录
`parse_error`，不会让整个循环崩溃；工具执行异常时由工具适配器返回错误文本，
模型看到后可以换工具或直接给出降级回答。

## 4. 场景三：知识库问答（RAG 作为 Agent 工具）

**用户输入**：`高血压患者饮食要注意什么？`

**前提**：知识库已上传医学指南（例如 `milvus_eval.db` 中 445 个文档块）。

**流程**：

1. 意图识别为"知识问答"。
2. 路由到 react；工具列表包含 `rag_search`（`set_rag_service()` 时注册）。
3. ReAct 循环第 1 轮：
   ```
   Thought: 用户问的是饮食建议，知识库里有医学指南，先检索
   Action: rag_search
   Action Input: {"query": "高血压 饮食 低盐 建议", "top_k": 5}
   ```
4. `rag_search` 内部调用 `RAGService.search(mode="hybrid")`：
   - 向量检索：问题编码为 384 维向量，在 Milvus 做余弦相似度召回；
   - 关键词检索：jieba 分词后 BM25 召回；
   - RRF 融合：两路结果按排名融合（`score = Σ 1/(k+rank)`），去重排序。
5. 工具返回带相关度和来源的文本块，Agent 基于检索内容生成回答，
   并在回答中用 `[1]`、`[2]` 标注引用。
6. 反思检查回答是否"有依据"；前端 RAGContext 组件展示引用来源。

**RAG 为什么不做成独立端点就够了？** 因为真实问题可能是
"饮食要注意什么 + 顺便帮我算下 BMI"，把 RAG 封装成工具后，
Agent 可以在一轮对话里自主决定"查库 + 计算 + 整合"，
而不是人为指定走哪条链路。

**追问点**：检索结果为空怎么办？——`rag_search` 工具返回提示文案，
Agent 会看到"未找到相关内容，建议换关键词或使用 web_search"，
并自动降级为网络搜索或基于已有知识回答（`tools/builtin/rag_search.py`）。

## 5. 场景四：复杂综合咨询（Plan-and-Execute）

**用户输入**：`我最近血压偏高、睡眠不好，体检血脂也高，帮我分析一下日常怎么调整。`

这是一个多因素、多约束问题，一次 ReAct 循环容易漏项，路由会走 plan_execute。

**流程**：

1. **规划**：Planner 调 LLM 生成子任务列表（JSON）：
   ```
   [{"title": "提取健康信息", "expected_tools": []},
    {"title": "检索高血压/血脂/睡眠知识", "expected_tools": ["rag_search"]},
    {"title": "生成综合调整建议", "expected_tools": []}]
   ```
2. **执行**：每个子任务创建一个独立的 ReAct 循环执行
   （复用 `_invoke_react()`，保证"执行=ReAct"的架构一致性）；
   子任务还可以指定 `allowed_tools` 限制工具范围。
3. **失败处理**：某子任务失败 → 触发**重规划**（最多 2 次）；
   整个 plan_execute 失败 → 编排器降级为纯 react 重跑，并在 prompt 加 `[Plan 降级]` 前缀，
   响应中 `degraded=True`。
4. **汇总**：所有子任务完成后，LLM 把结果整合成一份结构化回答
   （饮食、运动、睡眠、监测、就医提醒）。

**为什么不能只靠 ReAct？** ReAct 是"边想边做"，适合探索型任务；
但多目标任务容易步骤发散、执行链路不可控。Plan-and-Execute 先把问题
拆成有顺序的子任务，每步可控、可重试，最后统一汇总。

**追问点**：规划 JSON 解析失败怎么办？——`_extract_json_object` 会从
模型输出里用正则捞 JSON；捞不到则抛出异常，由上层降级 react。

## 6. 场景五：多轮对话与跨会话记忆

**用户输入（第 2 轮）**：`那我还适合喝咖啡吗？`

此时记忆系统发挥关键作用：

1. ReAct 循环开始前调用 `get_relevant(session_id, query)`，级联读取：
   - 短期：Redis 最近 N 条消息（滑动窗口，超阈值自动 LLM 摘要压缩）；
   - 冷存储：Redis 不可用 → PostgreSQL 最近消息；
   - 兜底：内存 dict；
   - 长期语义：Milvus 中按 query 语义召回历史片段，加 `[历史记忆]` 前缀插到最前面。
2. 合并结果注入 system prompt 的"检索记忆摘要"块，
   于是模型知道"用户前面说过自己有高血压"，回答咖啡问题时会带上前文约束。
3. 对话结束后 `append_turn` 双写：内存（同步）+ PostgreSQL（主）+ Redis（辅）。

**为什么分这么多层？** 短期记忆要快（Redis），长期事实要持久（PG），
跨会话语义召回要靠向量（Milvus）——"今天说了什么"和"上周说过什么"是两种需求，
单一存储无法同时满足低延迟、持久化、语义检索。

**追问点**：Redis 挂了会怎样？——每次读取失败会标记降级并切到 PG，
整个链路不中断，这就是设计里"渐进降级"的意义。

## 7. 场景六：故障与降级（面试必考）

| 故障 | 表现 | 降级路径 | 代码位置 |
|------|------|----------|----------|
| LLM 全部不可用 | 意图识别失败 | 关键词规则降级，仍能返回基础意图 | recognizer.py |
| LLM Router 决策失败 | 模式选择失败 | 直接兜底 react | mode_router.py |
| Redis 不可用 | 短期记忆读写失败 | 切 PostgreSQL → 内存 | persistent_memory.py |
| Milvus 不可用 | 向量检索失败 | 降级为内存向量库（n-gram 嵌入 + 暴力搜索） | rag_service.py |
| sentence-transformers 加载失败 | 语义嵌入失败 | 降级 n-gram 嵌入（256 维） | rag_service.py::_get_embedding_model |
| 知识库为空 | rag_search 无内容 | 工具提示改查 web_search | tools/builtin/rag_search.py |
| 工具执行异常 | 工具返回错误 | 错误文本回给模型，模型换工具或直接回答 | agent_service.py::_ToolRegistryAdapter |
| plan_execute 失败 | 规划/执行失败 | 重规划 2 次 → 降级 react（degraded=True） | orchestrator.py |
| 反思阶段异常 | 评分失败 | 跳过，只记 warning，不影响回答 | orchestrator.py::_run_reflection |
| 模型调用连续失败 | 下游服务故障 | 三态熔断器（Closed→Open→Half-Open）保护 | infrastructure/llm/circuit_breaker.py |

**一句话原则**：模型负责智能，代码负责边界。所有不确定性都走
"重试 → 降级 → 明确告知用户"的路径，而不是让链路崩溃或模型编造答案。

## 8. 场景七：文档上传与知识库构建（RAG 摄入）

**用户操作**：上传 PDF/TXT/Word 文档。

**流程**（`POST /api/v1/rag/ingest`）：

```
文件 → ingest_file()
  → 解析（PDF/TXT/Word → 纯文本）      app/etl/parser.py
  → 分块（递归分块 + overlap）          app/etl/chunker.py
  → 向量化（all-MiniLM-L6-v2, 384 维）  rag_service.py::_get_embedding_model
  → 双写入库：
      Milvus（向量 + 内容 + 来源）       _MilvusRAGStore.add_batch()
      BM25 内存索引（jieba 分词）         _BM25.add()
  → 返回 chunk_count
```

**关键设计**：BM25 索引是内存态，服务重启后必须从 Milvus 内容重建——
这是评估阶段发现并修复的真实 Bug（`_rebuild_bm25()`），
面试时可以主动讲"我通过评测发现重启后 keyword 检索静默失效，修复后 hybrid 才真正生效"。

**配套接口**：`/rag/status`（知识库状态）、`/rag/documents`（文档列表）、
`/rag/search_compare`（三路检索对比，前端调试面板用）。

## 9. 场景八：流式输出（SSE）

`POST /api/v1/chat/stream` 返回 `text/event-stream`：

```text
data: {"content": "你", "trace_id": "..."}

data: {"content": "好", "trace_id": "..."}

data: {"done": true}
```

前端逐块渲染，体验更接近真实对话。注意：流式端点走的是普通 Chat 链路
（OpenAI 流式接口直连），Agent 编排的步骤追踪走 `/chat/agent` 非流式端点。

## 10. 场景九：Function Calling 后端（进阶）

ReAct 有两种工具调用后端，通过配置切换：

| 后端 | 实现 | 特点 |
|------|------|------|
| 正则解析（默认） | `ReActAgent`：解析 `Thought/Action/Action Input` 文本 | 不依赖框架，Prompt 可控 |
| Function Calling | `FunctionCallAgent`：LangChain `bind_tools` 结构化调用 | 解析更稳，减少格式错误 |

两者共用同一套循环控制、记忆注入、步数上限（`_invoke_react()` 统一入口），
所以 FC **不是第三种模式**，只是 ReAct 内部的实现升级——这是本项目
与"套 LangChain 模板"类项目的关键区别，面试官常追问。

## 11. 响应结构（前端拿到的数据）

```json
{
  "id": "trace-uuid",
  "content": "最终回答",
  "agent_mode": "react",
  "intent": {"intent": "知识问答", "confidence": 0.9, "sub_intent": "概念原理"},
  "steps": [
    {"step": 0, "phase": "react", "thought": "...", "action": "rag_search",
     "action_input": {"query": "..."}, "observation": "检索结果..."}
  ],
  "tool_calls": ["rag_search"],
  "reflection_score": 85,
  "degraded": false
}
```

前端对应组件：`IntentBadge`（意图标签）、`AgentSteps`（执行步骤）、
`ToolCallLog`（工具日志）、`RAGContext`（引用来源）、`SearchCompare`（三路对比）、
`HealthPanel`（后端健康状态）。

## 12. 面试速答表

| 问题 | 一句话回答 |
|------|------------|
| 为什么用 Agent 而不是 ChatBot？ | 复杂问题需要规划、检索、计算、整合多步骤协同，Agent 让模型参与任务拆解与工具调度而非只生成文本 |
| 为什么两种范式？ | ReAct 适合探索型任务，Plan-and-Execute 适合多目标任务；条件路由兼顾灵活与可控 |
| RAG 为什么做成工具？ | 让 Agent 自主决定何时查库、何时搜网、何时交叉验证，而不是人工固定链路 |
| 为什么自研编排而不用 LangGraph？ | 面试可控、调试直观；LangChain 只用在 bind_tools 一处，其余全部自研 |
| 如何避免幻觉？ | 知识层面 RAG 依据、生成层面强制引用、流程层面任务拆解、安全层面就医提示、兜底层面检索不足明说 |
| 如何保证工程质量？ | 445 块知识库 + 29 条标注查询的量化评估（Recall@K/MRR/NDCG）、67 个单元测试、CI、全链路降级 |
| 最大难点是什么？ | 把意图、路由、记忆、RAG、工具、降级串成稳定链路；评测中发现并修复 BM25 重启丢失等真实问题 |

## 13. 新人 5 分钟上手路径

1. 读本文第 1 节，理解主链路；
2. 按 [README](../README.md) 启动后端，用 curl 打 `/chat/agent` 分别试：
   "你好"（闲聊）、"帮我算 123*456"（工具）、"高血压饮食注意什么"（RAG）；
3. 观察响应里的 `intent / agent_mode / steps / tool_calls` 字段；
4. 跑 `python -m pytest`（67 个用例）和 `scripts/eval_rag_standalone.py`（评估自检）；
5. 打开前端，三栏布局里点开 Agent 步骤和 RAG 引用，直观看到链路。
